## 1. HTTP 상태 코드란 무엇인가

클라이언트가 요청을 보내면 서버는 응답의 상태 라인에 세 자리 상태 코드를 포함한다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 100,
  "username": "kim"
}
```

HTTP/1.1에서는 `200 OK`처럼 상태 코드와 사유 문구를 볼 수 있다. HTTP/2와 HTTP/3에서는 사람이 읽는 사유 문구 없이 상태 코드가 `:status` 의사 헤더로 전달되지만 의미는 같다.

### 상태 코드의 다섯 분류

| 범위  | 분류          | 의미                                                |
| ----- | ------------- | --------------------------------------------------- |
| `1xx` | Informational | 최종 응답 전의 중간 정보                            |
| `2xx` | Successful    | 요청을 성공적으로 처리                              |
| `3xx` | Redirection   | 다른 위치, 표현 또는 캐시를 사용하기 위한 추가 처리 |
| `4xx` | Client Error  | 현재 요청을 서버가 처리할 수 없다                   |
| `5xx` | Server Error  | 유효한 요청을 서버가 처리하지 못한다                |

### 상태 코드와 응답 본문

상태 코드는 처리 결과의 큰 범주를 전달하고, 응답 본문은 구체적인 데이터나 오류 정보를 전달한다.

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-error",
  "title": "입력값 검증에 실패했다.",
  "status": 422,
  "errors": {
    "age": ["age는 0 이상의 정수여야 한다."]
  }
}
```

상태 코드만으로 모든 업무 오류를 세분화하지 말고, 안정적인 오류 코드와 상세 내용을 응답 본문에 함께 제공하는 것이 좋다.

## 알 수 없는 상태 코드를 받을 때

클라이언트는 등록되지 않았거나 처음 보는 상태 코드를 같은 범위의 `x00` 코드처럼 취급할 수 있어야 한다.

```text
299 -> 세부 의미는 모르지만 2xx 범주의 성공 응답
499 -> 세부 의미는 모르지만 4xx 범주의 요청 문제
599 -> 세부 의미는 모르지만 5xx 범주의 서버 문제
```

이는 `299`의 세부 동작이 `200 OK`와 완전히 같다는 의미는 아니다. 최소한 응답의 큰 범주를 판단하여 예기치 않게 동작이 중단되지 않도록 한다는 의미다.

알 수 없는 상태 코드를 받은 클라이언트는 다음처럼 방어적으로 처리해야 한다.

1. 백의 자리로 성공, 리다이렉션, 오류 범주를 판단한다.
2. 응답 헤더와 본문을 API 명세에 맞게 검증한다.
3. 무조건 캐시하지 않는다. 인식하지 못한 상태 코드의 응답은 캐시하면 안 된다.
4. 관측 가능한 로그나 모니터링 정보에 상태 코드를 남긴다.

새로운 상태 코드가 생겨도 클라이언트가 중단되는 것을 방지할 수 있으나, 새로운 코드의 특별한 의미까지 자동으로 이해하는 것은 아니다.
