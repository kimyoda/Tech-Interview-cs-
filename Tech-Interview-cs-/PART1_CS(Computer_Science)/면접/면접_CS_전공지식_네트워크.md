# 네트워크

---

## 네트워크 기초

### 처리량과 지연 시간

#### 대역폭

**대역폭(Bandwidth)**은 단위 시간 동안 전송할 수 있는 최대 데이터의 양이다.

다음과 같은 단위를 사용한다.

- `bps`: 초당 비트 수
- `Mbps`: 초당 메가비트 수
- `Gbps`: 초당 기가비트 수

```text
대역폭 = 도로의 최대 차선 수
```

대역폭이 크다고 해서 실제 데이터 전송 속도가 항상 최대치로 나오는 것은 아니다.

---

#### 처리량

**처리량(Throughput)**은 단위 시간 동안 실제로 전송하거나 처리한 데이터의 양이다.

```text
처리량 = 실제로 도로를 통과한 차량 수
```

처리량은 다음과 같은 요인의 영향을 받는다.

- 네트워크 대역폭
- 패킷 손실
- 네트워크 혼잡
- 서버 처리 능력
- 데이터베이스 처리 속도
- 동시 접속자 수
- 프로토콜 오버헤드

특정 네트워크 구간의 실제 처리량은 일반적으로 해당 구간의 최대 대역폭보다 작다.

---

#### Goodput

**Goodput**은 프로토콜 헤더와 재전송 데이터 등을 제외하고 애플리케이션이 실제로 전달받은 유효 데이터의 양이다.

```text
대역폭 >= 처리량 >= Goodput
```

예를 들어 네트워크에서 100MB를 전송했더라도 그 안에는 TCP/IP 헤더와 재전송된 데이터가 포함될 수 있다.

따라서 애플리케이션이 실제로 전달받은 유효 데이터의 양은 100MB보다 작을 수 있다.

---

#### 지연 시간

**지연 시간(Latency)**은 데이터가 출발지에서 목적지까지 전달되는 데 걸리는 시간이다.

지연 시간은 문맥에 따라 다음과 같이 구분할 수 있다.

- 단방향 지연 시간: 출발지에서 목적지까지 전달되는 데 걸리는 시간
- RTT: 요청이 목적지에 도착한 후 응답이 다시 출발지로 돌아오기까지 걸리는 시간
- API 응답 시간: 네트워크 지연뿐만 아니라 서버 처리 시간까지 포함한 시간

```text
API 응답 시간
= DNS 조회 시간
+ TCP 연결 시간
+ TLS 연결 시간
+ 네트워크 왕복 시간
+ 서버 대기 시간
+ 서버 처리 시간
+ 응답 데이터 전송 시간
```

항상 모든 단계가 발생하는 것은 아니다.

연결을 재사용하거나 DNS 결과를 캐시하고 있다면 DNS 조회, TCP 연결 및 TLS 연결 과정이 생략될 수 있다.

---

#### RTT

**RTT(Round Trip Time)**는 데이터가 목적지에 도착한 뒤 응답이 다시 출발지로 돌아오기까지 걸리는 왕복 시간이다.

```text
클라이언트 → 서버 → 클라이언트
```

`ping` 명령어로 확인하는 시간이 대표적인 RTT다.

단, `ping`은 ICMP를 사용하므로 실제 HTTP API의 응답 시간과 같지는 않다.

---

#### 처리량과 지연 시간 비교

| 구분        | 처리량                                | 지연 시간                                |
| ----------- | ------------------------------------- | ---------------------------------------- |
| 의미        | 단위 시간당 처리한 데이터나 요청의 양 | 요청이나 데이터 전달에 걸린 시간         |
| 대표 단위   | Mbps, Gbps, TPS, RPS                  | ms, s                                    |
| 개선 방법   | 서버 확장, 병렬 처리, 커넥션 풀 조정  | 캐싱, CDN, 쿼리 최적화, 가까운 리전 사용 |
| 사용자 체감 | 많은 요청을 동시에 처리할 수 있음     | 하나의 요청이 빠르게 응답함              |

- 처리량이 높아도 지연 시간이 크면 사용자는 서비스가 느리다고 느낀다.
- 단일 요청은 빠르더라도 동시에 처리할 수 있는 요청 수가 적으면 트래픽 증가 시 장애가 발생할 수 있다.

---

#### 게임 서버 예시

```text
처리량 문제

→ 동시에 많은 게임 요청을 처리하기 어려움
→ API 서버 증설, DB 커넥션 조정, 비동기 처리 검토

지연 시간 문제

→ 한 번의 랭킹 조회에 오랜 시간이 걸림
→ 인덱스 추가, 쿼리 최적화, Redis 캐싱 적용
```

> 처리량은 단위 시간 동안 실제로 처리할 수 있는 데이터나 요청의 양이고, 지연 시간은 하나의 요청이나 데이터가 전달되는 데 걸리는 시간이다.

> 처리량은 서버 확장, 병렬 처리 및 커넥션 풀 조정 등으로 개선할 수 있다. 지연 시간은 캐싱, CDN, 쿼리 최적화 및 네트워크 거리 단축 등으로 개선할 수 있다.

### 네트워크 토폴로지와 병목 현상

#### 네트워크 토폴로지

**네트워크 토폴로지(Network Topology)**는 네트워크 장치와 노드가 연결된 형태를 의미한다.

| 형태   | 설명                              | 장점                      | 단점                                      |
| ------ | --------------------------------- | ------------------------- | ----------------------------------------- |
| 버스형 | 하나의 공통 회선에 여러 노드 연결 | 구성이 단순함             | 공통 회선 장애에 취약함                   |
| 스타형 | 중앙 장치에 모든 노드 연결        | 관리와 장애 파악이 쉬움   | 중앙 장치가 단일 장애 지점이 될 수 있음   |
| 링형   | 노드를 원형으로 연결              | 일정한 순서로 데이터 전달 | 한 구간의 장애가 전체에 영향을 줄 수 있음 |
| 메시형 | 노드들을 여러 경로로 연결         | 장애에 강함               | 비용이 높고 구성이 복잡함                 |
| 트리형 | 계층 구조로 노드 연결             | 확장이 쉬움               | 상위 장치의 장애 영향이 큼                |

현대적인 사내 네트워크에서는 스위치를 중심으로 장치를 연결하는 스타형 구조를 많이 사용한다.

---

#### 병목 현상

**병목 현상(Bottleneck)**은 시스템의 특정 구간이 전체 시스템의 처리 성능을 제한하는 현상이다.

```text
클라이언트
    ↓
로드밸런서
    ↓
API 서버
    ↓
Redis
    ↓
MySQL
```

이 구조에서 API 서버를 여러 대 추가하더라도 MySQL이 처리할 수 있는 쿼리 수가 부족하면 전체 처리량은 증가하지 않는다.

이 경우 실제 병목은 API 서버가 아니라 MySQL이다.

---

#### 서버에서 자주 발생하는 병목

- 데이터베이스의 Slow Query
- 잘못된 인덱스
- DB Lock 대기
- 부족한 DB 커넥션 풀
- Redis의 특정 Key에 요청 집중
- 외부 API 응답 지연
- CPU 사용률 증가
- 메모리 부족과 Swap 발생
- Node.js Event Loop Blocking
- 네트워크 패킷 손실
- 로드밸런서의 연결 수 제한
- 과도한 로그 출력

---

#### 병목 분석 순서

```text
1. 사용자 또는 클라이언트 구간 확인

2. DNS, TCP, TLS 연결 시간 확인

3. 로드밸런서와 리버스 프록시 확인

4. API 서버 처리 시간 확인

5. Event Loop, CPU, 메모리 사용량 확인

6. 데이터베이스 쿼리와 Lock 확인

7. Redis와 외부 API 확인

8. 네트워크 패킷 손실과 RTT 확인
```

원인을 확인하지 않고 서버 인스턴스부터 늘리면 실제 병목이 데이터베이스에 있을 때 효과가 없을 수 있다.

오히려 더 많은 API 서버가 데이터베이스에 요청을 보내면서 DB 부하가 증가할 수 있다.

### 네트워크 분류

| 분류 | 범위                  | 예시                  |
| ---- | --------------------- | --------------------- |
| PAN  | 개인 주변의 짧은 거리 | 블루투스, 스마트워치  |
| LAN  | 건물, 사무실, 가정    | 사내망, 가정용 공유기 |
| MAN  | 도시 규모             | 도시 통신망           |
| WAN  | 국가 또는 대륙 규모   | 인터넷, 기업 전용 망  |

#### PAN

**PAN(Personal Area Network)**은 개인 주변의 짧은 거리에 사용하는 네트워크다

```text
스마트폰 <-> 블루투스 이어폰
```

#### LAN

**MAN(Metropolitan Area Network)**은 도시 규모의 네트워크다

#### WAN

**WAN(Wide Area Network)**은 국가나 대륙처럼 넓은 지역을 연결하는 네트워크다

인터넷은 여러 LAN과 WAN이 서로 연결된 거대한 네트워크다

### 네트워크 성능 분석 명령어

| 명령어       | 용도                                          |
| ------------ | --------------------------------------------- |
| `ping`       | RTT와 패킷 손실                               |
| `traceroute` | macOS/Linux에서 목적지까지 확인               |

| `nslookup`   | DNS 조회                                      |
| `dig`        | DNS 상세                                      |
| `curl`       | HTTP 요청과 단계별 시간 확인                  |

---

#### ping

```bash
ping api.example.com
```

확인할 수 있는 내용은 다음과 같다

- 대상 서버와 네트워크 통신 가능 여부
- RTT
- 패킷 손실률

주의할 점은 서버나 방화벽이 ICMP를 차단할 수 있다는 것

`ping`이 실패해서 반드시 HTTP 서버가 중단되는 것은 아님

---

#### traceroute, tracert

macOS/Liunx:

```bash
traceroute api.example.com
```

Windows:

```powershell
tracert api.example.com
```

목적지까지 거치는 라우터의 경로를 확인할 수 있음

각 라우터를 **홉(Hop)**라고 한다

다만 라우터가 응답하지 않거나 실제 왕복 경로가 서로 다를수 있기에 출력 결과만으로 정확한 장애 지점을 단정해서 안된다

---

#### 포트 상태 확인

Linux:

```bash
ss -lntp
```

macOS:

```bash
lsof -iTCP -sTCP:LISTEN -n -p
```

특정 포트 확인:

```bash
lsof -i :3000
```

#### HTTP 단계별 시간 확인

```bash
curl -o /dev/null -sS \
  -w 'remote_ip: %{remote_ip}\nDNS: %{time_namelookup}s\nTCP: %{time_connect}s\nTLS: %{time_appconnect}s\nTTFB: %{time_starttransfer}s\nTotal: %{time_total}s\nHTTP: %{http_code}\n' \
  https://api.example.com
```

| 항목                 | 의미                       |
| -------------------- | -------------------------- |
| `time_namelookup`    | DNS 조회가 끝난 시점       |
| `time_connect`       | TCP 연결이 끝난 시점       |
| `time_appconnect`    | TLS 연결이 끝난 시점       |
| `time_starttransfer` | 첫 응답 바이트를 받은 시점 |
| `time_total`         | 전체 요청이 끝난 시점      |

이 값들은 대부분 요청 시작 시점부터 측정한 누적 시간이다

따라서 순수 TLS 소요 시간을 구하려면 다음과 같이 차리를 계산해야 한다

```text
TLS 연결 시간 = time_appconnect - time_connect
```
