# DDL과 안전한 스키마 변경

> `CREATE`, `ALTER`, `RENAME`, `TRUNCATE`, `DROP`으로 데이터베이스 구조를 다루고, 운영 환경에서 스키마를 안전하게 변경하는 확장, 이행, 축소 절차를 이해한다.

---

## DDL이란?

- DDL(Data Definition Language)은 데이터 자체가 아닌 데이터를 담는 구조와 데이터베이스 객체를 정의하는 명령어

| 분류 | 대상                                       | 대표 명령                                       |
| ---- | ------------------------------------------ | ----------------------------------------------- |
| DDL  | 데이터베이스, 테이블, 열, 제약조건, 인덱스 | `CREATE`, `ALTER`, `RENAME`, `TRUNCATE`, `DROP` |
| DML  | 테이블 안의 행                             | `SELECT`, `INSERT`, `UPDATE`, `DELETE`          |
| DCL  | 계정과 권한                                | `GRANT`, `REVOKE`                               |
| TCL  | 트랜잭션                                   | `COMMIT`, `ROLLBACK`, `SAVEPOINT`               |

- 데이터가 아닌 테이블 구조를 만든다.

```sql
CREATE TABLE guilds (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50) NOT NULL UNIQUE
);
```

---

## MySQL DDL 두 가지

### 암묵적 커밋(Implicit Commit)

MySQL의 DDL 문장은 실행 전 트랜잭션을 암묵적으로 커밋하고, 대부분 실행 후에도 자체 작업을 확정한다.

```sql
START TRANSACTION;

UPDATE players
SET level = level + 1
WHERE id = 1;

CREATE TABLE ddl_example (
  id BIGINT UNSIGNED PRIMARY KEY
);

ROLLBACK;
```

- `ROLLBACK`을 실행해도 DDL 전에 실행한 `UPDATE`가 이미 암묵적으로 커밋될 수 있다.
- DML과 DDL을 하나의 사용자 트랜잭션으로 묶어 함께 되돌릴 수 있다고 생각하면 안 된다.

> `CREATE TEMPORARY TABLE`, `DROP TEMPORARY TABLE`에는 암묵적 커밋의 예외가 있으나, 해당 DDL 자체가 사용자 `ROLLBACK`으로 취소되는 것은 아니다.

### 원자적 DDL(Atomic DDL)

MySQL 8의 InnoDB는 지원되는 DDL에서 데이터 사전 변경, 스토리지 엔진 작업, Binary Log 기록을 하나의 원자적 작업으로 처리한다.

- 성공하면 관련 변경이 함께 반영
- DDL 실행 중 서버가 중단되면 지원 범위 안에서 전체 반영 또는 전체 취소
- 사용자가 `ROLLBACK`으로 DDL을 되돌릴 수 있다는 뜻은 아님

| 개념           | 의미                                                                 |
| -------------- | -------------------------------------------------------------------- |
| 원자적 DDL     | 장애 중간에 메타데이터와 스토리지 상태가 반쪽만 반영되는 문제를 줄임 |
| 트랜잭셔널 DDL | 사용자가 여러 DDL, DML을 묶고 `ROLLBACK`하는 기능을 뜻함             |

MySQL의 원자적 DDL과 트랜잭셔널 DDL은 같은 개념이 아니다.

## `CREATE DATABASE`

```sql
CREATE DATABASE game_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE game_db;
```

- `utf8mb4`: 한글과 이모지를 포함한 유니코드 문자 저장
- Collation: 문자열의 비교와 정렬 규칙
- `utf8mb4_0900_ai_ci`: 악센트, 대소문자를 구분하지 않는 MySQL 8 계열 정렬 규칙

존재할 때 오류를 피하려면 다음 문법을 사용한다.

```sql
CREATE DATABASE IF NOT EXISTS game_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

- `IF NOT EXISTS`는 이름 충돌 오류만 피한다.
- 이미 존재하는 데이터베이스의 문자 집합, 정렬 규칙이 원하는 설정과 같은지는 보장하지 않는다.

## `CREATE TABLE`

- 참조되는 부모 테이블을 먼저 만들고 외래키를 가진 자식 테이블을 나중에 만든다.
- 완성 예시는 그대로 다시 실행하지 말고 `SHOW CREATE TABLE`과 비교한다.

### `guilds` 테이블

```sql
CREATE TABLE guilds (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  founded_at DATE NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

  CONSTRAINT uk_guilds_name
    UNIQUE (name)
) ENGINE = InnoDB
  DEFAULT CHARACTER SET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

### `players` 테이블

```sql
CREATE TABLE players (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nickname VARCHAR(50) NOT NULL,
  email VARCHAR(100) NOT NULL,
  level INT UNSIGNED NOT NULL DEFAULT 1,
  vip_grade TINYINT UNSIGNED NOT NULL DEFAULT 0,
  gold BIGINT UNSIGNED NOT NULL DEFAULT 0,
  guild_id BIGINT UNSIGNED NULL,
  last_login_at DATETIME NULL,
  version INT UNSIGNED NOT NULL DEFAULT 0,

  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

  updated_at DATETIME NOT NULL
    DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP,

  CONSTRAINT uk_players_email
    UNIQUE (email),

  CONSTRAINT chk_players_level
    CHECK (level >= 1),

  CONSTRAINT chk_players_vip_grade
    CHECK (vip_grade BETWEEN 0 AND 5),

  CONSTRAINT fk_players_guild
    FOREIGN KEY (guild_id)
    REFERENCES guilds(id)
    ON DELETE SET NULL
) ENGINE = InnoDB
  DEFAULT CHARACTER SET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci;
```

### 정의를 읽는 순서

1. 열 이름과 자료형을 확인
2. `NULL` 허용 여부와 기본값을 확인
3. 기본키와 고유키를 확인
4. 값의 범위를 제한하는 `CHECK`를 확인
5. 외래키와 삭제 정책을 확인
6. 스토리지 엔진과 문자 집합을 확인

- `CREATE TABLE IF NOT EXISTS`도 기존 테이블 구조가 작성한 DDL과 동일한지 검증하지 않는다.

## 테이블 구조 확인

- 변경 전 현재 구조를 먼저 확인

```sql
DESCRIBE players;

SHOW CREATE TABLE players;

SHOW INDEX FROM players;
```

- `INFORMATION_SCHEMA`를 사용하면 코드에서 메타데이터를 조회할 수 있다.

```sql
SELECT
  column_name,
  column_type,
  is_nullable,
  column_default,
  extra
FROM information_schema.columns
WHERE table_schema = 'game_db'
  AND table_name = 'players'
ORDER BY ordinal_position;
```

- 외래키도 확인

```sql
SELECT
  constraint_name,
  column_name,
  referenced_table_name,
  referenced_column_name
FROM information_schema.key_column_usage
WHERE table_schema = 'game_db'
  AND table_name = 'players'
  AND referenced_table_name IS NOT NULL;
```

## `ALTER TABLE`: 열 변경

### 열 추가

```sql
ALTER TABLE players
ADD COLUMN bio VARCHAR(255) NULL;
```

### 자료형과 제약 변경

```sql
ALTER TABLE players
MODIFY COLUMN bio TEXT NULL;
```

`MODIFY COLUMN`에서는 유지할 자료형과 `NULL`, 기본값 등의 속성을 빠뜨리지 않도록 전체 정의를 정확히 작성한다.

### 열 이름 변경

```sql
ALTER TABLE players
RENAME COLUMN bio TO introduction;
```

```sql
ALTER TABLE players
CHANGE COLUMN introduction bio VARCHAR(255) NULL;
```

### 열 삭제

```sql
ALTER TABLE players
DROP COLUMN bio;
```

- 열을 삭제하면 그 열의 데이터도 함께 사라진다.
- 코드, 인덱스, 뷰, 배치, 통계 쿼리에서 해당 열을 사용하는지 먼저 조사한다.

## 제약조건과 인덱스 변경

- 같은 이름의 제약조건을 이미 만든 경우 중복 실행하지 않는다.

### 고유 제약조건 추가

```sql
ALTER TABLE players
ADD CONSTRAINT uk_players_nickname
UNIQUE (nickname);
```

- 기존 데이터에 중복 닉네임이 있으면 추가가 실패한다.

```sql
SELECT
  nickname,
  COUNT(*) AS duplicate_count
FROM players
GROUP BY nickname
HAVING COUNT(*) > 1;
```

### 고유 인덱스 삭제

- MySQL에서 고유 제약조건은 고유 인덱스로 구현되므로 인덱스 이름으로 삭제한다.

```sql
ALTER TABLE players
DROP INDEX uk_players_nickname;
```

### 외래키 추가

```sql
ALTER TABLE players
ADD CONSTRAINT fk_players_guild
  FOREIGN KEY (guild_id)
  REFERENCES guilds(id)
  ON DELETE SET NULL;
```

- 외래키 추가 전 고아 참조가 있는지 확인

```sql
SELECT
  p.id,
  p.guild_id
FROM players AS p
LEFT JOIN guilds AS g
  ON g.id = p.guild_id
WHERE p.guild_id IS NOT NULL
  AND g.id IS NULL;
```

### 외래키 삭제

```sql
ALTER TABLE players
DROP FOREIGN KEY fk_players_guild;
```

- 필요하지 않은 보조 인덱스까지 자동으로 모두 제거된다고 가정하지 말고 `SHOW INDEX`로 확인한다.

### 일반 인덱스 추가와 삭제

```sql
CREATE INDEX idx_players_guild_level
ON players (guild_id, level);
```

```sql
DROP INDEX idx_players_guild_level
ON players;
```

- 인덱스는 조회를 빠르게 할 수 있으나 저장 공간과 쓰기 비용을 늘린다.
- 실제 조회 조건과 `EXPLAIN` 결과를 기준으로 추가한다.

## 테이블 이름 변경

```sql
RENAME TABLE players TO game_players;
```

- 여러 테이블 이름을 하나의 문장으로 바꿀 수 있다.

```sql
RENAME TABLE
  players TO players_old,
  players_new TO players;
```

- 코드, 권한, 뷰, 저장 프로그램, 모니터링 및 배치 작업이 기존 이름을 참조하는지 확인한다.

## Online DDL, 잠금

- `ALTER TABLE`의 비용은 변경 종류와 테이블 크기에 따라 크게 달라진다.

| 알고리즘  | 개념                                   | 일반적인 부담              |
| --------- | -------------------------------------- | -------------------------- |
| `INSTANT` | 메타데이터만 변경                      | 가장 작음                  |
| `INPLACE` | 전체 복사 없이 스토리지 엔진 내부 처리 | 작업별 차이가 큼           |
| `COPY`    | 새 테이블을 만들고 데이터를 복사       | 시간, 공간, 잠금 부담이 큼 |

- MySQL이 지원하는 경우 `INSTANT`, 아니면 `INPLACE`, 필요하면 `COPY`를 선택한다.

```sql
ALTER TABLE players
  ADD COLUMN status VARCHAR(20) NULL,
  ALGORITHM = INSTANT;
```

- 동시 DML 허용 여부도 가능한 작업에서 제한할 수 있다.

```sql
ALTER TABLE players
  ADD INDEX idx_players_last_login_at (last_login_at),
  ALGORITHM = INPLACE,
  LOCK = NONE;
```

- 모든 변경이 모든 `ALGORITHM`, `LOCK` 조합을 지원하는 것은 아니다.
- 명시한 조건을 지원하지 않으면 문장이 실패할 수 있다.

### Online DDL도 완전한 무잠금이 아님

- 실행 시작과 종료 과정에 Metadata Lock이 필요할 수 있음
- 오래 실행 중인 트랜잭션이 Metadata Lock 획득을 지연시킬 수 있음
- CPU, 디스크 I/O, 임시 공간, 복제 지연이 증가할 수 있음
- `COPY` 알고리즘은 동시 DML을 막고 테이블과 인덱스 크기만큼 추가 공간이 필요할 수 있음

운영 실행 전 다음을 확인한다.

- 테이블 크기
- 장기 트랜잭션
- 지원 알고리즘
- 추가 디스크 공간
- 예상 시간
- 복제 상태

## 안전한 스키마 변경: Expand-Migrate-Contract

- 운영 환경에서 기존 열을 즉시 이름 변경하거나 삭제하면 이전 버전 애플리케이션이 실패할 수 있다.
- 새 구조를 추가하고, 데이터를 옮기고, 사용처를 전환한 후 오래된 구조를 제거한다.

### 예시: `nickname`을 `display_name`으로 전환

#### 1단계: Expand - 새 열 추가

```sql
ALTER TABLE players
ADD COLUMN display_name VARCHAR(50) NULL;
```

- 이 단계에서 기존 코드는 계속 `nickname`을 사용

#### 2단계: 새 코드에서 이중 쓰기

```sql
UPDATE players
SET
  nickname = 'Neo2',
  display_name = 'Neo2'
WHERE id = 1;
```

- 신규, 구버전 서버가 동시에 동작하는 배포 구간을 고려한다.

#### 3단계: 기존 데이터 이행

```sql
UPDATE players
SET display_name = nickname
WHERE display_name IS NULL
ORDER BY id
LIMIT 1000;
```

- 대량 테이블은 한 번에 모두 수정하지 말고 기본키 범위나 제한된 배치로 나눈다.
- 각 배치의 영향 행 수, 잠금 시간, 복제 지연을 확인한다.

#### 4단계: 검증

```sql
SELECT COUNT(*) AS missing_count
FROM players
WHERE display_name IS NULL;
```

```sql
SELECT COUNT(*) AS mismatch_count
FROM players
WHERE display_name <> nickname
   OR (display_name IS NULL) <> (nickname IS NULL);
```

#### 5단계: 읽기 전환 및 제약 강화

- 앱이 `display_name`을 읽도록 전환한 뒤 `NOT NULL`을 적용

```sql
ALTER TABLE players
MODIFY COLUMN display_name VARCHAR(50) NOT NULL;
```

#### 6단계: Contract - 오래된 열 제거

- 모든 코드와 배치의 전환을 확인한 후 별도 배포에서 제거

```sql
ALTER TABLE players
DROP COLUMN nickname;
```

#### 단계를 나누는 이유

- 배포 중 구버전과 신버전이 함께 동작할 수 있음
- 데이터 이행을 작은 배치로 제어
- 문제 발생 시 읽기 경로를 이전 열로 되돌리기 쉬움
- 파괴적 변경을 마지막으로 미룰 수 있음

## 자료형 변경 시 점검

```sql
ALTER TABLE players
MODIFY COLUMN nickname VARCHAR(100) NOT NULL;
```

- 길이를 늘리는 변경은 비교적 단순하지만 다음 변경은 데이터 손실과 긴 테이블 재구성을 유발할 수 있다.

- `BIGINT`를 `INT`로 축소

- `VARCHAR(100)`을 `VARCHAR(30)`으로 축소

- 문자열을 숫자나 날짜로 변경

- 문자 집합과 Collation 변경

- `NULL` 허용 열을 `NOT NULL`로 변경

- 정수의 `UNSIGNED` 속성 변경

- 변경 전 범위를 벗어나는 데이터를 검사한다.

```sql
SELECT
  id,
  nickname
FROM players
WHERE CHAR_LENGTH(nickname) > 30;
```

```sql
SELECT COUNT(*) AS null_count
FROM players
WHERE last_login_at IS NULL;
```

- 자료형 변경은 SQL이 실행된다는 사실보다 기존 데이터가 새 정의를 모두 만족하는지 먼저 확인한다.

## `TRUNCATE TABLE`

```sql
TRUNCATE TABLE player_items;
```

- `TRUNCATE`는 모든 행을 제거하지만 DML인 `DELETE`가 아니라 DDL로 분류된다.

| 항목               | `DELETE`                 | `TRUNCATE TABLE`                     |
| ------------------ | ------------------------ | ------------------------------------ |
| 분류               | DML                      | DDL                                  |
| 범위               | `WHERE`로 일부 또는 전체 | 항상 전체                            |
| 동작               | 조건에 맞는 행 삭제      | 테이블을 비우는 방식으로 처리        |
| 사용자 롤백        | 트랜잭션 안에서 가능     | 암묵적 커밋으로 불가                 |
| `AUTO_INCREMENT`   | 일반적으로 현재 값 유지  | 시작값으로 초기화                    |
| `ON DELETE` 트리거 | 실행                     | 실행하지 않는다                      |
| 삭제 행 수         | 영향 행 수 확인          | 의미 있는 삭제 행 수를 반환하지 않음 |

### 외래키 주의

- 다른 InnoDB 테이블의 외래키가 대상 테이블을 참조하면 `TRUNCATE`가 실패할 수 있다.

```sql
TRUNCATE TABLE players;
```

- 외래키 검사를 무조건 꺼서 우회하기보다 다음을 먼저 설계한다.

- 자식 데이터와 부모 데이터의 초기화 순서

- 재생성할 기준 데이터

- 실패 시 복구 절차

> `TRUNCATE`가 장애 도중 원자적으로 처리될 수 있다는 것과 사용자가 실행 후 `ROLLBACK`할 수 있다는 것은 다른 의미다.

## `DROP`

### 테이블 삭제

```sql
DROP TABLE players;
```

### 존재할 때만 삭제

```sql
DROP TABLE IF EXISTS players;
```

### 데이터베이스 삭제

```sql
DROP DATABASE game_db;
```

- `DROP`은 데이터뿐만 아니라 열 정의, 제약조건, 인덱스 같은 구조까지 삭제한다.
- 사용자 트랜잭션의 `ROLLBACK`으로 되돌릴 수 없다.
- 필요하면 백업이나 시점 복구 체계로 복원한다.
- 외래키 관계가 있으면 일반적으로 자식 테이블을 먼저 삭제한다.

```sql
DROP TABLE IF EXISTS player_items;
DROP TABLE IF EXISTS purchase_requests;
DROP TABLE IF EXISTS players;
DROP TABLE IF EXISTS items;
DROP TABLE IF EXISTS guilds;
```

- `IF EXISTS`는 재실행 편의성을 높이지만 예상과 다른 환경에서 대상이 없다는 사실을 숨길 수 있다.

## Node.js, DDL 실행

- DDL을 앱에서 시작할 때마다 무조건 실행하기보다 버전이 기록되는 마이그레이션 도구를 사용하는 것이 안전
- 직접 실행해야 한다면 대상 구조를 확인하고 오류를 숨기지 않는다.

```js
async function addDisplayNameColumn(pool) {
  const connection = await pool.getConnection();

  try {
    const [rows] = await connection.execute(
      `SELECT COUNT(*) AS column_count
       FROM information_schema.columns
       WHERE table_schema = DATABASE()
         AND table_name = 'players'
         AND column_name = 'display_name'`,
    );

    if (Number(rows[0].column_count) > 0) {
      console.log("display_name 열이 이미 존재한다.");
      return;
    }

    await connection.query(
      `ALTER TABLE players
       ADD COLUMN display_name VARCHAR(50) NULL,
       ALGORITHM = INSTANT`,
    );

    console.log("display_name 열을 추가했다.");
  } finally {
    connection.release();
  }
}
```

### 주의점

- DDL을 일반 DML 트랜잭션으로 감싸 롤백할 수 있다고 생각하지 않음
- 오류를 `.catch(() => {})`로 무시하지 않음
- 여러 서버 인스턴스가 동시에 같은 마이그레이션을 실행하지 않게 한다.
- 마이그레이션 버전, 적용 시간, 성공 여부를 기록
- 적용 전후 `SHOW CREATE TABLE` 결과를 확인

## MongoDB 구조 다루기

- MongoDB는 문서 구조가 유연하며 관계형 데이터베이스의 DDL과 정확히 일치하는 명령 체계가 없다.
- 컬렉션, Validator, 인덱스, 기존 문서 이행을 나누어 생각한다.

### 컬렉션과 Validator 생성

```js
await db.createCollection("players", {
  validator: {
    $jsonSchema: {
      bsonType: "object",

      required: ["nickname", "email", "level"],

      properties: {
        nickname: {
          bsonType: "string",
          minLength: 1,
          maxLength: 50,
        },

        email: {
          bsonType: "string",
        },

        level: {
          bsonType: "int",
          minimum: 1,
        },

        guildId: {
          bsonType: ["objectId", "null"],
        },
      },
    },
  },

  validationLevel: "strict",
  validationAction: "error",
});

await db.collection("players").createIndex({ email: 1 }, { unique: true });
```

- 문서를 처음 저장할 때 컬렉션이 자동 생성될 수 있지만 Validator나 Collation 같은 옵션이 필요하면 명시적으로 만드는 편이 명확하다.

### Validator 변경

```js
await db.command({
  collMod: "players",

  validator: {
    $jsonSchema: {
      bsonType: "object",

      required: ["nickname", "email", "level", "vipGrade"],

      properties: {
        nickname: {
          bsonType: "string",
          maxLength: 50,
        },

        email: {
          bsonType: "string",
        },

        level: {
          bsonType: "int",
          minimum: 1,
        },

        vipGrade: {
          bsonType: "int",
          minimum: 0,
          maximum: 5,
        },
      },
    },
  },

  validationLevel: "strict",
  validationAction: "error",
});
```

- Validator 변경은 기존 문서를 즉시 모두 고쳐주지 않는다.
- 기존 문서는 별도로 검사, 이행하고 이후 `Insert`, `Update`에 새 규칙이 어떻게 적용되는지 확인한다.

## MongoDB 필드 마이그레이션

### 기본값 성격 필드 추가

```js
await db.collection("players").updateMany(
  {
    displayName: {
      $exists: false,
    },
  },
  [
    {
      $set: {
        displayName: "$nickname",
      },
    },
  ],
);
```

### 필드 이름 변경

```js
await db.collection("players").updateMany(
  {
    nicknameColor: {
      $exists: true,
    },
  },
  {
    $rename: {
      nicknameColor: "nameColor",
    },
  },
);
```

### 필드 제거

```js
await db.collection("players").updateMany(
  {
    legacyField: {
      $exists: true,
    },
  },
  {
    $unset: {
      legacyField: "",
    },
  },
);
```

### 자료형 변경 전 잘못된 데이터 찾기

```js
db.players.find({
  $expr: {
    $ne: [
      {
        $type: "$level",
      },
      "int",
    ],
  },
});
```

- 데이터를 정리한 후 Validator를 강화한다.
- 필드 마이그레이션도 MySQL과 마찬가지로 다음 순서로 진행하는 것이 안전하다.

```text
추가
→ 이중 읽기/쓰기
→ 기존 문서 이행
→ 검증
→ 이전 필드 제거
```

## MongoDB 컬렉션 초기화, 삭제

- MongoDB에는 MySQL `TRUNCATE TABLE`과 정확히 같은 명령은 없다.

### 문서만 모두 삭제

```js
await db.collection("players").deleteMany({});
```

- 컬렉션은 유지
- 인덱스와 Validator도 유지
- 문서 단위 삭제 작업

### 컬렉션 자체 삭제

```js
await db.collection("players").drop();
```

- 문서와 컬렉션이 삭제
- 인덱스와 Validator도 함께 사라짐
- 다시 만들 때 컬렉션 옵션, Validator, 인덱스를 모두 재적용

두 작업은 같지 않다.

```js
await db.collection("players").deleteMany({});

await db.collection("players").drop();
```

- Drop 후 재생성을 MongoDB의 `TRUNCATE`라고 표현하는 것은 비슷한 결과를 만드는 비유일 뿐 완전히 같은 명령으로 이해하면 안 된다.

## 운영 DDL 실행 절차

### 실행 전

1. 대상 환경, 데이터베이스, 테이블 이름을 확인
2. 현재 `SHOW CREATE TABLE`을 보관
3. 테이블 크기와 행 수를 확인
4. 장기 트랜잭션과 Metadata Lock 대기를 확인
5. DDL이 사용할 알고리즘과 잠금 수준을 확인
6. 중복, `NULL`, 범위 초과 등 새 제약조건을 위반할 데이터를 검사
7. 필요한 추가 디스크 공간과 복제 지연을 예상
8. 백업과 복구 절차가 실제로 동작하는지 확인
9. 구버전, 신버전 애플리케이션 호환성 확인

### 실행 중

1. 실행 시작 시간, 담당자 기록
2. DB 연결 수, 잠금 대기, 디스크 I/O를 관찰
3. Replica Lag과 애플리케이션 오류율 관찰
4. 예상 시간을 크게 초과하면 중단 가능 여부와 영향을 먼저 확인

### 실행 후

1. `SHOW CREATE TABLE`로 최종 구조를 검증
2. 인덱스와 제약조건을 확인
3. 주요 조회와 쓰기 기능을 점검
4. 데이터 누락, 중복, 불일치를 검사
5. 배포 이력과 결과를 기록

## DDL을 막는 운영

- 애플리케이션 계정에 불필요한 `DROP`, `ALTER` 권한을 주지 않음
- 운영 DB에 직접 접속하는 기본 계정은 가능한 한 읽기 전용으로 사용
- DDL은 검토 가능한 마이그레이션 파일로 관리
- 로컬, 개발, QA, 운영 설정을 명확히 분리
- 파괴적 문장에서는 대상 DB, 테이블을 확인하는 보호 절차 사용
- 백업이 있다는 사실뿐 아니라 복원 시간과 복원 성공 여부도 확인
- `DROP`, `TRUNCATE`는 실행 후 SQL `ROLLBACK`으로 복구할 수 없다는 전제로 승인
- 한 번의 큰 변경보다 호환 가능한 여러 단계의 변경을 선호

## MySQL, MongoDB

| 작업              | MySQL                             | MongoDB                                 |
| ----------------- | --------------------------------- | --------------------------------------- |
| 구조 생성         | `CREATE DATABASE`, `CREATE TABLE` | `createCollection`, Validator, 인덱스   |
| 열, 필드 추가     | `ALTER TABLE ... ADD COLUMN`      | 새 필드 저장, 기존 문서는 `$set` 이행   |
| 자료형, 제약 변경 | `MODIFY COLUMN`, 제약조건 변경    | 데이터 이행 후 `collMod` Validator 변경 |
| 이름 변경         | `RENAME COLUMN`, `RENAME TABLE`   | `$rename`, 컬렉션 이름 변경 명령        |
| 열, 필드 삭제     | `DROP COLUMN`                     | `$unset`                                |
| 모든 데이터 제거  | `TRUNCATE TABLE` 또는 `DELETE`    | `deleteMany({})` 또는 Drop 후 재생성    |
| 구조 삭제         | `DROP TABLE`                      | `collection.drop()`                     |
| 참조 무결성       | 외래키로 DB가 강제                | 애플리케이션 관리                       |

- MongoDB의 유연한 스키마는 스키마가 없다는 뜻이 아니다.
- 구조 규칙과 이행 책임이 데이터베이스와 애플리케이션 사이에 다르게 배분된다는 의미다.

## 정리

- DDL은 데이터베이스, 테이블, 열, 제약조건, 인덱스 같은 구조를 다룬다.
- MySQL의 많은 DDL은 암묵적 커밋을 발생시키므로 DML과 같은 사용자 트랜잭션으로 되돌릴 수 있다고 생각하면 안 된다.
- MySQL 8 InnoDB의 원자적 DDL은 장애 중 일관성을 높이는 기능이며 사용자 `ROLLBACK`과는 다르다.
- `IF NOT EXISTS`는 기존 구조가 원하는 정의와 같은지 보장하지 않는다.
- `ALTER TABLE` 전에는 현재 구조, 기존 데이터, 실행 알고리즘, 잠금과 추가 공간을 확인한다.
- 운영 스키마 변경은 Expand-Migrate-Contract 순서로 호환성을 유지하는 것이 안전하다.
- `TRUNCATE`는 DDL이고 `WHERE`를 사용할 수 없으며, 암묵적 커밋과 `AUTO_INCREMENT` 초기화가 발생한다.
- `DROP`은 데이터와 구조를 함께 제거하며 백업, 시점 복구 없이는 되돌릴 수 없다.
- MongoDB에서는 컬렉션, Validator, 인덱스, 기존 문서 이행을 각각 관리한다.
- 마이그레이션 오류를 숨기지 말고 적용 이력과 검증 결과를 남긴다.
