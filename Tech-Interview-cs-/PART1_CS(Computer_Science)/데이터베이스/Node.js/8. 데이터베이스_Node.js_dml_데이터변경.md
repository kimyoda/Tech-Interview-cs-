# DML, 데이터 변경

## DML이란?

DML(Data Manipulation Language)은 테이블의 데이터를 조회, 변경하는 명령 집합

| 명령     | 역할         |
| -------- | ------------ |
| `SELECT` | 데이터 조회  |
| `INSERT` | 새 행 입력   |
| `UPDATE` | 기존 행 수정 |
| `DELETE` | 기존 행 삭제 |

## `INSERT` 새 데이터 입력

### 단일 행 입력

```sql
INSERT INTO players
  (nickname, level, guild_id, vip_grade, email, last_login_at)
VALUES
  ('Arin', 25, 3, 1, 'arin@example.com', '2026-09-02');
```

### 다중 행 입력

```sql
INSERT INTO items (name, item_type)
VALUES
  ('Iron Sword', 'weapon'),
  ('Wooden Shield', 'armor'),
  ('Health Potion', 'consumable');
```

- 여러 행을 한 문장으로 입력, 네트워크 왕복과 문장 실행 비용을 줄일 수 있다. 매우 큰 입력은 패킷 크기, 잠금 시간, 장애 시 재처리 단위를 고려해 적절한 배치로 나눈다

### 조회 결과 입력: `INSERT ... SELECT`

```sql
CREATE TABLE high_level_players (
  player_id BIGINT UNSIGNED PRIMARY KEY,
  snapshot_level INT UNSIGNED NOT NULL,
  captured_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO high_level_players (player_id, snapshot_level)
SELECT id, level
FROM players
WHERE level >= 40;
```

### 중복 키 처리: Upsert

`(player_id, item_id)` 복합 기본키가 이미 존재하면 수량을 1 증가

```sql
INSERT INTO player_items (player_id, item_id, quantity)
VALUES (1, 1, 1)
ON DUPLICATE KEY UPDATE
  quantity = quantity + 1;
```

Upsert는 편리하나 어떤 고유키 충돌을 의도한 것인지 명확해야 한다. 여러 `UNIQUE` 제약이 있는 테이블에서 예상하지 못한 충돌이 갱신으로 처리되지 않도록 설계 확인한다

## `UPDATE`: 기존 데이터 수정

### 조건에 맞는 행 수정

```sql
UPDATE players
SET vip_grade = 2
WHERE id = 10;
```

`WHERE`를 생략하면 모든 행이 수정된다. 실행 전 같은 조건의 `SELECT`로 대상을 확인하는 습관이 안전

```sql
SELECT id, nickname, vip_grade
FROM players
WHERE id = 10;
```

### 현재 값을 기준으로 원자적 증가

```sql
UPDATE player_items
SET quantity = quantity + 1
WHERE player_id = 1
  AND item_id = 1;
```

- 먼저 수량을 읽고 다시 저장하는 방식보다, 데이터베이스 안에서 한 문장으로 증가시키는 방식이 동시 갱신 손실을 줄이는 데 유리

### `CASE`를 사용한 일괄 수정

```sql
UPDATE players
SET vip_grade = CASE
  WHEN level >= 50 THEN 5
  WHEN level >= 40 THEN 4
  WHEN level >= 30 THEN 3
  ELSE vip_grade
END;
```

- 모든 행을 대상으로 하는 의도적인 수정, 운영에서 영향 행 수, 롤백 방법을 먼저 확인

### 조인을 사용한 수정

```sql
UPDATE players AS p
JOIN guilds AS g ON g.id = p.guild_id
SET p.vip_grade = p.vip_grade + 1
WHERE g.name = 'Knights'
  AND p.vip_grade < 5;
```

- 조인으로 수정 대상을 정할 때 조인으로 행이 중복되지 않는지, 변경 범위가 예상과 같은지 먼저 `SELECT`로 검증한다

## 동시성 제어와 낙관적 잠금

- 수정 충돌을 감지하기 위해 버전 열을 사용할 수 있다

```sql
ALTER TABLE players
ADD COLUMN version INT UNSIGNED NOT NULL DEFAULT 0;
```

```sql
UPDATE players
SET
  level = 43,
  version = version + 1
WHERE id = 1
  AND version = 0;
```

- 영향받은 행이 0개면 트랜잭션이 먼저 수정했거나 대상이 존재하지 않는 상황일 수 있다. 앱에서 현재 상태를 다시 읽고 충돌 처리 정책을 적용

## `DELETE` 행 삭제

### 조건 삭제

```sql
DELETE FROM player_items
WHERE player_id = 1
  AND item_id = 3;
```

### 조인을 이용한 삭제

```sql
DELETE pi
FROM player_items AS pi
JOIN items AS i ON i.id = pi.item_id
WHERE i.item_type = 'consumable'
  AND pi.quantity = 0;
```

`DELETE`도 `WHERE`를 생략하면 모든 행을 삭제한다

```sql
-- 모든 행 삭제: 실행 전 반드시 확인
DELETE FROM player_items;
```

## `DELETE`, `TRUNCATE`, `DROP` 비교

| 명령             | 삭제 대상 | 조건 지정 | 테이블 구조 | 대표 용도                 |
| ---------------- | --------- | --------: | ----------- | ------------------------- |
| `DELETE`         | 선택한 행 |      가능 | 유지        | 업무 조건에 따른 행 삭제  |
| `TRUNCATE TABLE` | 모든 행   |      불가 | 유지        | 테이블 전체 데이터 초기화 |
| `DROP TABLE`     | 테이블    |      불가 | 삭제        | 테이블 자체 제거          |

- 트랜잭션 처리와 자동 증가 값 초기화 여부 등 세부 동작은 DBMS에 따라 다르다. `TRUNCATE`를 단순히 빠른 `DELETE`로만 이해하면 안 된다

## 트랜잭션

- 트랜잭션(Transaction)은 하나의 논리적 작업 단위. 여러 변경이 모두 성공하거나 모두 취소되어야 할 때 사용

```sql
START TRANSACTION;

UPDATE player_items
SET quantity = quantity - 1
WHERE player_id = 1
  AND item_id = 1
  AND quantity >= 1;

UPDATE players
SET level = level + 1
WHERE id = 1;

COMMIT;
```

중간에 문제가 발생하면 다음을 실행

```sql
ROLLBACK;
```

### ACID

| 속성                | 의미                                                 |
| ------------------- | ---------------------------------------------------- |
| 원자성(Atomicity)   | 작업이 전부 반영되거나 전부 취소된다                 |
| 일관성(Consistency) | 트랜잭션 전후에 데이터 규칙이 유지된다               |
| 격리성(Isolation)   | 동시에 실행되는 작업이 서로 간섭하지 않도록 제어한다 |
| 지속성(Durability)  | 커밋된 결과는 장애 후에도 보존된다                   |

- 트랜잭션은 가능한 짧게 유지한다. 사용자 입력이나 외부 API 응답을 기다리는 동안 트랜잭션을 열어 잠금과 자원 점유가 길어질 수 있다

## Node.js 트랜잭션 처리

```js
const connection = await pool.getConnection();

try {
  await connection.beginTransaction();

  const [itemResult] = await connection.execute(
    `UPDATE player_items
     SET quantity = quantity - 1
     WHERE player_id = ?
       AND item_id = ?
       AND quantity >= 1`,
    [playerId, itemId],
  );

  if (itemResult.affectedRows !== 1) {
    throw new Error("아이템이 없거나 수량이 부족하다.");
  }

  await connection.execute(
    `UPDATE players
     SET level = level + 1
     WHERE id = ?`,
    [playerId],
  );

  await connection.commit();
} catch (error) {
  await connection.rollback();
  throw error;
} finally {
  connection.release();
}
```

- 트랜잭션 안의 모든 문장은 같은 커넥션에서 실행한다. 변경 후에는 `affectedRows`를 확인해 실제로 원하는 행이 처리되었는지 검증한다

## 소프트 삭제

- 이력 보존과 복구가 필요하면 실제 행을 지우는 대신 삭제 시각을 기록한다

```sql
ALTER TABLE players
ADD COLUMN deleted_at DATETIME NULL;
```

```sql
-- 소프트 삭제
UPDATE players
SET deleted_at = NOW()
WHERE id = 10
  AND deleted_at IS NULL;
```

```sql
-- 활성 데이터 조회
SELECT id, nickname, level
FROM players
WHERE deleted_at IS NULL;
```

```sql
-- 복구
UPDATE players
SET deleted_at = NULL
WHERE id = 10;
```

- 소프트 삭제에 다음 추가 설계가 필요

- 모든 기본 조회에서 삭제 행을 제외하는 규칙

- 고유값 재사용 정책

- 연관 데이터의 처리 방식

- 보관 기간과 최종 물리 삭제 정책

- 삭제 행까지 포함하는 관리자 조회 권한

## SQL Injection 방지

- 사용자 입력을 SQL 문자열에 직접 연결하지 않는다

```js
// 잘못된 예
const sql = `UPDATE players SET nickname = '${nickname}' WHERE id = ${id}`;
```

- 바인딩 변수를 사용한다

```js
const [result] = await connection.execute(
  `UPDATE players
   SET nickname = ?
   WHERE id = ?`,
  [nickname, id],
);

if (result.affectedRows !== 1) {
  throw new Error("수정할 플레이어를 찾지 못했다.");
}
```

- 테이블명, 열 이름, 정렬 방향처럼 SQL 구조에 해당하는 값은 일반 바인딩 변수로 처리하지 못하여 서버에서 정의한 허용 목록으로 제한

## MongoDB 데이터 변경

### 입력

```js
await db.collection("players").insertOne({
  nickname: "Arin",
  level: 25,
  guildId: guildId,
  vipGrade: 1,
  email: "arin@example.com",
  lastLoginAt: new Date("2026-09-02T00:00:00Z"),
  createdAt: new Date(),
  deletedAt: null,
});
```

### 수정과 원자적 증가

```js
const result = await db.collection("players").updateOne(
  { _id: playerId, deletedAt: null },
  {
    $set: { nickname: "Arin2" },
    $inc: { level: 1 },
  },
);
```

### Upsert

```js
await db.collection("playerItems").updateOne(
  { playerId, itemId },
  {
    $inc: { quantity: 1 },
    $setOnInsert: { acquiredAt: new Date() },
  },
  { upsert: true },
);
```

### 소프트 삭제와 물리 삭제

```js
await db
  .collection("players")
  .updateOne(
    { _id: playerId, deletedAt: null },
    { $set: { deletedAt: new Date() } },
  );

await db.collection("players").deleteOne({ _id: playerId });
```

### 다중 작업

```js
await db.collection("players").bulkWrite([
  {
    updateOne: {
      filter: { _id: playerId1 },
      update: { $inc: { level: 1 } },
    },
  },
  {
    updateOne: {
      filter: { _id: playerId2 },
      update: { $set: { vipGrade: 3 } },
    },
  },
]);
```

- MongoDB 트랜잭션은 지원되는 배포 구조에서 세션을 통해 실행한다. 단일 문서 변경은 원자적, 데이터 모델을 설계할 때 함께 변경되는 값을 한 문서에 둘 수 있는지 고려한다

## 변경 작업 안전 점검

- 실행 대상 데이터베이스와 환경이 맞는지?
- 변경 전 동일한 `WHERE` 조건으로 `SELECT` 결과를 확인했는지?
- 예상 영향 행 수를 알고 있는지?
- 값은 바인딩 변수로 전달하는지
- 여러 문장이 하나의 작업이면 트랜잭션이 필요한지
- 실패 시 `ROLLBACK` 또는 복구 방법이 있는지?
- 변경 후 `affectedRows`와 결과 데이터를 검증하는지?
- 대량 변경이면 배치 크기, 잠금, 로그, 복제 지연을 고려했는지?

## 핵심 정리

- `INSERT`, `UPDATE`, `DELETE`는 데이터 자체를 변경하는 DML이다
- 다중 입력과 Upsert는 편리하나 배치 크기와 고유키 충돌 의미를 확인
- `UPDATE`, `DELETE` 전에는 같은 조건의 `SELECT`로 대상을 검증한다
- 여러 변경의 원자성이 필요하면 같은 커넥션에서 트랜잭션을 사용
- 소프트 삭제는 복구와 이력에 유리, 조회, 고유값, 보관 정책이 추가로 필요하다
- 앱에서 바인딩 변수와 영향 행 수 검증을 사용
- MongoDB에서 `$set`, `$inc`, `upsert`, `bulkWrite`로 데이터 변경을 표현

## 복습 문제

1. 다중 행 `INSERT`의 장점과 주의점을 설명
2. 아이템 수량을 1 증가시키는 원자적 `UPDATE`를 작성
3. `UPDATE` 또는 `DELETE` 전에 같은 조건의 `SELECT`를 실행하는 이유
4. 트랜잭션의 ACID 속성을 설명
5. 소프트 삭제가 고유키 설계에 미치는 영향 설명
6. Node.js 트랜잭션에서 같은 커넥션을 사용해야 하는 이유
7. MongoDB에서 문서가 없으면 생성하고 있으면 수량을 증가시키는 Upsert를 작성
