## 데이터베이스

```sql
CREATE DATABASE game_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE game_db;
```

- `utf8mb4`: 한글과 이모지를 포함한 유니코드 문자를 저장할 수 있다
- Collation은 문자열의 비교, 정렬 규칙이다
- 운영 환경에서 이미 존재하는 데이터베이스를 실수로 바꾸지 않도록 접속 대상과 권한을 먼저 확인한다

## 자주 쓰는 MySQL 자료형

| 분류        | 자료형                          | 용도                            |
| ----------- | ------------------------------- | ------------------------------- |
| 정수        | `TINYINT`, `INT`, `BIGINT`      | 등급, 수량, 식별자              |
| 정확한 소수 | `DECIMAL(p, s)`                 | 금액, 정확한 비율               |
| 근사 소수   | `FLOAT`, `DOUBLE`               | 측정값, 과학 계산               |
| 문자열      | `CHAR`, `VARCHAR`, `TEXT`       | 코드, 이름, 긴 본문             |
| 날짜, 시간  | `DATE`, `DATETIME`, `TIMESTAMP` | 날짜, 접속 시각, 변경 시각      |
| 논리값      | `BOOLEAN`                       | MySQL에서 `TINYINT(1)`의 동의어 |
| JSON        | `JSON`                          | 구조가 유연한 부가 데이터       |

### 자료형 선택 원칙

- 값의 범위보다 지나치게 큰 자료형을 습관적으로 사용하지 않는다
- 금액처럼 오차가 허용되지 않는 값에는 `FLOAT`보다 `DECIMAL`을 사용한다
- 길이가 변하는 문자열에는 일반적으로 `VARCHAR`가 적합하다
- `DATE`는 날짜만, `DATETIME`은 날짜와 시간을 저장한다
- `TIMESTAMP`의 시간대 변환 특성은 서버와 세션 설정까지 함께 확인한다

## `players` 테이블

```sql
CREATE TABLE players (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nickname VARCHAR(50) NOT NULL,
  level INT UNSIGNED NOT NULL DEFAULT 1,
  guild VARCHAR(100) NULL,
  vip_grade TINYINT UNSIGNED NOT NULL DEFAULT 0,
  email VARCHAR(100) NOT NULL UNIQUE,
  last_login_at DATE NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT chk_players_level CHECK (level >= 1),
  CONSTRAINT chk_players_vip_grade CHECK (vip_grade BETWEEN 0 AND 5)
);
```

### 제약 조건

| 제약조건         | 역할                                 |
| ---------------- | ------------------------------------ |
| `PRIMARY KEY`    | 행을 유일하게 식별한다               |
| `AUTO_INCREMENT` | 새 행의 숫자 식별자를 자동 생성한다  |
| `NOT NULL`       | 값 누락을 허용하지 않는다            |
| `UNIQUE`         | 중복 값을 허용하지 않는다            |
| `DEFAULT`        | 값을 생략했을 때 기본값을 사용한다   |
| `CHECK`          | 지정한 조건을 만족하는 값만 허용한다 |

## 테이블 구조 변경

### 열 추가

```sql
ALTER TABLE players
ADD COLUMN bio VARCHAR(255) NULL;
```

### 열 자료형 변경

```sql
ALTER TABLE players
MODIFY COLUMN bio TEXT NULL;
```

### 열 삭제

```sql
ALTER TABLE players
DROP COLUMN bio;
```

`ALTER TABLE`은 변경 전에 백업, 실행 계획, 배포 절차를 확인해야 한다. `DROP`의 경우에는 개발이나 QA에서 사용되며, 실제 운영에서는 거의 사용되지 않는다. 대부분 `MODIFY` 등을 사용한다.

## 삭제 명령

| 명령             | 대상        | `WHERE` | 특징                                 |
| ---------------- | ----------- | ------: | ------------------------------------ |
| `DELETE`         | 행          |    가능 | 조건에 맞는 행을 삭제                |
| `TRUNCATE TABLE` | 모든 행     |  불가능 | 테이블 구조는 남기고 데이터를 비운다 |
| `DROP TABLE`     | 테이블 자체 |  불가능 | 구조와 데이터를 모두 제거한다        |

```sql
-- 실습 또는 개발 환경에서만 사용
TRUNCATE TABLE players;

DROP TABLE players;
```

> `TRUNCATE`, `DROP`을 운영 데이터베이스에서 사용한다면 대상과 백업 여부를 반드시 확인한다.

- 테이블 설계에서 값의 범위와 계산 목적에 맞는 자료형을 선택한다

## 복습

### 1. `INT`와 `BIGINT`를 선택할 때 고려할 점은?

**내 답변**

- 해당 값의 범위가 크다고 생각할 경우 `BIGINT`, `INT` 범위로 충분하다면 `INT`

`INT`와 `BIGINT`는 저장하려는 값의 **예상 범위**를 기준으로 선택한다.

- `INT` 범위로 충분하면 `INT`
- `INT` 범위를 넘어설 가능성이 있다면 `BIGINT`
- 필요 이상으로 큰 자료형을 습관적으로 사용하는 것은 피하는 것이 좋다

MySQL의 `UNSIGNED` 기준 범위는 다음과 같다.

| 자료형            |                           범위 |
| ----------------- | -----------------------------: |
| `INT UNSIGNED`    |              0 ~ 4,294,967,295 |
| `BIGINT UNSIGNED` | 0 ~ 18,446,744,073,709,551,615 |

**최종**

- 저장할 값의 최대 범위를 고려해서 선택한다.
- `INT` 범위로 충분하면 `INT`를 사용하고, 더 큰 값이 저장될 가능성이 있다면 `BIGINT`를 사용한다.
- 필요 이상으로 큰 자료형을 사용하는 것은 피하는 것이 좋다.

### 2. 금액 저장에 `DECIMAL`이 적합한 이유는?

- 표현과 소수점까지 표시하기에 적합해서

`DECIMAL`의 핵심은 단순히 소수점을 표현할 수 있다는 것이 아니다.

`FLOAT`, `DOUBLE`도 소수점을 표현할 수 있지만 **근사값**을 저장하기 때문에 계산 과정에서 미세한 오차가 발생할 수 있다.

금액처럼 정확한 값이 필요한 경우에는 `DECIMAL`이 적합하다.

```text
100.10
19.99
1500.50
```

**최종**

- `DECIMAL`은 소수 값을 정확하게 저장할 수 있기 때문에 금액처럼 오차가 허용되지 않는 데이터에 적합하다.
- `FLOAT`, `DOUBLE`은 근사값을 저장하기 때문에 계산 과정에서 미세한 오차가 발생할 수 있다.

### 3. `NOT NULL`, `UNIQUE`, `DEFAULT`의 역할을 설명하시오.

- `NOT NULL`은 해당 값이 누락되면 안 된다
- `UNIQUE`는 특별한 개체값
- `DEFAULT`는 반드시 필요한 객체

#### `NOT NULL`

해당 컬럼에 `NULL` 값이 저장되는 것을 허용하지 않는다.

```sql
nickname VARCHAR(50) NOT NULL
```

`nickname` 컬럼에는 `NULL`을 저장할 수 없다.

> `NULL`과 빈 문자열 `''`은 서로 다른 값이다.

#### `UNIQUE`

해당 컬럼 또는 컬럼 조합에 **중복된 값을 저장하지 못하도록 제한**한다.

```sql
email VARCHAR(100) NOT NULL UNIQUE
```

예를 들어 다음 이메일이 이미 저장되어 있다면

```text
neo@example.com
```

동일한 이메일을 다시 저장할 수 없다.

#### `DEFAULT`

`INSERT`할 때 해당 컬럼의 값을 생략하면 자동으로 사용할 **기본값**을 지정한다.

```sql
level INT UNSIGNED NOT NULL DEFAULT 1
```

`level` 값을 직접 전달하지 않으면 기본값인 `1`이 사용된다.

**최종**

- `NOT NULL`: 해당 컬럼에 `NULL` 값이 저장되는 것을 허용하지 않는다.
- `UNIQUE`: 해당 컬럼 또는 컬럼 조합에 중복 값이 저장되는 것을 막는다.
- `DEFAULT`: `INSERT`할 때 값을 생략한 경우 사용할 기본값을 지정한다.

### 4. `DELETE`, `TRUNCATE`, `DROP`의 차이는?

- `DELETE`는 해당 데이터 테이블을 그냥 지우는 것
- `TRUNCATE`는 해당 테이블 데이터 자체를 갈아끼우는 것
- `DROP`은 해당 값 자체를 날리는 것

세 명령의 가장 중요한 차이는 **무엇을 삭제하는지**이다.

| 명령             | 삭제 대상   | `WHERE`   | 테이블 구조 |
| ---------------- | ----------- | --------- | ----------- |
| `DELETE`         | 행(Row)     | 사용 가능 | 유지        |
| `TRUNCATE TABLE` | 모든 행     | 사용 불가 | 유지        |
| `DROP TABLE`     | 테이블 자체 | 사용 불가 | 삭제        |

#### `DELETE`

조건에 맞는 행을 삭제한다.

```sql
DELETE FROM players
WHERE id = 10;
```

특정 사용자 한 명만 삭제할 수 있다.

```sql
DELETE FROM players;
```

`WHERE` 없이 사용하면 모든 행이 삭제된다.

하지만 **테이블 구조는 그대로 남아 있다.**

#### `TRUNCATE TABLE`

테이블 안의 모든 데이터를 비운다.

```sql
TRUNCATE TABLE players;
```

테이블 구조는 그대로 유지된다.

```text
players 테이블
├─ 컬럼 구조 유지
├─ 인덱스 유지
├─ 제약조건 유지
└─ 데이터 전체 삭제
```

`WHERE` 조건을 사용할 수 없다.

MySQL에서는 일반적으로 `AUTO_INCREMENT` 값도 초기화된다.

#### `DROP TABLE`

테이블 자체를 삭제한다.

```sql
DROP TABLE players;
```

다음과 같은 테이블 관련 정보가 함께 제거된다.

```text
players 테이블
├─ 데이터
├─ 컬럼 구조
├─ 인덱스
└─ 제약조건
```

**최종**

- `DELETE`: 조건에 맞는 행을 삭제하며 테이블 구조는 유지한다.
- `TRUNCATE`: 테이블의 모든 행을 제거하지만 테이블 구조는 유지한다.
- `DROP`: 데이터뿐 아니라 테이블 구조 자체를 삭제한다.

### 5. `INSERT`에서 열 이름을 명시하는 것이 안전한 이유는?

- 명확하게 표현해서

다음처럼 컬럼을 명시하지 않으면

```sql
INSERT INTO players
VALUES (...);
```

테이블의 컬럼 순서에 의존하게 된다.

반면 컬럼을 명시하면

```sql
INSERT INTO players
  (nickname, level, email)
VALUES
  ('Neo', 10, 'neo@example.com');
```

어떤 값이 어떤 컬럼에 저장되는지 명확하게 확인할 수 있다.

또한 테이블에 새로운 컬럼이 추가되거나 구조가 변경되었을 때 발생할 수 있는 실수를 줄일 수 있다.

**최종**

- 어떤 값이 어떤 컬럼에 저장되는지 명확하게 알 수 있다.
- 테이블에 컬럼이 추가되거나 컬럼 순서가 변경되더라도 실수할 가능성을 줄일 수 있다.
- 따라서 `INSERT`에서는 가능한 한 컬럼 목록을 명시하는 것이 좋다.

### 6. MongoDB에서 이메일 중복을 막기 위해서는?

- `unique`를 설정한다.

정확하게 표현하면 `email` 필드에 **Unique Index**를 생성한다.

```js
db.players.createIndex({ email: 1 }, { unique: true });
```

이렇게 설정하면 동일한 `email` 값이 중복으로 저장되는 것을 MongoDB가 막는다.

**최종**

- `email` 필드에 `unique: true` 옵션을 가진 고유 인덱스(Unique Index)를 생성한다.
