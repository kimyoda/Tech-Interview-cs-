````markdown
# ERD, 데이터베이스 관계 설계

## ERD란

ERD(Entity Relationship Diagram)는 데이터베이스의 구조를 엔티티(Entity), 속성(Attribute), 관계(Relationship)으로 표현한 설계도다.

| 개념   | 설명                   | 예시                     |
| ------ | ---------------------- | ------------------------ |
| 엔티티 | 독립적으로 관리할 대상 | 플레이어, 길드, 아이템   |
| 속성   | 대상이 가진 특성       | 닉네임, 레벨, 길드명     |
| 식별자 | 각 대상을 구분하는 값  | `players.id`             |
| 관계   | 엔티티 사이의 연관     | 플레이어가 길드에 소속됨 |

좋은 ERD는 단순한 그림이 아닌 제약조건, 삭제 정책, 조회 패턴을 설명한다.

## 기본키, 외래키

```sql
CREATE TABLE guilds (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50) NOT NULL UNIQUE,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```
````

```sql
CREATE TABLE players (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nickname VARCHAR(50) NOT NULL,
  level INT UNSIGNED NOT NULL DEFAULT 1,
  guild_id BIGINT UNSIGNED NULL,
  email VARCHAR(100) NOT NULL UNIQUE,

  CONSTRAINT fk_players_guild
    FOREIGN KEY (guild_id) REFERENCES guilds(id)
);
```

- `guilds.id`: 길드를 식별하는 기본키

- `players.guild_id`: 길드를 참조하는 외래키

- 외래키의 자료형과 부호 속성은 참조 대상 키와 맞추는 것이 중요하다.

## 카디널리티, 선택성

| 관계 | 의미                                  | 예시                   |
| ---- | ------------------------------------- | ---------------------- |
| 1:1  | 한 행이 상대 테이블 최대 한 행과 연결 | 플레이어와 상세 프로필 |
| 1:N  | 한 행이 상대 테이블 여러 행과 연결    | 길드와 플레이어        |
| N:M  | 양쪽 모두 여러 행과 연결              | 플레이어와 아이템      |

관계에는 필수 여부도 포함한다.

- `1`: 반드시 하나

- `0..1`: 없거나 하나

- `0..N`: 없거나 여러 개

- `1..N`: 하나 이상

길드가 없는 플레이어를 허용하면 `players.guild_id`는 `NULL`이 가능하고, 길드 입장에서 플레이어가 0명일 수도 있다.

## 1:1 관계 구현

플레이어마다 상세 프로필이 최대 하나만 존재하도록 만들 수 있다.

```sql
CREATE TABLE player_profiles (
  player_id BIGINT UNSIGNED PRIMARY KEY,
  bio TEXT NULL,
  avatar_url VARCHAR(255) NULL,
  birth_date DATE NULL,

  CONSTRAINT fk_profiles_player
    FOREIGN KEY (player_id) REFERENCES players(id)
    ON DELETE CASCADE
);
```

`player_profiles.player_id`가 기본키이자 외래키이므로 한 플레이어에 프로필 행이 둘 이상 저장될 수 없다.

이 구조가 자동으로 '모든 플레이어는 반드시 프로필을 가진다'를 보장하진 않는다. 실제 관계는 플레이어 관점에서 `0..1`일 수 있다.

## 1:N 관계와 정규화

별도 테이블로 분리한다.

- 같은 길드 이름이 여러 행에 반복

- 이름 변경 시 여러 행을 수정

- 오타 때문에 같은 길드가 다른 값처럼 저장될 수 있다

### 길드 테이블, 데이터 생성

```sql
CREATE TABLE guilds (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50) NOT NULL UNIQUE
);

INSERT INTO guilds (name)
SELECT DISTINCT guild
FROM players
WHERE guild IS NOT NULL;
```

### 외래키 열 추가 및 데이터 이동

```sql
ALTER TABLE players
ADD COLUMN guild_id BIGINT UNSIGNED NULL;

UPDATE players AS p
JOIN guilds AS g ON g.name = p.guild
SET p.guild_id = g.id;
```

### 검증 후 외래키 적용

```sql
SELECT id, nickname, guild, guild_id
FROM players
ORDER BY id;

ALTER TABLE players
ADD CONSTRAINT fk_players_guild
  FOREIGN KEY (guild_id) REFERENCES guilds(id)
  ON DELETE SET NULL;
```

검증이 끝나면 중복 문자열 열을 제거할 수 있다.

```sql
ALTER TABLE players
DROP COLUMN guild;
```

운영 마이그레이션에서는 스키마 변경, 데이터 이행, 구·신 코드 호환, 검증, 롤백 절차를 단계적으로 준비한다.

## N:M 관계와 연결 테이블

플레이어는 여러 아이템을 가질 수 있고, 같은 아이템을 여러 플레이어가 가질 수 있다.

```sql
CREATE TABLE items (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE,
  item_type VARCHAR(30) NOT NULL
);

CREATE TABLE player_items (
  player_id BIGINT UNSIGNED NOT NULL,
  item_id BIGINT UNSIGNED NOT NULL,
  quantity INT UNSIGNED NOT NULL DEFAULT 1,

  PRIMARY KEY (player_id, item_id),

  CONSTRAINT fk_player_items_player
    FOREIGN KEY (player_id) REFERENCES players(id)
    ON DELETE CASCADE,

  CONSTRAINT fk_player_items_item
    FOREIGN KEY (item_id) REFERENCES items(id)
    ON DELETE RESTRICT,

  CONSTRAINT chk_player_items_quantity CHECK (quantity > 0)
);
```

`player_items`는 연결 테이블이고 다음 역할을 한다.

- N:M 관계를 두 개의 1:N 관계로 바꾼다.

- `quantity`, `acquired_at`처럼 관계 자체의 속성을 저장한다.

- 복합 기본키로 같은 플레이어, 아이템 조합의 중복을 막는다.

## 삭제, 수정 정책

| 정책        | 동작                             | 사용 예                                 |
| ----------- | -------------------------------- | --------------------------------------- |
| `RESTRICT`  | 참조 행이 있으면 삭제, 수정 거부 | 사용 중인 아이템 원본 삭제 방지         |
| `CASCADE`   | 부모 변경, 삭제를 자식에 전파    | 플레이어 삭제 시 보유 관계 삭제         |
| `SET NULL`  | 외래키를 `NULL`로 변경           | 길드 삭제 시 무소속 처리                |
| `NO ACTION` | DBMS 기준에 따라 검사            | MySQL InnoDB에서 보통 `RESTRICT`와 유사 |

삭제 정책은 편의성보다 업무 규칙을 기준으로 한다.

## 정규화 핵심

### 제1정규형(1NF)

각 열은 원자값을 가져야 한다. `items = '검, 방패, 물약'`처럼 여러 값을 한 문자열에 넣지 않는다.

### 제2정규형(2NF)

복합키를 사용할 때 일반 열이 키의 일부가 아닌 전체 키에 종속되어야 한다.

### 제3정규형(3NF)

일반 열이 다른 일반 열을 통해 간접적으로 기본키에 종속되는 구조를 줄인다.

정규화는 중복과 갱신 이상을 줄이고, 읽기 성능이나 분석 편의를 위해 검증된 비정규화를 선택하는 경우도 있다.

## 인덱스 설계 기초

MySQL은 외래키 검사를 위해 관련 인덱스를 요구하고, 조회 패턴에 따라 복합 인덱스도 검토한다.

```sql
CREATE INDEX idx_players_guild_level
ON players (guild_id, level);
```

해당 인덱스는 다음처럼 `guild_id`를 먼저 조건으로 사용하고, `level`을 함께 활용하는 조회에 적합할 수 있다.

```sql
SELECT id, nickname, level
FROM players
WHERE guild_id = 1
ORDER BY level DESC;
```

인덱스는 읽기를 빠르게 할 수 있으나 저장 공간과 쓰기 비용을 늘린다. 실제 쿼리와 `EXPLAIN` 결과를 기준으로 설계한다.

## MongoDB 포함, 참조

### 포함(Embedding)

```js
{
  _id: ObjectId("..."),
  nickname: "Neo",
  profile: {
    bio: "탱커 플레이어",
    avatarUrl: "/avatars/neo.png"
  }
}
```

문서와 함께 자주 읽고 크기가 제한적인 데이터에 적합하다.

### 참조(Referencing)

```js
{
  _id: ObjectId("..."),
  nickname: "Neo",
  guildId: ObjectId("...")
}
```

독립적으로 변경되거나 여러 문서가 공유하는 데이터에 적합하다. 필요하면 `$lookup`으로 결합한다.

MongoDB 설계는 관계형 정규화 규칙을 그대로 적용하기보다 읽기, 쓰기 패턴, 문서 크기, 원자적 변경 범위를 함께 고려한다.

## 설계 점검

- 각 테이블의 기본키가 명확한가

- 자연키에 필요한 `UNIQUE` 제약이 있는지

- 외래키의 자료형이 참조 키와 일치하는지

- 관계의 카디널리티와 선택성이 실제 업무 규칙과 맞는지

- 삭제 시 `CASCADE`, `SET NULL`, `RESTRICT` 중 어떤 동작이 필요한지

- N:M 관계에 연결 테이블과 관계 속성이 올바르게 배치되었는지

- 자주 사용하는 조회를 지원하는 인덱스가 있는지

## 정리

- ERD는 엔티티, 속성, 식별자, 관계를 표현하는 데이터 설계도

- 1:N 관계에서는 보통 N 쪽 테이블에 외래키를 둔다

- N:M 관계는 연결 테이블로 구현

- `UNIQUE`, 외래키, 삭제 정책은 업무 규칙을 데이터베이스에서 보장

- 정규화는 중복과 삽입, 수정, 삭제 이상을 줄인다

- MongoDB에서는 포함과 참조 중 조회, 변경 패턴에 맞는 방식을 선택

## 복습

1. 기본키와 외래키 역할

- 기본키: 식별하는 값, 외래키: 참조하는 값

  -> 기본키(Primary Key): 테이블의 각 행을 고유하게 식별하는 값

  -> 외래키(Foreign Key): 다른 테이블의 기본키 또는 `UNIQUE` 키를 참조하여 테이블 사이의 관계를 표현하는 값

- 위의 예시를 보면 `guilds.id`는 길드를 구분하는 기본키, `players.id`는 플레이어를 구분하는 기본키, `players.guild_id`가 플레이어가 어떤 길드에 소속되어 있는지 나타내는 외래키

- 즉 기본키는 자기 테이블의 행을 식별하고, 외래키는 다른 테이블의 행을 참조하여 관계를 만든다

2. 플레이어와 길드가 1:N 관계일 때 외래키는 어느 테이블에 두는지

- player.guilds에 둔다

  -> N 쪽인 `players` 테이블에 `guild_id` 외래키를 둔다

  -> 여러 개가 존재하는 쪽인 `players` 테이블에 길드를 참조하는 외래키를 둔다

  -> 1:N 관계에서 일반적으로 N 쪽 테이블에 외래키를 둔다

3. 플레이어와 아이템의 N:M 관계를 구현하는 테이블 설계

- 플레이어는 여러 아이템을 가질 수 있고, 같은 아이템도 여러 플레이어가 가질 수 있어 N:M 관계이다.

```sql
CREATE TABLE items (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE player_items (
  player_id BIGINT UNSIGNED NOT NULL,
  item_id BIGINT UNSIGNED NOT NULL,
  quantity INT UNSIGNED NOT NULL DEFAULT 1,

  PRIMARY KEY (player_id, item_id),

  CONSTRAINT fk_player_items_player
    FOREIGN KEY (player_id)
    REFERENCES players(id)
    ON DELETE CASCADE,

  CONSTRAINT fk_player_items_item
    FOREIGN KEY (item_id)
    REFERENCES items(id)
    ON DELETE RESTRICT
);
```

4. `ON DELETE CASCADE`와 `ON DELETE SET NULL`의 차이는?

- 앞부분은 보유 관계를 삭제하고, 뒤의 부분은 외래키를 `NULL` 처리하여 소속 없이 처리

- `ON DELETE CASCADE`는 부모 행이 삭제되면 해당 부모를 참조하는 자식 행도 함께 삭제한다. 플레이어 자체가 없어지기 때문에 해당 플레이어의 아이템 보유 관계도 필요 없다는 규칙에 적합하다.

- `ON DELETE SET NULL`은 부모 행이 삭제되면 자식 행은 유지하고 외래키 값을 `NULL`로 변경한다. 플레이어 자체는 삭제되지 않고 무소속 상태로 변경된다. 주의할 점은 `SET NULL`을 사용하려면 해당 외래키 열이 `NULL`을 허용해야 한다.

```text
CASCADE
부모 삭제 -> 자식 행도 삭제

SET NULL
부모 삭제 -> 자식 행은 유지, 외래키만 NULL
```

5. 1:1 테이블의 외래키에 `UNIQUE` 또는 `PRIMARY KEY`가 필요한 이유

-> 한 부모 행에 여러 자식 행이 연결되는 것을 막아 1:1 관계를 보장하기 위해 필요

```sql
CREATE TABLE player_profiles (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  player_id BIGINT UNSIGNED NOT NULL,

  FOREIGN KEY (player_id)
    REFERENCES players(id)
);
```

```text
players 1 : N player_profiles
```

해당 부분을 막기 위해 `player_id`에 `UNIQUE`를 적용한다.

```sql
CREATE TABLE player_profiles (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  player_id BIGINT UNSIGNED NOT NULL UNIQUE,

  FOREIGN KEY (player_id)
    REFERENCES players(id)
);
```

해당 구조에서는 같은 `player_id`를 두 번 저장할 수 없다.

6. MongoDB에서 포함보다 참조가 적합한 상황을 설명

- 독립적으로 변경하거나 여러 문서가 공유하는 데이터에 적합하다.

- 데이터가 독립적으로 자주 변경되는 경우

- 하나의 데이터를 여러 문서가 공유하는 경우

- 포함했을 때 동일 데이터가 여러 문서에 반복 저장되는 경우

- 포함되는 데이터의 크기가 계속 증가할 가능성이 있는 경우

- 별도의 컬렉션으로 독립적인 조회가 필요한 경우

아래처럼 길드 정보를 가정한다.

```js
{
  _id: ObjectId("player1"),
  nickname: "Neo",
  guildId: ObjectId("guild1")
}
```

```js
{
  _id: ObjectId("guild1"),
  name: "Red Knights",
  level: 10
}
```

여러 플레이어가 같은 길드 정보를 참조하고, 길드 정보를 모든 플레이어 문서에 포함한다고 가정한다.

```js
{
  nickname: "Neo",
  guild: {
    name: "Red Knights",
    level: 10
  }
}
```

```js
{
  nickname: "Alice",
  guild: {
    name: "Red Knights",
    level: 10
  }
}
```

참조 방식에서는 길드 문서 하나만 수정하면 된다.

```js
{
  _id: ObjectId("guild1"),
  name: "Blue Dragons",
  level: 10
}
```

필요한 경우 `$lookup`을 사용하여 두 컬렉션을 결합할 수 있다.

```js
db.players.aggregate([
  {
    $lookup: {
      from: "guilds",
      localField: "guildId",
      foreignField: "_id",
      as: "guild",
    },
  },
]);
```

```text
Embedding

문서와 항상 함께 조회
데이터 크기가 작다
독립적으로 변경될 일이 적다
```

```text
Referencing

독립적으로 변경
여러 문서가 공유
데이터가 커질 가능성이 있음
별도 조회가 필요
```
