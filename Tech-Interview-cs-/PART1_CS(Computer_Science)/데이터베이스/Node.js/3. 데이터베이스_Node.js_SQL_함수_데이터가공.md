# SQL 함수로 데이터 가공

## SQL 함수 분류

| 분류         | 입력과 출력                           | 예시                               |
| ------------ | ------------------------------------- | ---------------------------------- |
| 단일 행 함수 | 행마다 하나의 결과를 반환             | `CONCAT`, `ROUND`, `DATE_FORMAT`   |
| 집계 함수    | 여러 행을 하나의 값으로 요약          | `COUNT`, `SUM`, `AVG`              |
| 윈도우 함수  | 행을 유지하면서 그룹 계산 결과를 추가 | `RANK`, `ROW_NUMBER`, `SUM() OVER` |

실습을 위해 전적 열을 추가한다.

```sql
ALTER TABLE players
  ADD COLUMN wins INT UNSIGNED NOT NULL DEFAULT 0,
  ADD COLUMN losses INT UNSIGNED NOT NULL DEFAULT 0;
```

## 문자열 함수

```sql
SELECT
  nickname,
  UPPER(nickname) AS upper_name,
  LOWER(nickname) AS lower_name,
  CHAR_LENGTH(nickname) AS char_count,
  CONCAT('[', guild, ']', nickname) AS label
FROM players;
```

| 함수                     | 의미               |
| ------------------------ | ------------------ |
| `CONCAT(a, b, ...)`      | 문자열 연결        |
| `CONCAT_WS(sep, ...)`    | 구분자를 넣어 연결 |
| `CHAR_LENGTH(s)`         | 문자 수            |
| `LENGTH(s)`              | 바이트 수          |
| `UPPER(s)`, `LOWER(s)`   | 대문자·소문자 변환 |
| `TRIM(s)`                | 양쪽 공백 제거     |
| `SUBSTRING(s, pos, len)` | 부분 문자열 추출   |
| `REPLACE(s, from, to)`   | 문자열 치환        |

MySQL의 `CONCAT`은 인수 중 하나라도 `NULL`이면 전체 결과가 `NULL`이 된다.

```sql
SELECT
  CONCAT(
    '[',
    COALESCE(guild, '무소속'),
    ']',
    nickname
  ) AS label
FROM players;
```

## 숫자 함수와 안전한 나눗셈

```sql
SELECT
  nickname,
  wins,
  losses,
  ROUND(
    wins / NULLIF(wins + losses, 0) * 100,
    1
  ) AS win_rate
FROM players;
```

- `NULLIF(a, b)`는 두 값이 같으면 `NULL`, 다르면 `a`를 반환한다.
- 분모가 `0`일 때 `NULLIF(..., 0)`을 사용하면 0으로 나누는 문제를 피할 수 있다.
- `wins + losses`가 `0`이면 `win_rate`는 `NULL`이 된다.

| 함수             | 의미                       |
| ---------------- | -------------------------- |
| `ROUND(n, d)`    | 소수점 `d`자리로 반올림    |
| `TRUNCATE(n, d)` | 소수점 `d`자리 아래를 버림 |
| `CEIL(n)`        | 올림                       |
| `FLOOR(n)`       | 내림                       |
| `ABS(n)`         | 절댓값                     |
| `MOD(a, b)`      | 나머지                     |

정확한 금액이나 비율을 계산할 때는 입력 자료형과 반환 정밀도까지 확인하고 `DECIMAL` 사용을 고려한다.

## 날짜와 시간 함수

```sql
SELECT
  nickname,
  last_login_at,
  DATEDIFF(CURDATE(), last_login_at) AS inactive_days,
  DATE_ADD(last_login_at, INTERVAL 7 DAY) AS reminder_date,
  DATE_FORMAT(last_login_at, '%Y-%m-%d') AS formatted_date
FROM players;
```

| 함수                              | 의미                                        |
| --------------------------------- | ------------------------------------------- |
| `CURDATE()`                       | 현재 날짜                                   |
| `NOW()`                           | 현재 날짜와 시각                            |
| `DATEDIFF(a, b)`                  | `a - b`의 날짜 차이를 일수로 반환           |
| `TIMESTAMPDIFF(unit, a, b)`       | 지정한 단위로 `a`부터 `b`까지의 차이를 반환 |
| `DATE_ADD(date, INTERVAL n unit)` | 날짜 더하기                                 |
| `DATE_SUB(date, INTERVAL n unit)` | 날짜 빼기                                   |
| `DATE_FORMAT(date, format)`       | 날짜를 문자열로 포맷                        |

`DATE_FORMAT`의 결과는 날짜형이 아니라 문자열이다. 날짜 정렬이나 비교에는 가능한 한 원본 날짜 열을 사용하는 것이 안전하다.

`TIMESTAMPDIFF(MONTH, a, b)`는 단순히 달력의 월 숫자 차이를 계산하는 것이 아니라, 두 날짜 사이에 완전히 경과한 월 단위의 차이를 정수로 반환한다.

## 형 변환

```sql
SELECT
  CAST(level AS CHAR) AS level_text,
  CAST('2026-09-02' AS DATE) AS study_date,
  CAST('123.45' AS DECIMAL(10, 2)) AS amount
FROM players
LIMIT 1;
```

암시적 형 변환에 지나치게 의존하면 비교 결과나 인덱스 사용이 예상과 달라질 수 있다.

서로 다른 자료형을 변환해야 한다면 `CAST`를 사용해 의도를 명시한다.

## `NULL` 처리 함수

```sql
SELECT
  nickname,
  COALESCE(guild, '무소속') AS guild_name,
  IFNULL(guild, '무소속') AS guild_name_mysql
FROM players;
```

- `COALESCE(a, b, c)`는 왼쪽부터 확인해 처음 만나는 `NULL`이 아닌 값을 반환한다.
- `IFNULL(a, b)`는 MySQL 전용 함수이며, `a`가 `NULL`이면 `b`를 반환한다.
- 다른 DBMS와의 이식성이 필요하다면 `COALESCE`가 유리하다.

## 조건 함수와 `CASE`

```sql
SELECT
  nickname,
  level,
  CASE
    WHEN level >= 50 THEN 'Master'
    WHEN level >= 40 THEN 'Diamond'
    WHEN level >= 30 THEN 'Gold'
    ELSE 'Rookie'
  END AS tier
FROM players;
```

`CASE`의 조건은 위에서 아래로 평가된다. 따라서 범위가 겹치는 조건에서는 더 엄격한 조건을 먼저 작성한다.

단순 `CASE`도 사용할 수 있다.

```sql
SELECT
  nickname,
  CASE vip_grade
    WHEN 5 THEN 'VVIP'
    WHEN 4 THEN 'VIP'
    ELSE '일반'
  END AS vip_label
FROM players;
```

## 집계 함수와 그룹화

```sql
SELECT
  guild,
  COUNT(*) AS player_count,
  ROUND(AVG(level), 1) AS avg_level,
  MIN(level) AS min_level,
  MAX(level) AS max_level
FROM players
GROUP BY guild;
```

| 함수                         | 의미                   |
| ---------------------------- | ---------------------- |
| `COUNT(*)`                   | 행의 수                |
| `COUNT(column)`              | `NULL`이 아닌 값의 수  |
| `SUM(column)`                | 합계                   |
| `AVG(column)`                | 평균이며 `NULL`은 제외 |
| `MIN(column)`, `MAX(column)` | 최솟값과 최댓값        |

### `WHERE`와 `HAVING`

```sql
SELECT
  guild,
  COUNT(*) AS player_count
FROM players
WHERE level >= 20
GROUP BY guild
HAVING COUNT(*) >= 2
ORDER BY player_count DESC;
```

- `WHERE`는 그룹화 전의 개별 행을 필터링한다.
- `HAVING`은 그룹화 후의 집계 결과를 필터링한다.

처리 흐름을 단순화하면 다음과 같다.

```text
FROM
→ WHERE
→ GROUP BY
→ HAVING
→ SELECT
→ ORDER BY
```

## 윈도우 함수

윈도우 함수는 집계 함수와 달리 원래 행을 줄이지 않고 계산 결과를 덧붙인다.

```sql
SELECT
  nickname,
  guild,
  level,
  RANK() OVER (
    PARTITION BY guild
    ORDER BY level DESC
  ) AS guild_rank
FROM players;
```

| 함수           | 동점 처리                                      |
| -------------- | ---------------------------------------------- |
| `ROW_NUMBER()` | 동점이어도 서로 다른 연속 번호를 부여          |
| `RANK()`       | 동점은 같은 순위이며 다음 순위를 건너뜀        |
| `DENSE_RANK()` | 동점은 같은 순위이며 다음 순위를 연속으로 부여 |

예를 들어 점수가 `100`, `100`, `90`이라면 결과는 다음과 같다.

| 함수           | 순위 결과 |
| -------------- | --------- |
| `ROW_NUMBER()` | `1, 2, 3` |
| `RANK()`       | `1, 1, 3` |
| `DENSE_RANK()` | `1, 1, 2` |

누적 합계도 계산할 수 있다.

```sql
SELECT
  nickname,
  level,
  SUM(level) OVER (
    ORDER BY id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_level_sum
FROM players;
```

현재 행까지의 `level`을 순서대로 누적하여 계산한다.

## 인덱스와 함수 사용 시 주의점

인덱스가 설정된 열을 함수로 감싸면 일반적인 인덱스 범위 검색이 어려워질 수 있다.

```sql
-- 개선 전
WHERE DATE(created_at) = '2026-09-01'
```

```sql
-- 개선 후
WHERE created_at >= '2026-09-01 00:00:00'
  AND created_at <  '2026-09-02 00:00:00'
```

실제 인덱스 사용 여부는 `EXPLAIN`으로 확인한다.

```sql
EXPLAIN
SELECT id, nickname
FROM players
WHERE last_login_at >= '2026-08-25';
```

## MongoDB 집계 파이프라인

```js
db.players.aggregate([
  {
    $set: {
      guildName: {
        $ifNull: ["$guild", "무소속"],
      },
      tier: {
        $switch: {
          branches: [
            {
              case: { $gte: ["$level", 50] },
              then: "Master",
            },
            {
              case: { $gte: ["$level", 40] },
              then: "Diamond",
            },
            {
              case: { $gte: ["$level", 30] },
              then: "Gold",
            },
          ],
          default: "Rookie",
        },
      },
    },
  },
  {
    $group: {
      _id: "$guildName",
      playerCount: { $sum: 1 },
      avgLevel: { $avg: "$level" },
    },
  },
  {
    $sort: {
      avgLevel: -1,
    },
  },
]);
```

## 핵심 정리

- 단일 행 함수는 행마다 결과를 만든다.
- 집계 함수는 여러 행을 하나의 값으로 요약한다.
- `COALESCE`와 `NULLIF`는 `NULL` 처리와 0으로 나누는 문제를 방지할 때 유용하다.
- `CASE`는 조건에 따라 데이터를 분류하거나 다른 값을 반환한다.
- `WHERE`는 그룹화 전, `HAVING`은 그룹화 후에 데이터를 필터링한다.
- 윈도우 함수는 원래 행을 유지하면서 순위나 누적값을 계산한다.
- 날짜 열을 함수로 감싸기보다 범위 조건을 사용하는 것이 인덱스 활용에 유리할 수 있다.
- 실제 인덱스 사용 여부는 `EXPLAIN`으로 확인한다.

## 복습

### 1. 기본키와 외래키의 역할

- 기본키(Primary Key): 테이블의 각 행을 고유하게 식별하는 값
- 외래키(Foreign Key): 다른 테이블의 기본키 또는 `UNIQUE` 키를 참조하여 테이블 사이의 관계를 표현하는 값

예를 들어 다음과 같은 구조가 있다.

```sql
CREATE TABLE guilds (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE players (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nickname VARCHAR(50) NOT NULL,
  guild_id BIGINT UNSIGNED NULL,

  CONSTRAINT fk_players_guild
    FOREIGN KEY (guild_id)
    REFERENCES guilds(id)
);
```

여기서

- `guilds.id`는 각 길드를 구분하는 기본키
- `players.id`는 각 플레이어를 구분하는 기본키
- `players.guild_id`는 플레이어가 어떤 길드에 소속되어 있는지를 나타내는 외래키

예를 들어 다음 데이터가 있다면

```text
guilds

id | name
---|--------
1  | Red
2  | Blue
```

```text
players

id | nickname | guild_id
---|----------|---------
1  | Neo      | 1
2  | Alice    | 1
3  | Bob      | 2
```

`Neo`와 `Alice`는 `guilds.id = 1`인 `Red` 길드에 속한다.

즉 기본키는 **자기 테이블의 행을 식별**하고, 외래키는 **다른 테이블의 행을 참조하여 관계를 만든다.**

### 2. 플레이어와 길드가 1:N 관계일 때 외래키는 어느 테이블에 두는가?

정답:

```text
N 쪽인 players 테이블에 guild_id 외래키를 둔다.
```

잘못된 답:

```text
player.guilds에 둔다.
```

`player.guilds`라는 컬럼에 여러 길드 정보를 저장하는 방식이 아니다.

길드 하나에는 여러 플레이어가 소속될 수 있지만, 플레이어 한 명은 하나의 길드에 소속된다고 가정하면 다음과 같은 관계가 된다.

```text
guilds 1 : N players
```

따라서 여러 개가 존재하는 쪽인 `players` 테이블에 길드를 참조하는 외래키를 둔다.

```sql
CREATE TABLE players (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  nickname VARCHAR(50) NOT NULL,
  guild_id BIGINT UNSIGNED NULL,

  CONSTRAINT fk_players_guild
    FOREIGN KEY (guild_id)
    REFERENCES guilds(id)
);
```

예를 들어

```text
guilds

id | name
---|-------
1  | Red
```

```text
players

id | nickname | guild_id
---|----------|---------
1  | Neo      | 1
2  | Alice    | 1
3  | Bob      | 1
```

세 플레이어 모두 같은 `guilds.id = 1`을 참조할 수 있다.

즉

```text
guilds.id = 1
      ↑
      ├── players.guild_id = 1
      ├── players.guild_id = 1
      └── players.guild_id = 1
```

1:N 관계에서는 일반적으로 **N 쪽 테이블에 외래키를 둔다.**

### 3. 플레이어와 아이템의 N:M 관계를 구현하는 테이블 설계

플레이어는 여러 아이템을 가질 수 있고, 같은 아이템도 여러 플레이어가 가질 수 있으므로 N:M 관계이다.

```text
players N : M items
```

관계형 데이터베이스에서는 N:M 관계를 직접 표현하기보다 중간에 연결 테이블을 만든다.

```text
players
   1
   |
   N
player_items
   N
   |
   1
items
```

예시:

```sql
CREATE TABLE items (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE player_items (
  player_id BIGINT UNSIGNED NOT NULL,
  item_id BIGINT UNSIGNED NOT NULL,
  quantity INT UNSIGNED NOT NULL DEFAULT 1,

  PRIMARY KEY (player_id, item_id),

  CONSTRAINT fk_player_items_player
    FOREIGN KEY (player_id)
    REFERENCES players(id)
    ON DELETE CASCADE,

  CONSTRAINT fk_player_items_item
    FOREIGN KEY (item_id)
    REFERENCES items(id)
    ON DELETE RESTRICT
);
```

예를 들어 다음 데이터가 있을 수 있다.

```text
players

id | nickname
---|---------
1  | Neo
2  | Alice
```

```text
items

id | name
---|--------
10 | Sword
20 | Potion
```

```text
player_items

player_id | item_id | quantity
----------|---------|---------
1         | 10      | 1
1         | 20      | 5
2         | 10      | 1
```

이를 해석하면

- Neo는 Sword를 1개 보유
- Neo는 Potion을 5개 보유
- Alice는 Sword를 1개 보유

`player_items`와 같은 연결 테이블을 사용하면 N:M 관계를 두 개의 1:N 관계로 바꿀 수 있다.

```text
players 1 : N player_items
items   1 : N player_items
```

또한 연결 테이블에는 관계 자체의 속성을 저장할 수 있다.

예를 들어

```sql
quantity
acquired_at
equipped
enhancement_level
```

등을 저장할 수 있다.

### 4. `ON DELETE CASCADE`와 `ON DELETE SET NULL`의 차이는?

기존 답의 방향은 맞지만 더 정확하게 구분해야 한다.

#### `ON DELETE CASCADE`

부모 행이 삭제되면 해당 부모를 참조하는 자식 행도 함께 삭제한다.

예를 들어

```sql
FOREIGN KEY (player_id)
REFERENCES players(id)
ON DELETE CASCADE
```

가 설정되어 있다고 가정한다.

```text
players

id | nickname
---|---------
1  | Neo
```

```text
player_items

player_id | item_id
----------|--------
1         | 10
1         | 20
```

다음과 같이 플레이어를 삭제하면

```sql
DELETE FROM players
WHERE id = 1;
```

`player_id = 1`을 참조하고 있던 `player_items` 행도 자동으로 삭제된다.

```text
players
Neo 삭제

       ↓ CASCADE

player_items
Neo의 아이템 보유 관계도 삭제
```

플레이어 자체가 없어졌기 때문에 해당 플레이어의 아이템 보유 관계도 필요 없다는 업무 규칙에 적합하다.

---

#### `ON DELETE SET NULL`

부모 행이 삭제되면 자식 행은 유지하고 외래키 값을 `NULL`로 변경한다.

예를 들어

```sql
FOREIGN KEY (guild_id)
REFERENCES guilds(id)
ON DELETE SET NULL
```

이라고 가정한다.

```text
players

id | nickname | guild_id
---|----------|---------
1  | Neo      | 10
```

`guilds.id = 10`인 길드를 삭제하면

```text
id | nickname | guild_id
---|----------|---------
1  | Neo      | NULL
```

플레이어 자체는 삭제되지 않고 무소속 상태가 된다.

주의할 점은 `SET NULL`을 사용하려면 해당 외래키 열이 `NULL`을 허용해야 한다.

```sql
guild_id BIGINT UNSIGNED NULL
```

즉

```text
CASCADE
부모 삭제
→ 자식 행도 삭제

SET NULL
부모 삭제
→ 자식 행은 유지
→ 외래키만 NULL
```

### 5. 1:1 테이블의 외래키에 `UNIQUE` 또는 `PRIMARY KEY`가 필요한 이유

기존 답:

```text
- 이름 변경 시 여러 행 수정 방지
- 오타 때문에 생기는 이슈 방지
```

이 답은 잘못되었다.

위 내용은 주로 데이터 중복이나 정규화와 관련된 설명이며 1:1 관계에서 `UNIQUE` 또는 `PRIMARY KEY`가 필요한 직접적인 이유가 아니다.

정답:

> 한 부모 행에 여러 자식 행이 연결되는 것을 막아 1:1 관계를 보장하기 위해 필요하다.

예를 들어 다음 테이블이 있다고 가정한다.

```sql
CREATE TABLE player_profiles (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  player_id BIGINT UNSIGNED NOT NULL,

  FOREIGN KEY (player_id)
    REFERENCES players(id)
);
```

여기에는 `player_id`에 `UNIQUE`가 없다.

따라서 다음 데이터가 저장될 수 있다.

```text
id | player_id | bio
---|-----------|-------
1  | 100       | A
2  | 100       | B
3  | 100       | C
```

한 플레이어 `100`에게 프로필이 3개 존재하게 된다.

그러면 실제 관계는

```text
players 1 : N player_profiles
```

가 된다.

이를 막으려면 `player_id`에 `UNIQUE`를 적용할 수 있다.

```sql
CREATE TABLE player_profiles (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  player_id BIGINT UNSIGNED NOT NULL UNIQUE,

  FOREIGN KEY (player_id)
    REFERENCES players(id)
);
```

이제 같은 `player_id`를 두 번 저장할 수 없다.

```text
player_id = 100 → 최대 1개
```

또는 외래키 자체를 기본키로 사용할 수 있다.

```sql
CREATE TABLE player_profiles (
  player_id BIGINT UNSIGNED PRIMARY KEY,
  bio TEXT NULL,

  CONSTRAINT fk_profiles_player
    FOREIGN KEY (player_id)
    REFERENCES players(id)
    ON DELETE CASCADE
);
```

`PRIMARY KEY`는 기본적으로 중복을 허용하지 않으므로 플레이어 한 명당 프로필을 최대 하나만 저장할 수 있다.

즉

```text
UNIQUE 또는 PRIMARY KEY 없음

Player 1
 ├─ Profile A
 ├─ Profile B
 └─ Profile C

1:N 가능
```

```text
UNIQUE 또는 PRIMARY KEY 있음

Player 1
 └─ Profile A

최대 1개
```

다만 이것만으로

```text
모든 플레이어가 반드시 프로필을 하나 가지고 있다.
```

를 보장하는 것은 아니다.

프로필이 없는 플레이어도 존재할 수 있으므로 플레이어 기준 실제 관계는 다음과 같을 수 있다.

```text
Player 1 : Profile 0..1
```

### 6. MongoDB에서 포함(Embedding)보다 참조(Referencing)가 적합한 상황

기존 답:

> 독립적으로 변경하거나 여러 문서가 공유하는 데이터에 적합하다.

맞는 답이다.

조금 더 정확하게 설명하면 다음과 같다.

MongoDB에서 참조 방식은 다음과 같은 경우에 적합할 수 있다.

- 데이터가 독립적으로 자주 변경되는 경우
- 하나의 데이터를 여러 문서가 공유하는 경우
- 포함했을 때 동일 데이터가 여러 문서에 반복 저장되는 경우
- 포함되는 데이터의 크기가 계속 증가할 가능성이 있는 경우
- 별도의 컬렉션으로 독립적인 조회가 필요한 경우

예를 들어 길드 정보가 있다고 가정한다.

```js
{
  _id: ObjectId("player1"),
  nickname: "Neo",
  guildId: ObjectId("guild1")
}
```

```js
{
  _id: ObjectId("guild1"),
  name: "Red Dragons",
  level: 10
}
```

여러 플레이어가 같은 길드를 참조할 수 있다.

```text
Player Neo ─────┐
Player Alice ───┼──> Guild Red Dragons
Player Bob ─────┘
```

만약 길드 정보를 모든 플레이어 문서에 포함하면

```js
{
  nickname: "Neo",
  guild: {
    name: "Red Dragons",
    level: 10
  }
}
```

```js
{
  nickname: "Alice",
  guild: {
    name: "Red Dragons",
    level: 10
  }
}
```

길드 이름이 변경될 때 여러 플레이어 문서를 수정해야 할 수 있다.

반면 참조 방식에서는 길드 문서 하나만 수정하면 된다.

```js
{
  _id: ObjectId("guild1"),
  name: "Blue Dragons",
  level: 10
}
```

필요한 경우 `$lookup`을 사용하여 두 컬렉션을 결합할 수 있다.

```js
db.players.aggregate([
  {
    $lookup: {
      from: "guilds",
      localField: "guildId",
      foreignField: "_id",
      as: "guild",
    },
  },
]);
```

따라서 일반적으로

```text
Embedding

문서와 항상 함께 조회
데이터 크기가 작음
독립적으로 변경될 일이 적음
```

인 경우 적합하고,

```text
Referencing

독립적으로 변경
여러 문서가 공유
데이터가 커질 가능성이 있음
별도 조회가 필요
```

인 경우 적합할 수 있다.

```text
MongoDB에서는 관계형 데이터베이스의 정규화 규칙만을 기준으로 결정하기보다 실제 읽기 패턴, 쓰기 패턴, 데이터 크기, 변경 빈도를 함께 고려해야 한다.
```

```sql
DATE(created_at) = '2026-09-01'
```
