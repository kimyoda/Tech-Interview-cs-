## 블로킹 소켓

**블로킹 소켓(Blocking Socket)**은 소켓 함수를 호출했을 때 작업을 진행할 수 있을 때까지 호출한 스레드를 대기 상태로 만드는 소켓

```text
블로킹 수신
스레드: recv 호출 - 데이터가 없어서 대기 - 데이터 도착 - recv 반환
CPU:       실행              다른 작업 가능         실행
```

대기 중인 스레드는 CPU를 계속 계산에 사용하지 않지만, 스레드 자체의 스택 메모리와 운영체제 관리 비용은 남는다

연결마다 스레드를 하나씩 두면 구현은 단순, 동시 접속자가 많아질수록 다음 문제가 커진다

- 연결 수 만큼 스레드가 늘어날 수 있다
- 스레드 스택과 운영체제 관리 자원이 필요
- 깨어나는 스레드가 많아지면 문맥 교환 비용이 증가
- 여러 스레드가 같은 게임 상태를 만지면 잠금과 경쟁 조건이 늘어난다

```text
연결당 스레드 모델
클라이언트 1 -- 스레드 1 -- recv 대기
클라이언트 2 -- 스레드 2 -- recv 대기
클라이언트 3 -- 스레드 3 -- recv 대기
...
클라이언트 N -- 스레드 N -- recv 대기
```

### Node.js에서 무엇이 블로킹인가

Node.js의 net.Socket은 일반적으로 논블록 소켓과 이벤트 루프를 사용.

데이터가 없을 때 JS 스레드가 recv 안에서 멈추는 대신, 런타임이 운영체제의 통지를 기다렸다가 data, connect, drain 같은 이벤트를 실행

```ts
import net from "node:net";

const server = net.createServer((socket) => {
  socket.on("data", (chunk: Buffer) => {
    // 데이터가 도착했을 때 콜백이 실행
    console.log("received bytes:", chunk.length);
  });
});

server.listen(4000, "0.0.0.0");
```

그러나 "소켓이 논블록"이라는 사실이 "Node.js 애플리케이션 전체가 멈추지 않는다"는 뜻은 아니다. 이벤트 루프를 오래 점유할 수 있음

- 큰 배열을 한 번에 정렬하는 CPU 연산
- 거대한 JSON을 동기적으로 직렬화하거나 파싱하는 작업
- 종료 조건이 늦은 반복문
- 동기 파일 API, 동기 암호화 API
- 하나의 콜백에서 너무 많은 플레이어를 한꺼번에 갱신하는 작업

```ts
// 나쁜예
socket.on("data", () => {
  let sum = 0;

  for (let i = 0; i < 2_000_000_000; i += 1) {
    sum += i;
  }

  socket.write(String(sum));
});
```

### 게임 서버

Node.js 장점은 연결마다 스레드를 만들지 않고 많은 대기 연결을 다룰 수 있다.

반대로 한 콜백이 오래 실행되면 같은 이벤트 루프에 묶인 모든 플레이어가 함께 지연

네트워크 콜백은 짧게 유지, 무거운 CPU 작업은 Worker Threads나 별도 프로세스로 분리하는 것이 원칙

### 확인

- 블로킹 대기 중이면 CPU를 계속 100% 쓴다 -> 보통 스레드는 대기 상태라 CPU 계산을 하지 않는다
- 스레드를 늘리면 항상 처리량이 증가 -> 문맥 교환, 메모리, 공유 상태 잠금 비용도 함께 증가
- async 함수를 붙이면 CPU 작업도 논블록 -> async 문법은 동기 CPU 코드를 다른 스레드로 옮기지 않는다
- Node.js 스레드가 하나뿐 -> JS 실행은 기본적으로 한 이벤트 루프에 하지만 런타임과 워커는 다른 스레드를 사용할 수 있음

## 네트워크 연결 및 송신

TCP 클라이언트의 기본 흐름은 다음과 같다

```text
소켓 생성 -> DNS 조회 -> TCP 연결 -> 데이터 쓰기 -> 정상 종료
```

저수준 API에서 socket, bind, connect, send, close 순서를 직접 다룬다. Node.js에서 임시 로컬 포트 바인딩과 논블록 연결 과정을 net.createConnection이 대부분 처리

### Node.js TCP 클라이언트

```ts
import net from "node:net";

const host = "127.0.0.1";
const port = 4000;
const connectTimeoutMs = 3_000;

const socket = net.createConnection({ host, port });

const connectTimer = setTimeout(() => {
  socket.destroy(new Error("connect timeout"));
}, connectTimeoutMs);

socket.once("connect", () => {
  clearTimeout(connectTimer);

  // 작은 실시간 메시지의 지연을 줄이기 위해 Nagle 알고리즘을 끔
  socket.setNoDelay(true);

  // 유휴 연결의 생존 여부를 OS 수준에 확인하는 보존 수단
  socket.setKeepAlive(true, 30_000);

  socket.write(Buffer.from("hello", "utf8"));
});

socket.on("data", (chunk: Buffer) => {
  console.log("server response:", chunk.toString("utf8"));
});

socket.on("end", () => {
  console.log("server ended its writable side");
});

socket.on("error", (error: NodeJS.ErrnoException) => {
  console.error("socket error:", error.code, error.message);
});

socket.on("close", (hadError: boolean) => {
  clearTimeout(connectTimer);

  console.log("connection closed, hadError:", hadError);
});
```

### 연결 성립

connect 이벤트는 TCP 연결이 성립되어 소켓을 사용할 수 있다는 뜻.

- 게임 로그인에 성공
- 상대 애플리케이션이 내 메시지를 처리
- 서버가 게임 룸 참가를 승인

네트워크 연결과 애플리케이션 세션은 별도 단계로 설계

```text
TCP 연결 성공 -> 프로토콜 버전 확인 -> 인증 토큰 검증 -> 중복 로그인, 밴 상태 확인 -> 게임 세션 입장
```

### socket.write의 반환값

socket.write가 반환하면 현재 데이터를 커널 쪽으로 넘길 수 있었다. false라면 일부 데이터가 Node.js의 사용자 공간 버퍼에 쌓여 추가 쓰기를 멈추고 drain 이벤트를 기다린다

```ts
import { once } from "node:events";
import type net from "node:net";

async function writeWithBackpressure(
  socket: net.Socket,
  payload: Buffer,
): Promise<void> {
  const canContinue = socket.write(payload);

  if (!canContinue) {
    await once(socket, "drain");
  }
}
```

write의 성공과 콜백 실행은 **상대 게임 로직이 메시지를 처리했다는 보장**이 아님

거래, 아이템 지급, 매치 참가처럼 처리가 확인되어야 하는 명령은 앱 수준의 requestId와 응답 또는 ACK를 사용

```ts
type PurchaseRequest = {
  type: "purchase";
  requestId: string;
  itemId: string;
};

type PurchaseResult = {
  type: "purchaseResult";
  requestId: string;
  ok: boolean;
  reason?: string;
};
```

### Nagle 알고리즘, 작은 게임 패킷

Nagle 알고리즘은 작은 데이터를 모아 전송 효율을 높이는 대신 지연이 늘 수 있다. 짧은 입력 메시지를 자주 보내는 실시간 게임에서 setNoDelay(true)를 검토한다. 패킷 수가 지나치게 늘면 헤더 오버헤드와 시스템 호출 비용이 증가, 같은 틱에 발생한 여러 상태 갱신을 하나의 프레임으로 묶는 전략도 필요

### 자주 만나는 연결 오류

| 오류 코드    | 대표 원인                          | 처리 방향                       |
| ------------ | ---------------------------------- | ------------------------------- |
| ECONNREFUSED | 대상 포트에서 서버가 대기하지 않음 | 주소,포트 확인, 제한된 재시도   |
| ETIMEDOUT    | 연결 또는 네트워크 응답 지연       | 타임아웃 기록, 백오프 후 재시도 |
| EPIPE        | 상대가 연결을 강제로 종료          | 세션 정리, 필요하면 재접속      |
| EADDRINUSE   | 로컬 포트가 이미 사용 중           | 중복 프로세스와 포트 설정 확인  |

## 블로킹과 소켓버퍼

TCP 소켓에 운영체제가 관리하는 **송신 버퍼**와 **수신 버퍼**가 있음

애플리케이션의 쓰기가 곧바로 인터넷 반대편 앱에 도착하는 것은 아님

```text
송신 애플리케이션
write
Node.js 쓰기 버퍼
운영체제 TCP 송신 버퍼
네트워크
상대 운영체제 TCP 수신 버퍼
read
수신 애플리케이션
```

#### 송신 버퍼가 필요한 이유

앱이 데이터를 만드는 속도와 네트워크가 전송하는 속도는 항상 같지 않음

버퍼는 짧은 속도 차이를 흡수, 버퍼는 무한하지 않다

블로킹 소켓에 송신 버퍼에 공간이 없을 때 send 호출이 기다릴 수 있다

Node.js는 JS 스레드를 멈추는 대신 writer가 false를 반환해서 **백프레셔(backpressure)**를 알린다

### 백프레셔를 무시하면 생기는 이슈

```ts
// 나쁜예 느린 클라이언트에 계속 쓰며 메모리 큐를 키움
setInterval(() => {
  socket.write(createLargeWorldSnapshot());
}, 10);
```

네트워크보다 생산 속도가 빠른 상태에 계속 write하면 다음 현상이 발생

- 프로세스 메모리 증가
- 가비지 컬렉션 지연 증가
- 오래된 위치 스냅샷이 최신 스냅샷 앞을 막는다
- 한 명의 느린 클라이언트가 서버 전체 성능을 저하시킨다
- 최종적으로 프로세스 종료 또는 연결 강제 종료

### 게임 상태는 모두 큐에 넣지 않음

메시지 성격에 따라 혼잡 정책을 다르게 적용

| 메시지             | 권장                            | 이유                    |
| ------------------ | ------------------------------- | ----------------------- |
| 아이템 구매 결과   | 보존하고 응답 확인              | 정합성이 중요           |
| 채팅               | 제한된 큐에 보존                | 순서와 전달이 중요      |
| 플레이어 최신 위치 | 오래된 값 폐기 후 최신값만 유지 | 과거 위치는 가치가 낮음 |
| 월드 전체 스냅샷   | 빈도 축소 또는 델타 전송        | 크기가 크고 반복        |
| 핑, 통계           | 혼잡 시 생략 가능               | 핵심 게임 상태가 아닌   |

```ts
type PendingState = {
  latestPosition?: Buffer;
  reliableMessages: Buffer[];
};

function replaceLatestPosition(
  pending: PendingState,
  nextPosition: Buffer,
): void {
  // 보내지 못한 과거 위치를 계속 누적하지 않음
  pending.latestPosition = nextPosition;
}
```

### Node.js 관찰값

- socket.writableLength: Node.js 쓰기 큐에 대기 중인 바이트 수
- socket.writableHighWaterMark: write가 false로 바뀌기 시작하는 기준
- socket.bytesWritten: 소켓에 기록된 누적 바이트
- socket.bytesRead: 소켓에서 읽은 누적 바이트

highWaterMark는 엄격한 메모리 상한선이 아닌 백프레셔를 시작하는 기준이다. 연결별 최대 대기 바이트와 최대 대기 메시지 수는 정책으로 별도 제한하는 편이 안전

```ts
const MAX_PENDING_BYTES = 512 * 1024;

function guardSlowClient(socket: net.Socket): void {
  if (socket.writableLength > MAX_PENDING_BYTES) {
    socket.destroy(new Error("slow client: write queue overflow"));
  }
}
```

## 네트워크 연결받기 및 수신

TCP 서버의 저수준 흐름은 socket -> bind -> listen -> accept -> recv 순이다

Node.js에서 net.createServer와 이벤트가 이 과정을 감싼다

### Node.js TCP 서버

```ts
import net from "node:net";

const PORT = Number(process.env.GAME_TCP_PORT ?? 4000);
const HOST = process.env.GAME_TCP_HOST ?? "0.0.0.0";

const sockets = new Set<net.Socket>();

const server = net.createServer(
  { allowHalfOpen: false },

  (socket: net.Socket) => {
    sockets.add(socket);

    socket.setNoDelay(true);
    socket.setKeepAlive(true, 30_000);

    console.log("connected:", {
      address: socket.remoteAddress,
      port: socket.remotePort,
    });

    socket.on("data", (chunk: Buffer) => {
      // chunk 한 개가 메시지 한 개라는 보장은 없다
      console.log("received bytes:", chunk.length);
    });

    socket.on("end", () => {
      // 상대가 자신의 송신 방향을 정상 종료했다
      console.log("peer sent FIN");
    });

    socket.on("error", (error: NodeJS.ErrnoException) => {
      console.error("client socket error:", error.code);
    });

    socket.on("close", () => {
      sockets.delete(socket);
    });
  },
);

server.on("error", (error: NodeJS.ErrnoException) => {
  console.error("server error:", error.code, error.message);
});

server.listen({ port: PORT, host: HOST, backlog: 512 }, () => {
  console.log("TCP server listening:", server.address());
});
```

### listening 소켓과 연결 소켓

두 종류를 구분한다

| 구분       | 역할                                          |
| ---------- | --------------------------------------------- |
| net.Server | 주소와 포트에서 새 TCP 연결을 기다린다        |
| net.Socket | 특정 클라이언트와 데이터를 주고받는 연결 하나 |

backlog는 아직 앱에 전달되지 않은 **대기 연결 큐**의 길이와 관련된 값이다. 최대 동시 접속자 수와 같은 뜻이 아니고 실제 값은 운영체제 설정의 영향도 받는다

### TCP 수신 데이터에 메시지 경계가 없다

송신자가 write를 두 번 호출해도 수신자는 data 이벤트 한 번 또는 여러 번으로 받을 수 있음, 따라서 패킷 헤더와 본문을 누적해서 해석하는 프레이머가 필요

```ts
class LengthPrefixedDecoder {
  private pending = Buffer.alloc(0);

  constructor(private readonly maxFrameBytes = 64 * 1024) {}

  feed(chunk: Buffer): Buffer[] {
    this.pending = Buffer.concat([this.pending, chunk]);

    const frames: Buffer[] = [];

    while (this.pending.length >= 4) {
      const bodyLength = this.pending.readUInt32BE(0);

      if (bodyLength > this.maxFrameBytes) {
        throw new Error("frame too large");
      }

      const frameLength = 4 + bodyLength;

      if (this.pending.length < frameLength) {
        break;
      }

      frames.push(this.pending.subarray(4, frameLength));

      this.pending = this.pending.subarray(frameLength);
    }

    return frames;
  }
}
```

```ts
server.on("connection", (socket: net.Socket) => {
  const decoder = new LengthPrefixedDecoder();

  socket.on("data", (chunk: Buffer) => {
    try {
      for (const frame of decoder.feed(chunk)) {
        handleGameFrame(socket, frame);
      }
    } catch {
      socket.destroy(new Error("invalid frame"));
    }
  });
});

function handleGameFrame(socket: net.Socket, frame: Buffer): void {
  // 실제 서버에서 메시지 타입, 세션 상태, 권한, 값 범위를 함께 검증
  console.log("frame bytes:", frame.length, socket.remoteAddress);
}
```

- 원리 설명용, 매우 많은 조각을 받는 환경에서 청크 큐, 링 버퍼 또는 검증된 라이브러리를 고려

### 연결 종료 이벤트

| 메서드         | 의미                                 |
| -------------- | ------------------------------------ |
| end            | 상대가 정상적으로 송신 방향을 종료   |
| finish         | 로컬의 쓰기 데이터가 모두 처리됨     |
| close          | 소켓 자원이 닫힘                     |
| error          | 네트워크 또는 소켓 오류 발생         |
| socket.end     | 남은 쓰기를 처리한 뒤 정상 종료 요청 |
| socket.destroy | 오류 상황 등에 즉시 소켓 파괴        |

중복 실행되어도 안전하게 작성, error 다음에 close가 이어질 수 있다

```ts
let cleanedUp = false;

function cleanupConnection(): void {
  if (cleanedUp) {
    return;
  }

  cleanedUp = true;

  // 인증 타이머 해제, 룸 퇴장, 세션 만료 처리 등
}

socket.on("error", cleanupConnection);
socket.on("close", cleanupConnection);
```

## 수신 버퍼가 가득찰 때 발생현상

수신 애플리케이션이 데이터를 소비하는 속도보다 네트워크에서 데이터가 들어오는 속도가 빠르면 수신 측 버퍼가 차오른다

```text
송신 앱이 빠르게 write
송신 측 버퍼 증가
네트워크 전송
수신 측 커널 버퍼 증가
수신 앱의 read가 느림
```

TCP에서 수신 측이 받을 수 있는 여유 공간을 윈도 크기로 알림. 수신 버퍼가 가득 차면 광고 윈도가 줄거나 0, 송신 속도도 결국 느려짐.

송신 측 버퍼와 Node.js 쓰기 큐가 차며 socket.write가 false를 반환

**흐름 제어와 백프레셔의 전파**

```text
느린 수신 처리
수신 버퍼 포화
TCP 수신 윈도 축소
socket.write가 false
앱이 drain까지 생산 중단
```

### 연결이 즉시 끊어지는 게 아님

수신 버퍼가 찼다고 TCP 연결이 곧바로 종료되는 것이 아님. 앱이 연결된 상태로 남고, 실제 전송 속도가 느린 쪽에 맞춰질 수 있다. 게임 서버에서는 오래된 데이터가 계속 쌓인 연결을 무기한 유지하면 안된다

### 느린 클라 정책

- 연결별 최대 쓰기 큐 바이트
- 연결 신뢰성 메시지 최대 개수
- 마지막 정상 수신 시각
- 스냅샷 지연 틱 수
- 인증 완료 제한 시간
- 초당 메시지 수와 초당 바이트 수

```ts
type ConnectionHealth = {
  lastInboundAt: number;
  lastAckAt: number;
  pendingReliableCount: number;
};

function shouldDisconnectSlowClient(
  socket: net.Socket,
  health: ConnectionHealth,
  now: number,
): boolean {
  const idleTooLong = now - health.lastInboundAt > 60_000;

  const ackTooLate = now - health.lastAckAt > 15_000;

  const queueTooLarge = socket.writableLength > 512 * 1024;

  const tooManyReliableMessages = health.pendingReliableCount > 1_000;

  return idleTooLong || ackTooLate || queueTooLarge || tooManyReliableMessages;
}
```

### 수신 처리도 백프레셔가 필요

data 이벤트에서 시작한 비동기 작업이 완료되기 전에 다음 data 이벤트를 계속 처리하면 내부 작업 큐가 증가할 수 있다. 연결별 직렬 큐를 두거나, 처리량이 한계를 넘으면 socket.pause로 읽기를 잠시 멈춘 뒤 socket.resume으로 재개할 수 있음

pause는 보안 정책이나 큐 상한을 대신하지 않음. 공격자가 선언한 메시지 길이가 비정상적으로 크거나 메시지 빈도가 과도하면 연결을 종료

### UDP와의 차이

UDP에는 TCP와 같은 연결별 흐름 제어가 없다. 수신 소켓 버퍼가 가득 차면 새 데이터그램이 버려질 수 있고, 송신자는 그 사실을 자동으로 전달받지 못한다.

UDP 게임 프로토콜은 시퀀스 번호, 손실 통계, 중요 메시지 ACK, 최신 상태 우선 정책을 설계해야한다

## 논블록 소켓

**논블록 소켓(Non-blocking socket)**은 지금 작업을 완료할 수 없어도 호출한 스레드를 기다리게 하지 않고 즉시 반환

저수준 API에서 받을 데이터가 없으면 EAGAIN 또는 EWOULDBLOCK 같은 결과가 나올 수 있고 아무런 준비 없이 모든 소켓을 반복 검사하면 CPU를 낭비

```text
소켓 1 검사 -> 준비 안 됨
소켓 2 검사 -> 준비 안 됨
...
소켓 10000 검사 -> 준비 안 됨
다시 처음부터 반복
```

그래서 실무에서 select, poll, epoll, kqueue 같은 준비 상태 통신 장치나 IOCP 같은 완료 통지 장치를 함께 사용

### Node.js 논블록 처리

Node.js는 일반적으로 libuv가 운영체제의 I/O 통지 장치에 소켓을 등록, 준비되거나 완료된 작업을 이벤트루프에 전달

```ts
socket.on("data", handleData);
socket.on("drain", resumeSending);
socket.on("error", handleError);
socket.on("close", cleanup);
```

내부적으로 다음과 대응

| 이벤트     | 관점                 |
| ---------- | -------------------- |
| data       | 읽을 데이터가 생김   |
| drain      | 다시 쓸 여유가 생김  |
| connection | accept할 연결이 생김 |
| close      | 연결 자원이 닫힘     |

### 이벤트 루프의 공정성

하나의 이벤트 루프가 여러 연결을 번갈아 처리하려면 각 콜백이 빠르게 끝나야 한다. 소켓 수가 많아도 콜백 하나가 100ms 동안 CPU를 독점하면 다른 모든 연결의 응답이 최소 100ms 이상 늦어진다

게임 서버는 평균 처리 시간만 보는 게 아닌 p95, p99 이벤트 루프 지연도 관찰해야 한다

```ts
import { monitorEventLoopDelay } from "node:perf_hooks";

const histogram = monitorEventLoopDelay({
  resolution: 20,
});

histogram.enable();

setInterval(() => {
  const p99Ms = histogram.percentile(99) / 1_000_000;

  console.log("event loop delay p99 ms:", p99Ms.toFixed(2));

  histogram.reset();
}, 10_000);
```

### 논블록이 성능을 자동 보장하지 않음

논블록 모델은 대기 연결을 효율적으로 다루나 다음은 그대로 남는다

- 패킷 역직렬화 비용
- 게임 틱 계산 비용
- 데이터베이스 쿼리 지연
- 외부 API 호출
- 잠금이 있는 공유 메모리
- 과도한 로그 출력
- 큰 버퍼 복사와 가비지 컬렉션

## Overlapped I/O 혹은 비동기 I/O

비동기 I/O는 작업을 요청한 뒤 호출자가 다른 일을 하고, 나중에 결과를 통지받는 방식

### 준비 통지와 완료 통지

언제 알려주는지가 다름

| 모델           | 통지 시점              | 통지 후 작업               |
| -------------- | ---------------------- | -------------------------- |
| 준비 완료 기반 | 지금 읽거나 쓸 수 있음 | 실제 read 또는 write 수행  |
| 작업 완료 기반 | 요청한 I/O가 완료      | 완료 결과와 바이트 수 처리 |

epoll과 kqueue는 주로 준비 완료 기반 설명, IOCP는 완료 기반으로 설명

Node.js는 운영체제에 따라 다른 방식을 libuv로 감싸서 비슷한 콜백, 이벤트 API를 제공

### async와 await는 커널 비동기 I/O가 아님

TS의 async/await는 Promise 완료를 읽기 쉽게 기다리는 문법, 어떤 작업이 실제로 운영체제 비동기 I/O인지, libuv 스레드 풀을 쓰는지, JS 스레드에서 동기 실행되는지 호출한 API에 달려있음

```ts
async function misleadingExample(): Promise<number> {
  // async 함수 안이어도 반복은 JS 스레드에서 동기 실행됨
  let result = 0;

  for (let i = 0; i < 500_000_000; i += 1) {
    result += i;
  }

  return result;
}
```

### Node.js 작업 종류별 위치

| 작업                   | 일반적인 처리 방식                 |
| ---------------------- | ---------------------------------- |
| TCP, UDP 네트워크 I/O  | 논블록 소켓과 운영체제 이벤트 통지 |
| 타이머                 | 이벤트 루프가 만료된 콜백 실행     |
| 일부 파일 시스템 API   | libuv 워커 스레드 풀               |
| DNS, 암호화, 압축 작업 | libuv 워커 스레드 풀               |
| JavaScript 게임 로직   | 이벤트 루프 JavaScript 스레드      |
| Worker Threads 작업    | 별도 JavaScript 실행 스레드        |

비동기 함수 하나당 새 스레드 하나가 생성되는 건 아님

### I/O 완료 순서와 게임 로직 순서

비동기 작업은 요청한 순서와 완료 순서가 다를 수 있음. 플레이어 저장 요청 A, B를 동시에 보냈는데 B가 먼저 완료될 수 있음

순서가 중요한 상태 변경은 다음 중 하나로 통제

- 연결 또는 플레이어 단위 직렬큐
- 단조 증가 버전 번호
- 낙관적 잠금
- 멱등성 키
- 하나의 권위 있는 틱에서 상태 적용

```ts
class SerialTaskQueue {
  private tail: Promise<void> = Promise.resolve();

  enqueue(task: () => Promise<void>): Promise<void> {
    const next = this.tail.then(task, task);

    this.tail = next.catch(() => undefined);

    return next;
  }
}
```

### 취소와 타임아웃

비동기 작업은 호출 스택이 기다리고 있지 않아 별도의 취소 신호와 수명 관리가 필요

연결이 끊긴 뒤 완료된 DB 조회가 이미 사라진 세션을 다시 살리지 않도록, 세션 버전 등을 확인

## epoll

**epoll**은 Linux에 많은 파일 디스크립터 가운데 현재 I/O 가능한 대상을 효율적으로 찾기 위한 준비 상태 통지 API

```text
관심 목록 소켓 1, 소켓 2, 소켓 3, ... 소켓 10000
준비 목록: 소켓 27, 소켓 581
준비 목록 소켓만 처리
```

1. 관심 있는 소켓과 이벤트를 epoll에 등록
2. epoll_wait로 준비 이벤트를 기다린다
3. 준비된 소켓만 읽거나 쓴다
4. 모든 준비 데이터를 적절히 소비하고 다시 이벤트를 기다린다

### select, poll과 비교

| 방식   | 대규모 연결 관점                                    |
| ------ | --------------------------------------------------- |
| select | 검사할 집합 크기 제한과 반복 스캔 부담이 있음       |
| poll   | 파일 디스크립터 집합 전체를 반복 확인               |
| epoll  | 커널이 준비된 항목 목록을 제공, 활성 연결 중심 처리 |

epoll이 연결 수와 완전히 무관한 비용을 보장한다는 건 아니다. 등록,해제,이벤트 처리, 버퍼 복사, 사용자 코드 비용은 여전히 존재

대부분이 유휴 상태인 대규모 연결을 다루는데 유리

### 레벨 트리거와 엣지 트리거

| 방식            | 특성                                     | 주의                                        |
| --------------- | ---------------------------------------- | ------------------------------------------- |
| Level Triggered | 처리 가능한 상태가 남아 있으면 계속 알림 | 이해하기 쉽지만 반복 알림                   |
| Edge Triggered  | 상태가 바뀌는 순간 중심으로 알림         | EAGAIN이 나올 때까지 읽는 등 엄격 처리 필요 |

Node.js에 이를 직접 설정하는 경우는 드물다. libuv와 Node.js Stream이 세부 동작을 감싸서 개발자는 data/readable, pause/resume, write/drain 계약을 지키는 것이 더 중요

### Linux에서 Node.js 동작

```text
Linux 커널 epoll
 준비 이벤트
libuv 이벤트 루프
 Node.js 내부 콜백
net.Socket 이벤트
게임 서버 핸들러
```

Kubernetes의 Node.js Pod도 일반적으로 Linux 위에 실행되므로 epoll의 혜택을 받고 그렇다고 Pod 하나가 무제한 연결을 처리하는 건 아니고 한계도 있다

- 프로세스 파일 디스크립터 한도
- 컨테이너와 노드의 리소스 한도
- 로드밸런서의 유휴 타임아웃
- Pod 종료 유예 시간
- 단일 이벤트 루프의 CPU 한계
- 연결별 메모리와 쓰기 큐

## IOCP

**IOCP(I/O Completion Port)**는 여러 비동기 I/O 작업의 결과를 효율적으로 전달받는 기반 메커니즘

```text
앱 비동기 I/O 요청
앱 I/O 진행
완료 패킷을 Completion Port 큐에 추가
대기 중인 처리 스레드가 완료 결과 소비
```

IOCP에서 요청한 읽기 또는 쓰기가 완료되었다는 결과가 중심. 완료 결과에 성공 여부, 전송된 바이트 수, 작업을 식별할 문맥 등이 연결

### epoll, IOCP 비교

| 항목              | epoll                       | IOCP                    |
| ----------------- | --------------------------- | ----------------------- |
| 운영체제          | Linux                       | Windows                 |
| 모델              | 준비 상태 통지              | 작업 완료 통지          |
| 통지 의미         | 지금 읽기, 쓰기가 가능      | 요청한 I/O가 완료       |
| 관점              | 준비된 소켓에 실제 I/O 수행 | 완료 결과를 큐에서 소비 |
| Node.js 직접 사용 | 보통 하지 않음              | 보통 하지 않음          |
| Node.js 추상화    | libuv                       | libuv                   |

### mac, BSD의 kqueue

운영체제별로 내부 장치가 다름

| 운영체제        | libuv가 사용하는 통신 장치 |
| --------------- | -------------------------- |
| Linux           | epoll                      |
| macOS, BSD 계열 | kqueue                     |
| Windows         | IOCP                       |
| Solaris 계열    | event ports                |

Node.js 코드는 같은 net.Socket API를 사용해도 내부 구현은 운영체제에 따라 다르다

이식성은 libuv가 제공, 운영체제별 파일 디스크립터 한도와 TCP 설정, 성능 특성까지 모두 같아지는 건 아니다

### Node.js 개발자 참조

- epoll, IOCP를 직접 구현하지 않아도 원리는 알아야 장애를 해석
- 이벤트가 왔다는 사실과 앱 명령이 성공했다는 사실 구분
- 소켓 I/O는 비동기여도 JavaScript 게임 로직은 이벤트 루프를 오래 점유할 수 있음
- 운영체제 최적화보다 먼저 프레이밍, 백프레셔, 타임아웃, 큐 상한을 구현

## Node.js, NestJS 게임 서버 적용

### 전송 계층 선택

| 상황                 | 검토 방식                              | 이유                                           |
| -------------------- | -------------------------------------- | ---------------------------------------------- |
| 게임 클라이언트      | WebSocket 또는 Socket.IO               | 브라우저는 일반 raw TCP 소켓을 직접 열 수 없음 |
| 커스텀 프로토콜      | node:net 또는 별도 네트워크 게이트웨이 | 길이 접두사와 프로토콜을 직접 통제             |
| NestJS RPC           | Nest Microservice TCP, gRPC            | 프레임워크 규약과 요청, 응답 패턴 활용         |
| 네이티브 게임        | UDP, QUIC 계열 별도 검토               | 손실 허용과 낮은 지연 정책 가능                |
| 로그인,결제,운영 API | HTTPS                                  | 인증, 프록시, 관측 도구 활용이 쉬움            |

### NestJS에서 TCP 서버 수명 관리

raw TCP 서버를 NestJS 프로세스 안에 둘 경우, 시작과 종료 생명주기에 연결

import 시점에 즉시 listen을 호출하면 테스트와 정상종료가 어렵다

```ts
import {
  BeforeApplicationShutdown,
  Injectable,
  OnApplicationBootstrap,
} from "@nestjs/common";

import net from "node:net";

@Injectable()
export class RawTcpGateway
  implements OnApplicationBootstrap, BeforeApplicationShutdown
{
  private readonly sockets = new Set<net.Socket>();

  private server?: net.Server;

  async onApplicationBootstrap(): Promise<void> {
    this.server = net.createServer((socket) => {
      this.sockets.add(socket);

      socket.setNoDelay(true);

      socket.on("data", (chunk) => this.handleChunk(socket, chunk));

      socket.on("error", () => undefined);

      socket.on("close", () => this.sockets.delete(socket));
    });

    await new Promise<void>((resolve, reject) => {
      const server = this.server;

      if (!server) {
        reject(new Error("server was not created"));

        return;
      }

      server.once("error", reject);

      server.listen(4000, "0.0.0.0", () => {
        server.off("error", reject);

        resolve();
      });
    });
  }

  async beforeApplicationShutdown(): Promise<void> {
    const server = this.server;

    if (!server) {
      return;
    }

    // 새 연결 수락을 먼저 중단
    const closed = new Promise<void>((resolve) => {
      server.close(() => resolve());
    });

    // 기존 연결은 정상 종료 요청
    for (const socket of this.sockets) {
      socket.end();
    }

    await closed;
  }

  private handleChunk(socket: net.Socket, chunk: Buffer): void {
    // 연결별 프레이머, 세션 검증 전달
    console.log(socket.remoteAddress, chunk.length);
  }
}
```

## 소켓 서버 타임아웃

하나의 timeout 값으로 모든 상황을 처리하지 않고 목적별로 나눔

| 타임아웃       | 시작                          | 만료 시 처리              |
| -------------- | ----------------------------- | ------------------------- |
| 연결 타임아웃  | 외부 서버에 connect 시작      | 연결 취소와 제한된 재시도 |
| 인증 타임아웃  | TCP 연결 직후                 | 미인증 연결 종료          |
| 유휴 타임아웃  | 마지막 정상 메시지 수신 후    | ping 확인 또는 연결 종료  |
| 요청 타임아웃  | requestId가 있는 명령 전송 후 | 실패 응답, 중복 실행 방지 |
| 종료 유예 시간 | 서버 종료 시작                | 남은 연결 강제 종료       |

Node.js의 socket.setTimeout은 상태를 알려 주는 timeout 이벤트를 발생, 연결을 자동으로 닫지는 않는다. 이벤트 핸들러에서 end 또는 destroy 정책을 명시

```ts
socket.setTimeout(60_000);

socket.on("timeout", () => {
  socket.end();
});
```

로드밸런서, NAT, 모바일 네트워크 연결 정책을 고려해 앱 ping과 세션 만료 규칙을 별도로 둠

## 소켓 프로토콜 보안 체크

- 프레임 길이는 본문을 할당하기 전에 최대값을 검사
- 인증 전 허용하는 메시지 종류를 최소화
- 메시지 타입, 필수 필드, 숫자 범위, 문자열 길이 검증
- 연결별 초당 메시지 수와 바이트 수에 제한을 둔다
- 알 수 없는 메시지 타입과 잘못된 상태 전이 거부
- requestId를 사용해 중복 결제와 중복 보상을 막음
- 소켓 오류 로그에 인증 토큰이나 패킷 원문 전체를 남기지 않음
- 느린 클라이언트 송신 큐에 상한을 둔다
- IP 제한만 믿지 말고 계정,세션,기기 단위 정책을 조합
- TLS가 필요한 연결은 node:tls 또는 검증된 프록시 계층을 사용

## 자주 헷갈리는 부분

1. **write가 true면 상대가 처리했다고 생각**

- 로컬 버퍼 처리 상태. 중요한 명령은 앱 응답을 확인

2. **data 이벤트 한 번을 패킷 하나로 생각**

- TCP는 바이트 스트림, 길이 접두사 등으로 프레이밍

3. **write가 false여도 계속 사용**

- drain을 기다리고 연결별 큐 상한을 적용

4. **setTimeout을 호출하면 소켓이 자동 종료된다고 생각**

- timeout은 알림, end 또는 destroy를 직접 호출

5. **async 함수를 사용하면 무거운 계산도 논블록이라고 생각**

- 동기 계산은 이벤트 루프를 막고 워커나 별도 프로세스로 분리

6. **backlog를 최대 동시 접속자 수로 이해**

- 아직 수락되지 않은 연결 대기 큐와 관련된 값

7. **TCP keepalive만 있으면 게임 heartbeat가 필요 없다고 생각**

- 감지 목적과 시간이 다르다. 세션 규칙은 앱에서 정의

8. **epoll 또는 IOCP를 직접 써야 고성능 Node.js 서버라고 생각**

- Node.js는 libuv를 통해 이미 운영체제의 효율적인 I/O 장치를 사용

## 요약

- 블로킹 소켓은 I/O가 가능할 때까지 호출 스레드를 기다리게 한다
- 논블록 소켓은 즉시 반환, 효율적인 처리를 위해 I/O 가능 상태 통지 필요
- Node.js의 네트워크 API libuv와 이벤트 루프를 통해 논블록, 비동기 방식으로 동작
- TCP의 write는 원격 애플리케이션 처리 완료를 의미하지 않음
- TCP는 바이트 스트림이므로 메시지 프레이밍이 반드시 필요
- 송신, 수신 버퍼는 속도 차이를 흡수하나 무한하지 않음
- socket.write가 false면 백프레셔 신호로 받아들이고 drain을 기다림
- Linux의 epoll은 준비 상태, Windows의 IOCP는 작업 완료를 중심으로 통지
- 비동기 네트워크 I/O와 JavaScript CPU 연산 별개
- 게임서버는 최신 상태 우선 정책, 큐 상한, 타임아웃, 정상 종료, 관측 지표를 함께 설계
