# 2장 컴퓨터 네트워크 - 네트워크 기초

---

## 1. 컴퓨터 네트워크를 구성하는 기기

네트워크는 컴퓨터들을 연결하는 인프라이다. 주요 구성 기기는 다음과 같다

| 기기                            | 역할                                           | OSI 계층            |
| ------------------------------- | ---------------------------------------------- | ------------------- |
| **허브(Hub)**                   | 연결된 모든 포트에 데이터 전달 (브로드 캐스트) | 계층 1 (물리)       |
| **스위치(Switch)**              | MAC 주소 기반으로 특정 포트에만 데이터 전달    | 계층 2 (데이터링크) |
| **라우터(Router)**              | IP 주소 기반으로 최적 경로를 찾아 패킷 전달    | 계층 3 (네트워크)   |
| **NIC(Network Interface Card)** | 컴퓨터를 네트워크에 연결하는 하드웨어          | 게층 1~2            |

```
일반적인 네트워크 구성

인터넷
  ↕
라우터 (ISP 제공 / 공유기)
  ↕
스위치 (사무실/데이터센터 내부망)
  ↕  ↕  ↕
 PC  서버  서버

```

## 2. OSI 모델

**OSI(Open Systems Interconnection) 모델**은 네트워크 통신을 7개 계층으로 나눠 표준화한 모델이다. 각 계층은 하위 계층의 서비스를 이용하고 상위 계층에 서비스를 제공한다.

```
7. 응용 계층 (Application) - HTTP, WebSocket, gPRC
6. 표현 계층 (Presentation) - 데이터 인코딩, 암호화(LTS)
5. 세션 계층 (Session) - 연결 관리, 세션 제어
4. 전송 계층 (Transport) - TCP, UDP - 포트 번호
3. 네트워크 계층 (Network) - IP, 라우팅 IP주소
2. 데이터링크 계층 (Data Link) - 이더넷, MAC 주소
1. 물리 계층 (Physical) - 케이블, 전기 신호
```

게임 서버 개발자가 주로 다루는 계층은 **계층 3(IP)**과 **계층 4(TCP/UDP)**이다. HTTP/WebSocket은 계층 7에 해당한다.

### OSI 계층 2 - 데이터링크 계층

이더넷이 여기에 속한다. **MAC 주소(Media Access Control Address)**를 사용해 같은 네트워크(LAN) 내의 기기를 식별한다.

- MAC 주소: 48비트, 하드웨어에 고정된 고유 주소
- 같은 스위치에 연결된 기기 간 통신에 사용
- 라우터를 넘어가면 MAC 주소가 변경된다 (IP 주소는 유지한다)

### OSI 계층 3- 네트우 ㅓ크 계층

**IP(Internet Protocol)**이 여기에 속한다. 서로 다른 네트워크를 연결하고 **라우팅(최적 경로 탐색)**을 담당한다.

- IPv4: 32비트 주소(예: `192.168.0.1`)
- IPv6: 128비트 주소(예: `2001:0db8:85a3::8a2e:0370:7334`)

## 3. 인터넷

**인터넷**은 전 세계의 수많은 네트워크를 하나로 연결한 거대한 네트워크이다. IP 프로토콜을 공통 언어로 사용한다.

```
인터넷 구조 - 단순화
한국 ISP 망 ──── 인터넷 백본(광케이블) ──── 미국 ISP 망
     ↕                                          ↕
내 컴퓨터                                   미국 서버
```

게임 서버는 데이터센터(AWS, GCP, Azure 등)에 위치, 플레이어는 인터넷을 통해 연결된다. 이 구간이 레이턴시(지연 시간)가 게임 품질에 영향을 미친다.

## 4. 컴퓨너 네트워크 데이터

네트워크로 전송되는 데이터의 구조 방식은 두가지로 나뉜다.

### 스트림 형식 (Stream)

데이터가 **경계 없이 연속적인 바이트 흐름**으로 전달된다. TCP가 대표적이다.

```
스트림 형식

전송: [Hello][World][GameData]
수신: [HelloWorldGa][meData] <- 경계가 사라진다

-> 수신 측에서 메시지 경계를 직접 구분해야 한다
```

스트림에서 메세지를 구분하는 방법:

- **고정 길이:** 항상 N바이트를 하나의 메시지로 읽는다
- **구분자**: 특정 문자(예: `\n`)로 메세지 끝 표시
- **길이 접두사**: 메시지 옆에 길이 정보를 붙인다(게임 서버에서 많이 사용된다)

```js
// 길이 접두사 방식 패킷 파싱 (Node.js)
class PacketParser {
  private buffer = Buffer.alloc(0);

  // 수신 데이터를 버퍼에 누적하고 완성된 패킷 추출
  feed(data: Buffer): Buffer[] {
    this.buffer = Buffer.concat([this.buffer, data]);
    const packets: Buffer[] = [];

    while (this.buffer.length >= 4) {
      // 4바이트에서 패킷 길이 읽기
      const packetLength = this.buffer.readUInt32BE(0);

      if (this.buffer.length < 4 + packetLength) {
        break;
      }
      const packet = this.buffer.slice(4, 4 + packetLength);
      packets.push(packet);
      // 처리한 만큼 제거
      this.buffer = this.buffer.slice(4 + packetLength);
    }
    return packets;
  }

  // 메시지를 길이 접두사 포함 버퍼로 직렬화
  static serialize(messeage: objecdt): Buffer {
    const body = Buffer.form(JSON.stringify(message), 'utf8');
    const header = Buffer.alloc(4);
    header.wrtieUInt32BE(body.length, 0); // 4바이트에 길이 기록
    return Buffer.concat([header, body]);
  }
}
```

### 메시지 형식(Message / Datagram)

데이터가 **독립적인 단위(패킷)**로 전달된다. UDP가 대표적이다.

```
메시지 형식
전송: [패킷 A] [패킷 B] [패킷 C]
수신: [패킷 A] [패킷 B] [패킷 C] <- 각 패킷의 경계가 보존된다
-> 수신 측에서 별도 파싱 불필요, 대신 크기 제한이 있다
```

UDP는 하나의 데이터그램이 그대로 수신되어 경계 처리가 단순하다. 단, MTU(최대 전송 단위, 보통 1500바이트)를 초과하면 분열(Fragmentation)이 발생하여 패킷 크기를 관리해야 한다.

## 컴퓨터 네트워크 식별자

네트워크에서 특정 컴퓨터와 프로세스를 식별하는 요소들이다

### IP 주소

네트워크 상의 컴퓨터 주소이다.

- **공인 IP(Public IP):** 인터넷에서 유일한 주소
- **사설 IP(Private IP):** 내부 네트워크에서만 사용(`192.168.x.x`, `10.x.x.x`, `172.16~31.x.x`)

### 포트 번호 (Port)

같은 컴퓨터 안의 어떤 프로세스(서비스)에 접속 할 지 구분한다. 0~65535 범위

```
IP 주소: 포트 = 특정 컴퓨터의 특정 프로세스
예: 192.168.0.10:3000 -> 3000번 포트에서 실행중인 서버
```

| 포트 범위   | 용도                                           |
| ----------- | ---------------------------------------------- |
| 0~1023      | 잘 알려진 포트 (HTTP: 80, HTTPS: 443, SSH: 22) |
| 1024~49151  | 등록된 포트 (애플리케이션이 사용)              |
| 49152~65535 | 동적/사설 포트 (임시 클라이언트 포트)          |

### dns(Domain Name System)

도메인 이름을 IP주소로 변환하는 시스템이다.

```
game.example.com -> DNS 조회 -> 1.2.3.4
```

```JS
// NestJS에서 DNS 조회
import * as dns from "dns/promises";

const addresses = await dns.lookup("game.example.com");
console.log(addresse); // { address: '1.2.3.4', family: 4 }
```

### 소켓 (Socket)

**IP 주소 + 포트 번호**의 조합, 네트워크 통신의 양쪽 끝점이다.

```
클라이언트 소켓: 203.0.113.5:54321
서버 소켓:          1.2.3.4:3000

-> 이 쌍(4-tuple)이 하나의 TCP 연결을 유일하게 식별
```

## 컴퓨터 네트워크의 품질과 특성

### 네트워크 품질을 저해하는 것

| 요인              | 설명                              | 게임 서버 영향              |
| ----------------- | --------------------------------- | --------------------------- |
| 패킷 유실         | 패킷이 목적지에 도달하지 못한다   | 위치 동기화 오류, 입력 누락 |
| 지터(Jitter)      | 패킷 도착 간격이 불규칙한다       | 움직임이 끊김(끊김 현상)    |
| 레이턴시(Latency) | 패킷 전달에 걸리는 시간           | 반응 지연, 입력 지연        |
| 대역폭 부족       | 한 번에 전송 가능한 데이터량 한계 | 패킷 밀림, 추가 지연        |

### 전송 속도와 전송 지연 시간

**대역폭(Bandwidth)**과 **레이턴시(lantency)**는 별개의 개념이다.

```
대역폭, 레이턴시 비유
고속도로 폭(차선 수) = 대역폭 (많을수록 한번에 많이 보낸다)
서울 <- 부산 거리 = 레이턴시 (아무리 넓어도 거리는 단축이 안된다)
```

- **왕복시간(RTT, Round Trip Time)**: 패킷을 보내고 응답을 받기까지 시간
- 게임에서 RTT가 낮을수록 반응성이 좋다

### 네트워크 품질 기준 세 가지

1. **레이턴시(Latency)**: 전달 시간 - ms 단위
2. **처리량(Throughtput)**: 단위 시간당 전달 데이터량 - Mbps 단위
3. **패킷 유실물(Packet Loss Rate)**: 전체 패킷 중 유실 비율 - % 단위

### 무선 네트워크 품질

Wi-Fi와 모바일(LET/5G) 네트워크는 유선보다 불안정하다.

- **지터가 크다:** 신호 간섭, 기지국 혼잡
- **패킷 유실이 잦다**: 전파 환경 변화
- **레이턴시 변동이 크다**: 핸드오버(기지국 전환)시 순간 지연

모바일 게임 서버 설계 시 이러한 특성을 고려해야 한다

```js
// NestJS: 네트워크 품질 모니터링 (RTT 측정 ping/pong)
@WebSocketGateway()

    // 클라이언트가 보낸 timestamp를 그대로 반환
    client.emit('pong', { timestamp: payload.timestamp });
  }
}
```

## UDP 네트워킹

**UDP(User Datagram Protocol)**은 연결 없이 데이터그램을 전송하는 프로토콜이다.

### 특징

| 항목      | 내용                            |
| --------- | ------------------------------- |
| 연결      | 비연결형 (연결 수립 과정 없음)  |
| 순서 보장 | ❌                              |
| 도달 보장 | ❌                              |
| 속도      | 빠름 (오버헤드 낮음)            |
| 헤더 크기 | 8바이트 (TCP 20바이트보다 작음) |

### 게임에서 UDP를 쓰는 이유

- **실시간 위치 동기화:** 이전 위치 데이터는 최신 데이터로 대체되어 유실돼도 무방하다
- **낮은 레이턴시:** TCP 재전송 대기 없이 즉시 전송
- **빠른 FPS, 레이싱 게임**: 약간의 유실보다 낮은 지연이 더 중요하다

```
UDP 패킷 구조

출발지 포트(2바이트) -> 목적지 포트(2바이트) -> 데이터 길이(2바이트) -> 체크섬(2바이트) -> 데이터 (가변 길이)
```

```JS
  const response = Buffer.from("pomg");
```

## TCP 네트워킹

**TCP(Transmission Control Protocol)** 는 연결 기반의 신뢰성 있는 전송 프로토콜이다.

### 특징

| 항목      | 내용                                 |
| --------- | ------------------------------------ |
| 연결      | 연결형 (3-way handshake로 연결 수립) |
| 순서 보장 | ✅                                   |
| 도달 보장 | ✅ (재전송 메커니즘)                 |
| 속도      | 상대적으로 느림 (오버헤드 있음)      |
| 흐름 제어 | ✅ (수신 버퍼 기반)                  |
| 혼잡 제어 | ✅ (네트워크 상태 감지)              |

### TCP 3-wat Handshake(연결 수립)

```
클라이언트                    서버
    │──── SYN ───────────────→│   "연결하고 싶어요"
    │←─── SYN + ACK ──────────│   "좋아요, 연결합시다"
    │──── ACK ───────────────→│   "확인했습니다"
    │                          │
    │←── (데이터 송수신) ──────│
```

### TCP 4-way Handshake(연결 종료)

```
클라이언트                    서버
    │──── FIN ───────────────→│   "연결 끊겠습니다"
    │←─── ACK ────────────────│   "알겠습니다"
    │←─── FIN ────────────────│   "저도 끊겠습니다"
    │──── ACK ───────────────→│   "확인했습니다"
```

### 게임에서 TCP를 쓰는 이유

- **로그인, 캐릭터 데이터 로드:** 절대 유실되면 안 되는 중요 데이터
- **채팅:** 순서와 도달이 보장되어야 한다
- **거래, 아이템 획득:** 데이터 정합성 필수
- **MMORPG의 대부분 통신**

```js
// NestJS WebSocket (Socket.IO — TCP 기반)
import {
  WebSocketGateway, WebSocketServer, SubscribeMessage,
  OnGatewayConnection, OnGatewayDisconnect
} from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';

@WebSocketGateway({ cors: true })
export class GameGateway implements OnGatewayConnection, OnGatewayDisconnect {
  @WebSocketServer()
  server: Server;

  private connectedPlayers = new Map<string, PlayerInfo>();

  handleConnection(client: Socket) {
    console.log(`플레이어 접속: ${client.id}`);
  }

  handleDisconnect(client: Socket) {
    const player = this.connectedPlayers.get(client.id);
    if (player) {
      // 같은 룸의 다른 플레이어에게 퇴장 알림
      client.to(player.roomId).emit('playerLeft', { playerId: client.id });
      this.connectedPlayers.delete(client.id);
    }
  }

  @SubscribeMessage('joinRoom')
  handleJoinRoom(client: Socket, payload: { roomId: string; playerName: string }) {
    client.join(payload.roomId);
    this.connectedPlayers.set(client.id, {
      id: client.id,
      name: payload.playerName,
      roomId: payload.roomId,
    });

    // 룸의 다른 플레이어에게 알림
    client.to(payload.roomId).emit('playerJoined', {
      playerId: client.id,
      playerName: payload.playerName,
    });
  }
}
```

## 패킷 유실 시 UDP와 TCP에서 현상

같은 패킷 유실이 발생해도 UDP와 TCP의 반응은 완전히 다르다

### UDP에서 패킷 유실

```
전송: [패킷1][패킷2][패킷3][패킷4]
수신: [패킷1]      [패킷3] [패킷4] <- 패킷2 유실, 그냥 지나친다
-> 유실된 패킷 무시, 이후 패킷은 정상처리
-> 게임에서 위치 데이터 유실 = 잠깐 튀는 현상
```

### TCP에서 패킷 유실

```
전송: [패킷1] [패킷2] [패킷3] [패킷4]
수신: [패킷1] 유실    [패킷3]  [패킷4]

-> TCP는 패킷2를 재전송 요청
-> 패킷2가 도착할 때까지 패킷3, 4도 응용 계층에 전달을 못한다
-> HOL(Head-of-Line) Blocking: 유실 하나가 이후 데이터 전체를 지연시킨다
```

이 HOL Blocking 때문에 실시간 게임에서 UDP가 선호된다. 패킷 하나의 유실이 이후 패킷 전체를 막지 않는다.

실시간 FPS 게임 패킷 유실 비교

UDP: 프레임 t=100ms 데이터 유실 -> t=110ms 데이터로 바로 업데이트

TCP: 프레임 t=100ms 데이터 유실 -> 재전송 대기 -> 100~150ms 구간 모두 지연

## 주로 사용하는 메시지 형식

게임 서버에서 패킷을 직렬화하는 주요 포맷

### JSON

```json
{
  "type": "playerMove",
  "playerId": 12345,
  "position": { "x": 100.5, "y": 0.0, "z": -200.3 },
  "timestamp": 16200
}
```

- 장점: 사람이 읽기 쉽고, 디버깅이 용이하고, 언어/플랫폼이 무관
- 단점: 크기가 크고 파싱 비용이 높다
- 적합한 용도: REST API, 로그인/캐릭터 데이터 등 빈도가 낮은 통신

### Protocol Buffers (protobuf)

Google이 만든 이진 직렬화 포맷이다.

```protobuf
// player.proto
message PlayerMove {
  uint32 player_id = 1;
  float x = 2;
  float y = 3;
  float z = 4;
  uint64 timestamp = 5;
}
```

- 장점: JSON 대비 작은 크기, 파싱 속도 빠름
- 단점: 사람이 읽기 어렵고, 스키마 관리가 필요
- 적합한 용도: 실시간 위치 동기화, 빈도 높은 게임 상태 동기화

```js
// NestJS에서 protobuf 사용 예시
import { Injectable } from '@nestjs/common';
import * as protobuf from 'protobufjs';

@Injetable()
export class ProtobufService {
  private PlayerMove: protobuf.Type;

  async onModuleInit() {
    const root = await protobuf.load('src/proto/player.proto');
    this.PlayerMove = root.lookupType('PlayerMove');
  }

  encode(data: object): Buffer {
    const message = this.PlayerMove.create(data);
    reutrn Buffer.from(this.PlayerMove.encode(message.finish()));
  }

  decode(buffer: Buffer): object {
    return this.PlayerMove.decode(buffer) as unknown as object;
  }
}
```

### MessagePack

JSON과 호환되고 이진 포맷으로 직렬화한다.

- JSON보다 작은 크기
- 별도 스키마 불필요 (JSON처럼 구조 자유)
- protobuf보다 크나 도입 비용이 낮다

## 네트워크 주소 변환 (NAT)

**NAT(Network Address Translation)**는 사실 IP를 공인 IP로 변환해 인터넷 통신을 가능하게 하는 기술이다.

```
NAT 동작 원리

사설 IP (내부망)         NAT 장비(공유기)     인터넷
192.168.0.10:54321 -> 공인 IP:1024   ->   게임서버
192.168.0.11:54322 -> 공인 IP:1025   ->   게임서버
192.168.0.12:54323 -> 공인 IP:1026  ->   게임서버
```

### P2P 게임에서 NAT의 문제

P2P(Player-to-Player) 직접 연결 방식의 게임, NAT 뒤에 있는 두 플레이어가 직접 연결하려면 **NAT 통과(NAT Traversal)** 기술이 필요하다.

- **STUN:** 자신의 공인 IP/포트를 알아내는 방법
- **TURN:** 릴레이 서버를 통한 우회 연결 (NAT 통과 실패 시 사용)
- **ICE:** STUN/TURN을 조합한 최적 경로 탐색 (WebRTC에서 사용)

### 게임 서버 방식 NAT 우회

중앙 게임 서버를 두면 클라이언트는 모두 서버에 아웃바운드로 연결하여 NAT 문제가 없다. 대부분의 온라인 게임이 이 방식을 채택한다.

```
[중앙 서버 방식 — NAT 문제 없음]

플레이어A (NAT 뒤) ──→ 게임 서버 (공인 IP) ←── 플레이어B (NAT 뒤)
                   ←── 서버가 중계 ──→
```
