# 감으로 판단하지 말고 tinker로 직접 찍어보자 — 라이브 Pod 재현 디버깅

- 운영에서 접근 가능 여부 판정 로직이 계속 `false`를 반환하는 이슈 발생
- 원인을 추측하는 대신, `exec-pod.sh`로 운영 Pod에 직접 들어가 `tinker`로 실제 데이터와 조건식을 그 자리에서 실행해 확인
- 정상 케이스와 비정상 케이스를 나란히 비교하며 원인 범위를 데이터 → 로직 순으로 좁혀나감
- 실제 원인은 거창한 게 아니라 단순한 코드 로직 오류였음 — 오히려 그래서 "추측 대신 확인"하는 과정 자체가 이 케이스의 핵심

## 1. 상황

접근 가능 여부를 판정하는 로직이 왜 계속 `false`를 반환하는지 코드만 봐서는 원인이 바로 보이지 않는 상태였다. 이런 경우 로컬에서 아무리 코드를 들여다봐도 답이 안 나올 때가 많다 — 결국 실제 운영 데이터로 직접 찍어보는 수밖에 없다.

## 2. 운영 Pod 접속

배포 스크립트로 운영 Pod에 직접 접속한다.

```bash
$ ./exec-pod.sh api-server prod
Selected pod: api-server-7fdf8b6dbc-qlbsf
Defaulted container "api-server" out of: api-server, api-server-redis

/var/www/html # php artisan tinker
```

`tinker` 진입 후, 확인할 때 필요한 클래스/네임스페이스를 미리 `use`로 로드해두면 이후 확인 과정이 훨씬 수월하다.

```php
> use App\Models\EventSchedule;
> use App\Services\AccessService;
> use Illuminate\Support\Carbon;
```

## 3. 실제 데이터부터 눈으로 확인

의심되는 레코드를 tinker에서 직접 조회한다.

```php
> $schedule = EventSchedule::find(207);
= App\Models\EventSchedule {#6420
    id: 207,
    period_start_at: "2026-08-06 11:00:00",
    period_end_at: "2026-08-13 10:59:59",
    ...
  }
```

값 자체는 눈으로 보기에 이상이 없었다. 여기서 중요한 건 "데이터는 정상"이라는 사실을 먼저 확정해두는 것 — 그래야 이후 원인 범위를 데이터 문제와 로직 문제로 나눠서 좁혀갈 수 있다.

## 4. 서비스 코드의 조건식을 그 자리에서 그대로 실행

코드를 고쳐서 배포하지 않고, 실제 서비스 코드에 있는 조건식을 tinker에 그대로 붙여넣어 즉시 실행해본다.

```php
> $result =  !is_null($schedule->period_start_at)
        && !is_null($schedule->period_end_at)
        && $schedule->period_start_at->lte(now())
        && $schedule->period_end_at->gte(now());
= false
```

이렇게 하면 "이 조건식이 실제 운영 데이터를 만났을 때 어디서 `false`가 나오는지"를 재기동이나 배포 없이 바로 그 자리에서 확인할 수 있다.

## 5. 다른 레코드와 나란히 비교해서 패턴 좁히기

케이스 하나만 보고 판단하지 않고, 이미 종료된 스케줄과 진행 중이어야 하는 스케줄을 나란히 놓고 같은 조건식을 돌려본다.

```php
> $closed = EventSchedule::find(206); // 이미 종료된 스케줄
> $open   = EventSchedule::find(207); // 진행 중이어야 하는 스케줄
```

두 결과를 나란히 찍어보면, `false`가 "예상되는 케이스(이미 종료된 스케줄)"에서만 나오는지, 아니면 "예상 못한 케이스(진행 중이어야 할 스케줄)"에서도 나오는지 구분할 수 있다. 이 비교를 통해 원인 범위를 데이터 쪽이 아니라 조건식/로직 쪽으로 좁힐 수 있었다.

## 6. 결론

파고 들어가 보니 원인은 별다른 게 아니라, 조건식 안에 있던 단순한 코드 로직 오류였다. 오히려 그래서 이 케이스가 기억에 남는다 — 원인이 단순했던 만큼 감으로 추측했다면 훨씬 오래 헤맸을 것이고, tinker로 직접 찍어보고 하나씩 좁혀나가는 과정이 없었다면 원인을 특정하는 데 더 오래 걸렸을 것이다.

## 7. 실무 체크리스트

| 단계 | 하는 일                                                      |
| ---- | ------------------------------------------------------------ |
| 1    | 원인을 추측하지 말고 운영 Pod에 직접 들어가 tinker로 진입    |
| 2    | 의심 레코드를 조회해서 데이터 자체는 정상인지 먼저 확정      |
| 3    | 서비스 코드의 조건식을 tinker에 그대로 붙여넣어 즉시 실행    |
| 4    | 정상 케이스와 비정상 케이스를 나란히 비교해 원인 범위를 좁힘 |
| 5    | 데이터 문제인지 로직 문제인지 구분한 뒤에 실제 코드 수정     |

## 실무 한 마디

> 운영 이슈는 재현이 반이다. 로컬에서 아무리 코드를 들여다봐도 안 보이던 원인이, 운영 Pod에 직접 들어가 실제 데이터로 조건식을 한 줄씩 실행해보면 순식간에 드러나는 경우가 많다. tinker는 "고치는 도구"가 아니라 먼저 "확인하는 도구"로 쓰는 습관이 중요하다.
