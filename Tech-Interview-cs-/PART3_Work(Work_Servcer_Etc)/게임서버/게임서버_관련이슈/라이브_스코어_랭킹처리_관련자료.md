## 라이브 스코어 보정, 랭킹 처리 완료 관한 이슈

특정 계정의 스코어(타수)가 버그로 인해 비정상적인 값으로 기록되는 이슈 확인
스코어를 기준으로 계산되는 최종점수, 시즌, 합산기록, 랭킹 점수까지 맞춰야 순위와 보상이 나오는 구조

해당 보정 절차를 라이브에 바로 적용하기 전, 스케줄러가 정상 흐름을 그대로 타고 지나가서 동작이 되는지 문제를 검증하는 것이 필요하였다.
현재 배포되어 있는 개발서버에 동일한 상황을 재현, 스케줄러를 강제로 돌리고 검증 과정에서 스코어 보정이 랭킹 집계 테이블까지 전파되는 과정을 확인하는 절차를 거치게 되었다.

---

### 문제 확인 샷 거리값이 튀었다

문제가 된 샷 기록을 확인하니 거리 값이 정상 범위보다 정확히 10배 커져 있었다. 예시로 표현하면 다음과 같은 상태였다.
정상 범위: 수백 단위
실제 저장된 값: 3520 <- 정상이면 352정도

테스트 계정의 샷 기록에서 해당 값을 직접 보정했다. (DB에 들어가서 직접 조정)

---

### 테스트 계정으로 먼저 검증, 연관 값 전부 동기화 -> 다른 계정으로 순위 확인

샷 거리 값만 고치고 끝이 아닌, 값에서 파생되는 최종 점수, 시즌 합산 기록, 랭킹 점수까지 함께 갱신해 랭킹에 정상 반영하였다.

해당 DB에 관련된 yard값과 최종 점수를 직접 수정하여 진행하였다. 그리고 다른 계정으로 게임 클라이언트에 접속해 랭킹 화면에서 순외가 실제로 바뀌었는 지 확인했다. DB 값 뿐만 아니라 실제 유저가 보는 화면 기준으로 순위 변동이 반영되는 지 확인하였다.

---

### 스케줄러르 강제로 작동시켜 다음날 보상 지급까지 검증(바뀐 순위로)

랭킹 순위 변경까지 확인하였고, 이후 해당 바뀐 랭킹 순위가 실제로 다음날 보상에 제대로 이어져서 적용되는지 확인을 했다.
배치가 하루에 한 번만 도는 구조로 되어 있어 실제 시간을 기다리는 대신, 서버 시간을 강제로 이동시켜 확정 배치를 돌려봤다.

```bash
php artisan tinker
```

```php
use App\Services\ConfigBootstrapper;
use App\Services\Season\SeasonCloseoutServices;
use Illuminate\Support\Carbon;

// 스케줄러가 랭킹을 확정하는 시점(다음날 집계)로 서버 시간을 이동
Carbon::setTestNow('2026-06-30 00:01:01');

ConfigBootstrapper::warmUp();

$closeoutHandler = new SeasonCloseoutService();

$snapshotOutcome = $closeoutHanlder->refreshDailySnapshotBatch();
$lockOutcome = $closeoutHandler->lockInFinalStandings();
```

서버 시간을 확정 시각으로 이동시켜 배치를 돌리고, 유저 디버그 메뉴로 클라이언트 시간을 다음날 보상 수령 시각으로 이동시켜 보상 목록 조회(GetList)를 호출했다.
서버 시간 이동 (당일 집계 확정 시각, 스케줄러 확정 배치 실행) -> 유저 디버그 시간 이동(다음날 보상 수령 확인, 보상 목록 조회) -> 결과 확인(게임 클라, 보상 지급 여부 확인)

2026-06-30 13:01:00으로 이동시켰을 때 해당 계정에 정상적으로 보상을 받을 수 있는 것을 확인하였다. 테스트 계정 기준으로 yard값 수정 -> 랭킹 반영 -> 다음날 보상 지급의 흐름을 확인할 수 있었다.

### 라이브 적용 중 발견된 이슈

테스트 계정에서 전체 흐름 및 과정, 보상을 확인 하고 실제 문제가 됐던 라이브 계정에 적용하였다. 관련 yard 점수 변경 등을 확인.
스코어 데이터는 정상적으로 보정하였고, 해당 값을 자동으로 집계하여 업데이트하는 배치가 이미 지나갔기에 랭킹 응답과 실제 보정된 기록이 서로 다른 값을 가리키는 상황이 생겼다.

관련된 랭킹 점수가 변하지 않고 상세 데이터를 조회할 시 에러가 나오는 현상을 확인하였다. 이에 확인해보니 응답쪽에서 recoredAt 필드가 null로 나왔는데, 이는 랭킹 집계 테이블의 점수와 일치하는 플레이 기록이 없어서 발생한 증상임을 파악하였다.
해당 시점에는 직접 관련 도전 최고 값을 디비를 통하여 수정을 하였다.

---

### 랭킹 점수를 보정하였을 때 최고 점수에 맞춰 기입

랭킹 집계 테이블의 점수를 보정한 도전 최고 점수 값에 맞춰 직접 업데이트하였다.
해당 값을 직접 채워 넣은 뒤, 현재 시즌은 랭킹을 조회하는 시점에 순위를 다시 계산하는 구조여서 별도 배치 없어도 순위가 자동으로 재계산되었고 에러 없이 동작하는 것을 확인하였다.
이후 라이브 계정을 가지고 있는 기획팀에서 확인했을 때, 다른 유저 계정에서도 해당 계정의 상세 기록과 순위를 정상적으로 조회를 하였다.

### 검증

마지막으로 tinker 쿼리로 랭킹 집계 데이터와 배치 확정 상태를 각각 확인하여 이슈처리를 확인하였다.

```php
// 보정된 랭킹 확정 데이터 확인
\App\Models\LeaderboardSnapshotLock::query()
    ->where('user_id', 71890)
    ->where('game_mode', 1)
    ->where('event_id', 208)
    ->where('round_no', 3)
    ->where('lock_type', 1)
    ->first()?->toArray();

// 해당 회차의 배치 확정 상태 확인
\App\Models\BatchExecutionLog::query()
    ->where('game_mode', 1)
    ->where('event_id', 208)
    ->where('round_no', 3)
    ->where('lock_type', 1)
    ->first()?->toArray();
```

---

> 랭킹 집계처럼 스케줄러 배치에 의존해서 갱신되는 값은, 원본 데이터를 고쳐도 배치 시간이 지나면 반영되지 않는다. 해당 경우 원본 기준으로 직접 채워넣어 해당 이슈 있는 데이터들, 랭킹 관련 점수들을 직접 수정하는 것이 훨씬 낫다. 랭킹 조회 로직이 저장된 순위가 아닌 조회 시점에 점수 기준으로 순위를 다시 계산하는 구조여서도 가능하였다.

테스트 계정으로 전체 흐름(값 보정 -> 랭킹 반영 -> 스케줄러를 활용한 다음날 보상 확인)을 먼저 검증 및 확인하여, 라이브에서 랭킹 점수가 자동 반영되지 않아도 어느 값을 맞추고 적용하는지 판단할 수 있었다. 해당 부분 관련하여 대응하는 방식을 인지하였고 명령어, 해당 흐름 등을 인지하였다.
