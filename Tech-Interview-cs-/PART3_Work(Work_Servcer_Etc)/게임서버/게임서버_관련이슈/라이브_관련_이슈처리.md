# 서버는 정상, 클라이언트 이슈 - 협력 점수 관련 이슈

## 정리

"미니게임을 선택하면 오류 99999가 뜨고 타이틀 화면으로 튕긴다"

같음 문의가 3건 접수되었다는 로그를 확인했다. 원인을 찾으려고 각종 라이브 로그를 확인하고, 기획팀 및 다른 팀원들의 아이디로 들어가서 확인을 하려고 하였으나 로그가 확인되지 않는 부분등이 있었고, 로그가 있어도 해당하지 않은 이슈들이라 꽤나 큰 시행착오를 겪었다. 그러다가, **협력 미션으로 저장되는 총 값이 클라이언트가 처리할 수 있는 자료형의 범위를 벗어나는**것을 뒤늦게 확인하여 이슈를 해결할 수 있었다. 해당 원인을 좁히는 과정과, 값을 서버쪽에서 **범위를 넘는 값을 최대치로 제한**하는 방식으로 해결한 과정을 정리하였다.

---

## 장애 증상

- 발생 시점: 특정 시각
- 발생화면: 미니게임 선택 -> 미니/탑으로 들어가야 되나 들어가지질 않음
- 증상: 공통 예외 코드 `99999` 표시 후 타이틀 화면으로 강제 이동
- 접수: 동일 증상 문의 3건

정상적인 흐름이면

```text
미니게임 선택
    │
    ▼
mini/top 요청
    │
    ▼
미니게임 정보 응답
    │
    ▼
미니게임 TOP 화면 진입
```

문제가 발생한 사용자 및 이후 로그인한 유저들에게 다음과 같은 흐름이 발생했다.

```text
미니게임 선택
    │
    ▼
mini/top 요청
    │
    ▼
서버 응답
    │
    ▼
클라이언트 응답 처리 실패(이때까진 몰랐음)
    │
    ▼
99999
    │
    ▼
타이틀 화면 이동
```

처음에는 `99999`가 표시되어 서버 API 및 처리 과정에서 예외가 발생했을 경우를 우선으로 의심하고 로그나 해당 코드 등을 확인하였다.

---

## 첫 번째 확인 - 라이브 서버 로그 추적

해당 문의가 발생한 시간대를 기준으로 라이브 API 로그를 확인하였다.

확인하려고 했던 것은 다음과 같았다.

```text
1. 해당 사용자의 mini/top 요청이 서버까지 들어왔는가?
2. Laravel에서 Exception이 발생했는지?
3. DB 조회 중 문제가 발생했는지?
4. Redis 또는 다른 외부 의존성에서 문제가 발생했는지?
5. 특정 사용자 데이터 때문에 서버 로직이 실패했는지?
```

기획팀 및 다른 팀원들의 계정으로 미니게임 `mini/get_list`까진 직접 진입할 수 있었고, 해당 리스트에 있는 탑에 들어가려고 할 때 이슈가 생겼기에 로그와 데이터를 비교하였다.

생각했던 것과 달리 서버에서 원인을 바로 확인할 수 없었고, 일부 요청은 관련 로그를 찾기 어려웠고 확인한 로그들은 해당 이슈와 직접적인 관련이 없는 내용이었다.

**서버 쪽에서는 요청 자체가 정상적으로 처리되고 있었다.**

```text
서버 요청 수신
-> 로직 실행
-> DB 조회
-> 응답 생성
-> 정상 반환
```

까지는 문제가 없었고 서버의 Exception 로그만 계속 확인해서 원인을 찾기 어려웠다.

---

## 방향 전환 - 서버 로직이 아닌 응답 데이터 확인

서버에서 명확한 예외 및 에러 로그 등이 확인되지 않아 범위를 넓혔다.

`서버에서 에러가 발생했는가?`에서 `서버가 어떤 값을 응답하고 있는가?`를 확인하였다.

문제가 발생한 미니게임 스케줄의 데이터를 하나씩 확인하는 과정에서 **협력 미션과 관련된 누적된 점수 값**이 예상했던 값보다 훨씬 크게 누적되어 있는 것을 확인하였다.

해당 값은 일정 기간 동안 누적되며 매우 큰 값까지 증가한 상태였고, 관련 부분은 서버에서 진작에 Int에서 BigInt로 자료형 자체를 변경하여 적용시켰다(MySQL 자료형).

문제는 해당 값을 전달받는 **Unity 클라이언트 응답 자료형**이었다.

---

## 원인 - 협력 점수가 클라이언트 자료형 범위를 넘음

확인 결과, 협력 미션 누적 점수가 Unity에서 해당 응답 필드에 사용하고 있던 정수 자료형의 최대값을 넘어선 상태였다.

대표적인 정수 자료형의 범위는 다음과 같다.

| 자료형         | 최대값                    |
| -------------- | ------------------------- |
| `Int32`        | 2,147,483,647             |
| `UInt32`       | 4,294,967,295             |
| `Int64 / long` | 9,223,372,036,854,775,807 |

서버에서 더 큰 범위의 숫자를 정상적으로 처리할 수 있어 문제가 드러나지 않았다.

클라이언트는 해당 응답값을 더 작은 범위의 정수 자료형으로 처리하고 있었다.

```text
협력 미션 누적 점수 증가
    │
    ▼
클라이언트 자료형 최대 범위 초과
    │
    ▼
mini/top 요청
    │
    ▼
서버에서 정상적으로 값 조회
    │
    ▼
JSON 응답 정상 반환
    │
    ▼
Unity에서 응답 역직렬화
    │
    ▼
해당 정수 값을 자료형에 담을 수 없다
    │
    ▼
JSON 파싱 / 역직렬화 실패
    │
    ▼
오류 99999
    │
    ▼
타이틀 화면 이동
```

서버 입장에서는 **정상적인 응답**이었으나 클라이언트 입장에서는 **처리할 수 없는 응답**이었다.

## 개발 환경에서 재현

원인을 확정하기 위해 개발 환경에 동일한 조건을 만들어 확인했다.

라이브에서 문제가 발생한 수준과 동일하게 협력 미션 점수를 크게 만든 뒤 미니게임에 진입했다.

결과적으로 서버에서 여전히 정상적인 응답을 반환했으나, 클라이언트에서 JSON 응답 처리 과정에서 오류가 발생하는 것을 확인할 수 있었다.

값을 클라이언트에서 처리 가능한 범위 안(마스터 설정 기준)으로 낮추면 정상적으로 미니게임 화면에 진입할 수 있었다.

해당 조건을 확인했다.

```text
점수 <= 클라이언트 처리 가능 범위 -> 정상

점수 > 클라이언트 처리 가능 범위 -> JSON 응답 처리 실패 -> 99999
```

라이브에서 서버 로그만 확인했기에 보이지 않았던 문제가 개발 환경에서 동일한 데이터를 직접 넣었을 때 드러났다.

## 서버 로그에서 나오지 않았던 이유

해당 이슈에서 가장 많은 시간을 사용했던 이유다.

일반적인 서버 장애라면 다음과 같은 흔적을 기대할 수 있다.

```text
Exception

SQL Error

Redis Error

HTTP 500

Validation Error 등
```

이번 장애에서는 서버가 정상적으로 요청을 처리했었다.

```text
Request
    ↓
Server Logic
    ↓
DB Query
    ↓
Response 생성
    ↓
HTTP 정상 응답
```

오류는 그 이후에 발생했다.

```text
HTTP 정상 응답
    ↓
Unity 응답 수신
    ↓
JSON Deserialize
    ↓
Integer 변환 실패
    ↓
클라이언트 공통 예외
```

서버의 로그만 확인하면 문제가 없는 것처럼 보일 수밖에 없다.

해당 이슈를 통해 **HTTP 200이나 서버 정상 로그가 반드시 정상적인 서비스 동작을 의미하는 것은 아니다**라는 것을 다시 확인할 수 있었다.
