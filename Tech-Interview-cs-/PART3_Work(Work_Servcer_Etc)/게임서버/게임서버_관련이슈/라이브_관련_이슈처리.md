# 서버는 정상, 클라이언트에서 실패한 협력 점수 범위 초과 이슈

## 정리

"미니게임을 선택하면 오류 `99999`가 발생하고 타이틀 화면으로 돌아간다."

라는 동일한 문의가 3건 접수되었다.

처음에는 공통 오류 코드인 `99999`가 표시되었기 때문에 서버 API에서 예외가 발생했을 가능성을 우선적으로 의심했다.

문의가 발생한 시간대의 라이브 서버 로그를 확인하고, 기획팀 및 다른 팀원들의 계정으로 직접 미니게임에 진입하면서 데이터를 비교했다.

하지만 서버에서는 명확한 Exception이 확인되지 않았고, 일부 로그는 해당 현상과 관련이 없었다.

원인을 계속 좁혀가던 중, 문제는 서버 로직 자체가 아니라 **서버가 클라이언트에 전달하고 있던 협력 미션 누적 점수의 크기**에 있다는 것을 확인했다.

협력 미션의 누적 점수가 계속 증가하면서 Unity 클라이언트가 해당 응답 필드에서 처리할 수 있는 정수 자료형의 범위를 넘어섰고, 그 결과 서버에서는 정상 응답을 반환했지만 클라이언트의 JSON 역직렬화 과정에서 실패하고 있었다.

이번 글에서는 해당 원인을 추적한 과정과 원본 누적 데이터는 유지하면서 **클라이언트에 전달하는 값을 마스터에 정의된 최대 점수까지만 제한하여 해결한 과정**을 정리한다.

---

## 장애 증상

- 발생 시점: 특정 미니게임 스케줄 진행 중
- 발생 화면: 미니게임 목록에서 특정 미니게임 선택
- 증상: 공통 예외 코드 `99999` 표시 후 타이틀 화면으로 강제 이동
- 접수: 동일 증상 문의 3건

정상적인 흐름은 다음과 같다.

```text
미니게임 선택
    │
    ▼
mini/top 요청
    │
    ▼
서버에서 미니게임 정보 응답
    │
    ▼
클라이언트 응답 처리
    │
    ▼
미니게임 TOP 화면 진입
```

문제가 발생했을 때 실제 흐름은 다음과 같았다.

```text
미니게임 선택
    │
    ▼
mini/top 요청
    │
    ▼
서버 정상 응답
    │
    ▼
클라이언트 응답 처리 실패
    │
    ▼
99999
    │
    ▼
타이틀 화면 이동
```

당시에는 클라이언트의 응답 처리 과정에서 문제가 발생하고 있다는 것을 알지 못했기 때문에, 처음에는 서버 API 내부에서 예외가 발생하고 있을 가능성을 우선적으로 확인했다.

---

## 첫 번째 확인 - 라이브 서버 로그 추적

문의가 발생한 시간대를 기준으로 라이브 API 로그를 확인했다.

주로 다음 항목들을 확인했다.

```text
1. 해당 사용자의 mini/top 요청이 서버까지 들어왔는가?
2. Laravel 내부에서 Exception이 발생했는가?
3. DB 조회 과정에서 오류가 발생했는가?
4. Redis 등 외부 의존성에서 문제가 발생했는가?
5. 특정 사용자 데이터 때문에 서버 로직이 실패했는가?
```

기획팀 및 다른 팀원들의 계정으로도 직접 확인했다.

```text
mini/get_list
    │
    ▼
미니게임 목록 정상 조회
    │
    ▼
특정 미니게임 선택
    │
    ▼
mini/top
    │
    ▼
99999 발생
```

`mini/get_list`까지는 정상적으로 진입할 수 있었지만 특정 미니게임의 TOP 화면으로 들어가는 과정에서 문제가 발생했다.

따라서 해당 시점의 로그와 사용자 데이터를 중심으로 확인했지만, 예상과 달리 서버에서 원인을 바로 찾을 수 없었다.

일부 요청은 관련 로그를 특정하기 어려웠고, 확인된 오류 로그 역시 이번 현상과 직접적인 관련이 없는 내용이었다.

결과적으로 서버에서는 다음 과정이 정상적으로 진행되고 있었다.

```text
서버 요청 수신
    ↓
비즈니스 로직 실행
    ↓
DB 조회
    ↓
응답 데이터 생성
    ↓
HTTP 정상 응답
```

즉, 서버의 Exception 로그만 계속 확인해서는 원인을 찾기 어려운 상황이었다.

---

## 방향 전환 - 서버 오류가 아니라 응답 데이터 확인

서버에서 명확한 예외나 에러 로그가 확인되지 않았기 때문에 조사 범위를 넓혔다.

기존에는 다음 질문에 집중하고 있었다.

```text
"서버에서 어떤 에러가 발생했는가?"
```

하지만 서버가 요청을 정상적으로 처리하고 있다는 것을 확인한 뒤에는 질문을 다음과 같이 변경했다.

```text
"서버가 클라이언트에게 실제로 어떤 값을 응답하고 있는가?"
```

문제가 발생한 미니게임 스케줄과 관련된 데이터를 하나씩 확인하던 중 **협력 미션의 누적 점수가 예상보다 매우 큰 값까지 증가해 있는 것**을 발견했다.

해당 점수는 일정 기간 동안 계속 누적되는 데이터였다.

서버에서는 이전부터 큰 누적값을 처리할 수 있도록 MySQL 컬럼의 자료형을 `BIGINT`로 확장해 둔 상태였기 때문에 서버 측에서는 해당 값을 정상적으로 저장하고 조회할 수 있었다.

문제는 이 값을 전달받는 **Unity 클라이언트의 응답 DTO 자료형**이었다.

---

## 원인 - 협력 점수가 클라이언트 자료형 범위를 초과

확인 결과 협력 미션 누적 점수가 Unity에서 해당 응답 필드에 사용하고 있던 정수 자료형의 범위를 넘어선 상태였다.

대표적인 정수 자료형의 범위는 다음과 같다.

| 자료형         |                    최대값 |
| -------------- | ------------------------: |
| `Int32`        |             2,147,483,647 |
| `UInt32`       |             4,294,967,295 |
| `Int64 / long` | 9,223,372,036,854,775,807 |

서버에서는 더 큰 범위의 정수를 정상적으로 저장하고 처리할 수 있었기 때문에 별도의 Exception이 발생하지 않았다.

하지만 클라이언트에서는 해당 응답 필드를 서버보다 작은 범위의 정수 자료형으로 처리하고 있었다.

따라서 다음과 같은 문제가 발생했다.

```text
협력 미션 누적 점수 증가
    │
    ▼
클라이언트 응답 자료형 범위 초과
    │
    ▼
mini/top 요청
    │
    ▼
서버에서 정상적으로 값 조회
    │
    ▼
JSON 응답 정상 생성
    │
    ▼
HTTP 정상 응답
    │
    ▼
Unity에서 JSON 역직렬화
    │
    ▼
응답 숫자를 지정된 정수 자료형에 저장할 수 없음
    │
    ▼
역직렬화 실패
    │
    ▼
클라이언트 공통 오류 처리
    │
    ▼
99999
    │
    ▼
타이틀 화면 이동
```

즉, 서버 입장에서는 **문법적으로도 정상이고 처리 과정에도 문제가 없는 응답**이었다.

하지만 클라이언트 입장에서는 **자신의 DTO 자료형으로 변환할 수 없는 응답값**이었다.

---

## 개발 환경에서 재현

원인을 확정하기 위해 개발 환경에서 동일한 조건을 만들어 재현했다.

라이브에서 문제가 발생한 것과 유사하게 협력 미션 누적 점수를 매우 큰 값으로 설정한 뒤 미니게임에 진입했다.

서버에서는 여전히 정상적으로 JSON 응답을 반환했다.

하지만 Unity 클라이언트에서는 응답 처리 과정에서 역직렬화 오류가 발생했다.

반대로 점수를 클라이언트가 처리 가능한 범위로 낮춘 뒤 다시 요청하면 정상적으로 미니게임 TOP 화면에 진입할 수 있었다.

결과적으로 다음 조건을 확인할 수 있었다.

```text
응답값이 클라이언트 자료형 범위 내
    ↓
정상 역직렬화
    ↓
정상 진입
```

```text
응답값이 클라이언트 자료형 범위 초과
    ↓
JSON 역직렬화 실패
    ↓
99999
```

라이브 환경에서는 서버 로그만 중심적으로 확인하고 있었기 때문에 발견하기 어려웠지만, 개발 환경에서 동일한 수준의 데이터를 직접 만들어 테스트하면서 원인을 명확하게 확인할 수 있었다.

## 서버 로그에서 원인이 나오지 않았던 이유

이번 이슈에서 가장 많은 시간을 사용했던 부분이다.

일반적인 서버 장애라면 다음과 같은 흔적을 예상할 수 있다.

```text
Exception

SQL Error

Redis Error

HTTP 500

Validation Error
```

하지만 이번 장애에서는 서버가 요청을 정상적으로 처리하고 있었다.

```text
Request
    ↓
Server Logic
    ↓
DB Query
    ↓
Response 생성
    ↓
HTTP 정상 응답
```

실제 오류는 서버가 응답을 완료한 이후에 발생했다.

```text
HTTP 정상 응답
    ↓
Unity 응답 수신
    ↓
JSON Deserialize
    ↓
Integer 변환 실패
    ↓
클라이언트 공통 예외 처리
```

따라서 서버 로그만 보면 요청이 정상적으로 처리된 것처럼 보일 수밖에 없었다.

이번 이슈를 통해 다시 확인한 부분은 다음과 같다.

> **HTTP 200 또는 서버 정상 로그가 반드시 최종적인 서비스 정상 동작을 의미하지는 않는다.**

서버가 정상적으로 응답하더라도 클라이언트가 해당 응답을 정상적으로 해석하고 사용할 수 있는지까지 확인해야 한다.

## 해결 방법 검토

원인을 확인한 뒤 몇 가지 해결 방법을 검토했다.

### 1. 원본 누적 점수를 직접 수정

가장 단순하게 생각할 수 있는 방법은 누적된 협력 점수를 직접 낮추는 것이다.

```text
현재 누적 점수
    ↓
원본 데이터 수정
    ↓
클라이언트 처리 가능 범위로 변경
```

하지만 해당 값은 단순히 화면에 표시하기 위한 값이 아니다.

협력 미션과 관련된 다른 서버 로직에서도 사용되는 실제 누적 데이터이며, 집계 과정에서도 Redis 등의 데이터를 이용하고 있기 때문에 장애 해결을 위해 원본 누적값 자체를 임의로 변경하는 방식은 적절하지 않다고 판단했다.

특히 원본 데이터를 수정하면 현재까지 정상적으로 누적된 협력 미션 진행도 자체가 변경될 수 있다.

따라서 이 방법은 제외했다.

---

### 2. 클라이언트 자료형 변경

클라이언트 응답 모델에서 해당 필드의 자료형을 더 큰 범위의 타입으로 변경하는 방법도 있다.

예를 들면 다음과 같다.

```text
int
 ↓
long
```

장기적으로는 서버와 클라이언트 간 자료형을 다시 맞추는 것이 하나의 해결책이 될 수 있다.

하지만 당시 장애를 즉시 해결해야 하는 상황에서 클라이언트 수정은 새로운 클라이언트 빌드와 배포 과정이 필요했다.

게임 클라이언트의 경우 서버 패치처럼 즉시 반영하기 어렵기 때문에 긴급 대응 방법으로는 적합하지 않다고 판단했다.

---

### 3. 서버 응답 단계에서 최대값 제한

최종적으로 선택한 방법은 **원본 데이터는 그대로 유지하고 클라이언트에 전달되는 응답값만 제한하는 것**이었다.

협력 미션에는 마스터에서 정의한 최대 점수가 존재한다.

클라이언트에서는 해당 최대 점수를 초과한 값을 실제 진행도 표시에 사용할 필요가 없기 때문에, 누적 점수가 마스터 최대 점수를 초과한 경우 응답 단계에서 최대 점수까지만 전달하도록 처리했다.

```text
실제 누적 점수
    ↓
서버에서 조회
    ↓
마스터 최대 점수와 비교
        │
   ┌────┴────┐
   │         │
초과하지 않음  초과함
   │         │
실제 값      최대값
   │         │
   └────┬────┘
        ▼
클라이언트 응답
```

이 방법을 선택하면 다음과 같은 장점이 있었다.

```text
원본 누적 데이터 유지

기존 협력 미션 계산 로직 유지

다른 서버 로직에 미치는 영향 최소화

클라이언트 수정 불필요

서버 패치만으로 즉시 대응 가능
```

---

## 서버 패치

실제 패치에서는 협력 미션의 누적 점수가 마스터에 설정된 최대 점수를 초과하는 경우, 초과된 값을 그대로 클라이언트에 전달하지 않도록 처리했다.

개념적으로 표현하면 다음과 같다.

```php
$exampleScore = $exampleGlobal->exampleScore;
$exampleMaxScore = $exampleMaster->example_max_score;

$responseExampleScore = min(
    $exampleScore,
    $exampleMaxScore
);
```

예를 들어 실제 누적 점수가 다음과 같다고 가정한다.

```text
실제 누적 점수: 3,000,000,000

마스터 최대 점수: 2,000,000,000
```

기존에는 다음 값이 그대로 클라이언트에 전달됐다.

```text
3,000,000,000
```

패치 이후에는 다음 값까지만 전달한다.

```text
2,000,000,000
```

즉,

> **원본 누적 데이터를 삭제하거나 변경하는 것이 아니라 클라이언트로 전달되는 값만 마스터의 유효 범위로 제한한다.**

실제 프로젝트 구조를 단순화해서 표현하면 다음과 같다.

```php
public function getExampleScore(
    ExampleGlobal $exampleGlobal,
    ExampleMaster $exampleMaster,
): int {
    return min(
        (int) $exampleGlobal->exampleScore,
        (int) $exampleMaster->example_max_score,
    );
}
```

처리 방식의 핵심은 다음과 같다.

```text
클라이언트에서 사용할 필요가 없는 초과 누적값은
응답 단계에서 마스터 최대값으로 제한한다.
```

## 패치 검증

패치 이후 동일한 조건과 환경을 만들어 다시 검증했다.

### 서버 응답 검증

다음과 같은 상태를 만들었다.

```text
실제 협력 점수 > 마스터 최대 점수
```

그리고 `mini/top` 응답을 확인했다.

```text
응답 점수 = 마스터 최대 점수
```

로 반환되는 것을 확인했다.

즉,

```text
실제 데이터
3,000,000,000

↓

마스터 최대값
2,000,000,000

↓

클라이언트 응답
2,000,000,000
```

의 형태로 동작했다.

원본 누적 점수 자체는 그대로 유지된다.

```text
DB / Redis 실제 누적값
3,000,000,000
```

클라이언트에 전달되는 값만 제한된다.

```text
Response
2,000,000,000
```

## 클라이언트 검증

동일한 데이터에서 게임 클라이언트로 다시 진입했다.

패치 이전에는 다음과 같이 동작했다.

```text
mini/top
    ↓
큰 협력 점수 응답
    ↓
Unity 역직렬화 실패
    ↓
99999
    ↓
타이틀 이동
```

패치 이후에는 다음과 같이 정상적으로 처리됐다.

```text
mini/top
    ↓
마스터 최대값으로 제한된 점수 응답
    ↓
Unity 정상 역직렬화
    ↓
미니게임 TOP 화면 정상 진입
```

최종적으로 다음 항목들을 확인했다.

- 동일한 데이터에서 JSON 역직렬화 오류가 발생하지 않는다.
- 미니게임 선택 시 `99999`가 발생하지 않는다.
- 미니게임 TOP 화면에 정상적으로 진입한다.
- 응답 점수가 마스터에 설정된 최대 점수를 초과하지 않는다.
- 실제 서버의 누적 데이터는 변경되지 않는다.

라이브 패치 이후 기존에 접수되었던 동일 증상도 해결된 것을 확인했다.

---

## 해당 이슈에서 확인이 오래 걸린 부분

이번 이슈에서 실제 해결 코드는 복잡하지 않았다.

결과적으로 필요한 처리는 다음 한 줄과 비슷하다.

```php
min($exampleCurrentScore, $exampleMaxScore);
```

하지만 어려웠던 부분은 코드를 작성하는 것이 아니라 **문제가 발생하고 있는 위치를 찾는 과정**이었다.

처음에는 `99999`가 발생했기 때문에 서버 이슈라고 생각했고, 서버 로그와 사용자 데이터를 중심으로 계속 확인했다.

하지만 실제 상태는 다음과 같았다.

```text
서버 요청 정상

서버 로직 정상

DB 조회 정상

응답 생성 정상

HTTP 응답 정상

JSON 자체 정상

클라이언트 자료형 범위 초과

Unity 역직렬화 실패
```

즉, **사용자에게 오류가 표시되는 위치와 실제 원인이 발생한 위치가 달랐다.**

서버에서는 모든 처리가 끝난 이후였기 때문에 서버 Exception 로그만으로는 찾기 어려운 문제였다.

---

## 해당 이슈를 통해 배운 점

### 1. 서버 로그에 문제가 없다면 실제 응답까지 확인해야 한다

서버 예외가 없다고 해서 전체 요청 흐름이 정상이라고 확언할 수는 없다.

게임 서버처럼 서버와 Unity 클라이언트의 DTO가 강하게 연결되어 있는 환경에서는 실제 Response 데이터까지 확인할 필요가 있다.

```text
서버 로그 확인
    ↓
이상 없음
    ↓
HTTP 응답 확인
    ↓
Response JSON 확인
    ↓
필드별 실제 값 확인
    ↓
클라이언트 DTO 자료형 확인
```

서버 내부에서 문제가 발견되지 않는다면 이런 식으로 조사 범위를 점차 넓혀야 한다.

---

### 2. 숫자는 타입뿐 아니라 값의 범위도 확인해야 한다

일반적으로 데이터 문제를 확인할 때 다음 항목들을 많이 확인한다.

```text
null인가?

필드가 누락되었는가?

타입이 다른가?

잘못된 ID인가?

DB 데이터가 존재하는가?
```

하지만 숫자 데이터에는 하나를 더 확인할 필요가 있다.

```text
해당 값이 자료형의 범위를 넘어가지 않았는가?
```

특히 누적 데이터는 서비스 운영 기간이 길어지면서 처음 설계 당시 예상했던 크기를 넘어설 수 있다.

```text
100
 ↓
1,000
 ↓
1,000,000
 ↓
1,000,000,000
 ↓
자료형 최대값 접근
 ↓
Overflow / Deserialize 문제 발생
```

서버의 DB 컬럼을 `BIGINT`로 변경했다고 해서 모든 문제가 해결되는 것은 아니다.

서버와 클라이언트가 서로 다른 자료형을 사용한다면 다음 전체 구간을 확인해야 한다.

```text
Database
    ↓
Server Model
    ↓
Server DTO
    ↓
JSON
    ↓
Client DTO
```

---

### 3. 서버가 처리할 수 있는 값과 클라이언트가 필요한 값은 다를 수 있다

이번 협력 미션 점수는 서버에서는 실제 누적값을 계속 유지할 필요가 있었다.

하지만 클라이언트에서는 마스터 최대 점수를 넘어간 이후의 값까지 사용할 필요가 없었다.

예를 들어 다음과 같다.

```text
마스터 목표
2,000,000,000

실제 누적
3,000,000,000
```

클라이언트 입장에서는

```text
2,000,000,000 / 2,000,000,000
```

까지만 알면 해당 미션이 최대치에 도달했다는 사실을 판단할 수 있다.

따라서 서버 내부에서는 실제 누적값을 보존하고,

```text
Server
3,000,000,000
```

클라이언트에는 필요한 값까지만 전달한다.

```text
Client Response
2,000,000,000
```

이렇게 서버 내부 데이터와 외부 응답 데이터를 분리하면 기존 집계 로직을 유지하면서도 클라이언트와의 호환성을 지킬 수 있다.

## 마무리

이번 장애는 서버 로직의 Exception이나 DB 오류가 아니라 **서버와 클라이언트 사이의 숫자 자료형 범위 차이**에서 발생한 문제였다.

특히 서버에서는 요청을 정상적으로 처리하고 있었기 때문에 처음에는 서버 로그를 중심으로 원인을 추적했고, 그 과정에서 많은 시행착오를 겪었다.

하지만 서버가 정상적으로 응답하고 있다는 것을 확인한 뒤 조사 범위를 Response와 클라이언트까지 넓히면서 원인을 찾을 수 있었다.

서버가 정상적으로 응답했는데도 사용자가 오류를 경험한다면 문제의 범위를 서버 내부에만 한정해서는 안 된다.

```text
Server Logic
    ↓
Database
    ↓
Response DTO
    ↓
Response JSON
    ↓
Network
    ↓
Client DTO
    ↓
Deserialize
    ↓
Client Logic
```

전체 흐름을 확인할 필요가 있다.

또한 이번 사례처럼 누적되는 숫자 데이터는 현재 정상적인 값이라 하더라도 서비스 운영 기간이 길어지면서 자료형의 한계를 넘어설 수 있다.

이번에는 원본 데이터를 직접 수정하는 대신 다음 방식으로 해결했다.

```text
실제 누적 데이터는 그대로 유지

+

클라이언트에 필요한 범위까지만 응답
```

이를 통해 기존 협력 미션의 누적 및 집계 로직에 영향을 주지 않으면서 클라이언트에서 발생하던 역직렬화 문제를 해결할 수 있었다.
