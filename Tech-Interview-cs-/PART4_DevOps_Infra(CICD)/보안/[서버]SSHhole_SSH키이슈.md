# 🌐 SSHhole 이슈 | 비밀번호 해시가 없는 계정에 OpenSSH 인증이 우회된 이유

SSH 키로만 접속하도록 만든 계정에 비밀번호 로그인이 성공하면 어디서 문제가 생긴 이슈일까? 2026년 11월 5일 공개된 **SSHhole(CVE-2026-123158)**의 OpenSSh 서버 취약점이다. musl libc를 사용하는 일부 리눅스에서 PAM 없이 비밀번호를 검증할 때, 해시 계산 실패가 인증 성공으로 처리될 수 있었다.
[OpenSSH 릴리스 노트][openssh] · [KISA 보안 공지][kisa]

## `/etc/shadow`의 `*`는 무엇인지

리눅스는 로컬 계정의 비밀번호 해시를 `/etc/shadow`에 저장. Alpine linux에 필드가 `*`인 계정이 있음. `*`sms **사용 가능한 비밀번호 해시가 없다는 표시**다. SSH 키 전용 계정도 의도적으로 이 상태로 운영할 수 있음
비밀번호 등록이 끝나지 않은 계정만 생각, 정상적으로 운영 중인 키 전용 계정을 점검에서 빠뜨리게 된다.
[Alpine 보안 공지][alpine]

계정의 비밀번호 필드와 서버의 인증 정책은 서로 다른 층에 있다. 계정 하나에 `*`가 들어 있어도, `sshd`에 비밀번호 인증을 허용하면 그 검증 경로는 열려 있음. Alpine 공지는 비밀번호 필드가 `!`인 잠금 계정과 `*`가 들어있는 계정을 구분. 영향 여부를 판단하면 실제 저장 상태와 로그인 정책을 함께 확인.
[Alpine 보안 공지][alpine]

## 해시 게산 실패가 어떻게 인증 성공으로 이어졌는 지

PAM을 사용하지 않는 OpenSSH의 비밀번호 인증 경로는 `crypt()`로 입력값을 해시한 다음 저장된 값과 비교. 이 과정에 musldml `crypt()`는 입력이 길이 제한을 넘으면 오류 표시로 `*`를 반환할 수 있음. 길이 제한의 단위는 **바이트**다. 취약한 검증 경로에 반환값과 계정에 저장된 `*`가 같은 문자열로 비교되며 인증이 성공할 수 있었다
[Alpine 보안 공지][alpine]

| 값                            | 의미                                  |
| ----------------------------- | ------------------------------------- |
| `/etc/shadow`에 저장된 `*`    | 사용 가능한 비밀번호 해시가 없는 계정 |
| musl의 `crypt()`가 돌려준 `*` | 해시 계산 실패                        |

두 값의 문자열 표현은 같지만 의미는 다름. 인증 코드가 문자열을 비교하기 전에 **계산이 성공했는지**와 **저장된 값이 유효한 해시인지**를 구분해야 하는 이유. OpenSSH 10.6p2에 오류가 인증 우회로 이어지지 않도록 서버 측 수정이 들어감.
[OpenSSH 릴리스 노트][openssh] · [OpenSSH 수정 커밋][patch]

## 어떤 서버가 영향을 받는지

Alpine 공식 공지를 기준으로 보면 영향 여부는 아래 조건의 조합으로 결정. [Alpine 보안 공지][alpine]

| 항목           | 조건                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------- |
| 실행 환경      | musl libc 기반 리눅스에 수정 전 OpenSSH 서버(`sshd`)가 동작하고 PAM을 사용하지 않음         |
| 서버 정책      | 해당 계정에 SSH 비밀번호 인증이 허용되어 있음                                               |
| 계정 상태      | 해당 계정의 비밀번호 필드가 `*`이며 SSH 로그인 정책상 접근 가능한 계정                      |
| 다른 로컬 계정 | 같은 시스템에 SHA-256 crypt 또는 SHA-512 crypt 방식의 비밀번호 해시를 가진 로컬 계정이 있음 |

Alpine 기반 Docker 이미지면 먼저 컨테이너가 `sshd`를 실제로 실행하는지 보면 된다. 일반적인 glibc 기반 Ubuntu·Debian 환경과 PAM을 사용해 검증하는 OpenSSH 환경은 이슈의 영향 범위에서 벗어난다.

**키로만 열리도록 해 둔 문에서 잠금장치가 오류를 통과 신호로 받아들인 셈**이다. Alpine 공지는 일부 공식 클라우드 이미지 기본 계정을 사례로 들었다. 계정은 SSH 키로 접속하도록 설정되어 있었고, 로그인 후에 비밀번호 없이 `doas`를 사용할 수 있음. 해당 인스턴스가 취약 조건을 충족하면 일반 계정의 인증 우회가 관리자 권한 획득으로 이어질 수 있음

## 운영 서버에 확인

1. **배포판이 제공하는 수정 패키지를 적용 `sshd`를 재시작.** OpenSSH의 공식 수정 버전은 `10.6p2`다. Alpine은 기존 배포판 브랜치에 수정 사항을 백포트. Alpine 3.24 수정 패키지는 `10.3_p1-r2`다. 설치된 패키지 버전을 배포판 공지의 브랜치별 버전과 대조 후 업데이트 후 실행.
2. **당장 패치할 수 없으면 SSH 비밀번호 인증을 끔.** `PasswordAuthentication no`를 적용하고 `sshd`를 재시작한다. 작업 전 SSH 키 로그인이 가능한지 확인, 기존 세션을 유지한 채 세션으로 접속을 검증. `Match` 블록으로 계정별 설정을 관리하면 해당 조건에서 비밀번호 인증이 꺼졌는 지 확인
3. **키 전용 계정의 비밀번호 로그인 기록을 확인**
